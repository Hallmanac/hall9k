# Hall9k - Agentic Workflow Platform - Planning Document

**Status:** Initial plan, output of exploration/discovery conversation (Aug 2026). Living document - refine in Claude Code as build proceeds.
**Owner:** Brian Hall ("Hallmanac") - solo builder, v0 user count = 1
**Name:** **Hall9k** - Hall (owner's name / "Hallmanac") + HAL 9000. The wink is the thesis: HAL is the AI that escaped supervision; Hall9k exists to keep the human in the loop. Conventions: repo/org/CLI `hall9k`, namespaces `Hall9k.*` (e.g. `Hall9k.Cli`, `Hall9k.Daemon`, `Hall9k.Domain`).
**Purpose:** Define what we're building, why, the architecture, the domain model, and a build plan. This doc seeds the Claude Code project (`PLAN.md` / basis for `CLAUDE.md`).

---

## 1. Vision & Goal

Move from **Level 2 (Parallel - human orchestrates ~10 agents manually)** to **Level 3 (Supervised Autonomy - agents run semi-autonomously, human supervises at checkpoints)** per Anthropic's "Steps of AI Adoption" (Boris Cherny, Jul 2026).

The Step 2 → 3 recipe from that doc is effectively our build spec:

1. Let Claude pull its own context (agents read code/wikis/docs themselves)
2. Break work into loops and routines (repeatable named workflows, not ad-hoc prompts)
3. Let Claude kick off Claude (orchestration loop; one agent dispatches others)
4. Trust in the loop (automated verification/review so the human stops reading everything)

**#4 is the real bottleneck at Level 3** - the dispatcher is the easy part; the verification pipeline that lets the human *not look* is where a homegrown build earns its keep, because trust gets calibrated to our own standards.

### Deployment philosophy: local-first, P2P later, portal maybe

**Hall9k runs locally.** It is a CLI app on the PATH plus a daemon running in the background on the user's machine. There is no cloud host.

- **Now (v0):** one machine, one node: `h9k` CLI + `h9kd` daemon + local Postgres (container).
- **Later:** a **decentralized network of nodes** - each machine runs its own daemon + Postgres; nodes coordinate with each other so work shards across machines (possibly working the same projects).
- **Maybe eventually:** a web portal as a nicer remote window into the nodes - manage tasks away from the machines. Far down the priority list; nothing in the core design depends on it.

### What this platform is

An **orchestration brain over external systems**, running on your own machines:

- **Work items** (tasks, epics) live in **Jira or GitHub** - they are the source of truth once work is published.
- **Code and PRs** live in **GitHub** (always).
- **Agents** (AI coding sessions) run locally, spawned and supervised by the node's daemon.
- The platform itself owns: the **funnel** (ideas → triage → discovery → publish), **orchestration state**, **connector configs**, **run logs/learnings**, and the **attention surface** (what's awaiting the human).

### What this platform is not

- Not a kanban board / work tracker (Jira & GitHub already do that).
- Not an agent runtime (Claude Code / Agent SDK already do that).
- Not a hosted web app / SaaS. Local-first is the identity, not a stopgap.

## 2. Core Concepts & Vocabulary

| Term | Meaning |
|---|---|
| **Idea** | Anything entering the funnel: bug report, feature thought, big initiative. Deliberately unstructured at capture. Lives on the platform, never in Jira/GitHub. |
| **Inbox** | Node-level queue of new ideas awaiting triage. |
| **Triage** | Decision gate: pursue now / park / kill. Parked ideas keep history; a `resurfaced_count` gives recurring ideas weight over time. |
| **Discovery** | Interactive process turning a pursued idea into implementable work: an interview-style agent session that drafts scope, breakdown, and acceptance criteria. Includes what other shops call "refinement" - exit criterion is "tasks are dispatch-ready." |
| **Refinement** | The *backward* loop: implementation discovered the work was mis-shaped ("this task is really 3 tasks"), so it goes back for re-discovery. Same muscle as discovery, different trigger. |
| **Publish** | One-way handoff: discovery output is written to Jira/GitHub as work items. From that moment, the external system is the source of truth. No two-way content sync, ever. |
| **Adopt** | The reverse of publish: link a task to an *existing* external work item (§3.1a). |
| **Parking garage** | Where parked/killed ideas live, with full history and resurfacing counts. Never touches Jira/GitHub. |
| **Epic** | Optional grouping created only when discovery yields more than one task. Problem scope + objectives + desired outcomes. Never forced - single-card work stands alone. |
| **Task** | The unit of work. Always maps to exactly one Jira card or GitHub issue. Must satisfy the readiness contract (§4) before dispatch. |
| **Project** | A configured workspace: which connections, which repo(s), which Jira project or GitHub issue tracker, its own context (CLAUDE.md), agents' memory. Projects can be *born from the funnel* (triage outcome: "this idea becomes a new project"). |
| **Node** | One machine running Hall9k: `h9kd` daemon + Postgres + spawned agents. v0 = exactly one node; the P2P future is many nodes coordinating. |
| **Daemon (`h9kd`)** | The resident orchestrator process on a node: dispatch loop, run monitoring, lease management, verification orchestration. |
| **CLI (`h9k`)** | Execute-and-exit control surface on the PATH. Used by humans, scripts, *and headless agents*. Thin - logic lives in Domain/daemon. |
| **Agent** | An AI session (Claude Code headless, later possibly Codex/Kimi) spawned by the daemon to do work. |
| **Executor** | The specific AI CLI/SDK the daemon uses to spawn agents (Claude Code = the only v0 executor). |
| **Orchestrator window** | An interactive Claude Code session acting as the conversational UI, driving `h9k`. Stateless and disposable - all state is in Postgres. |

## 3. The Lifecycle

### 3.1 Funnel (lives on the platform)

```
Idea (inbox) → Triage ─┬→ Pursue → Discovery → Publish → [work items in Jira/GitHub]
                       ├→ Park   (→ parking garage; resurfacing tracked)
                       └→ Kill   (→ parking garage, as record)
```

- Ideas are captured with near-zero friction: freeform text + optional attachments/links + optional project assignment. Default state: `triage`.
- Triage can also spawn a **new project** from an idea.
- Discovery is conversational (see §7). Output: an approved breakdown (epic + tasks, or a single task).
- Publish writes to the external system via the connector, records external refs, and links back to the discovery record (**origin link** - implementing agents can pull the full discovery context: conversation, alternatives considered, rejected approaches).
- The **parking garage lives on the platform** - killed/deferred ideas never touch Jira/GitHub.
- **Open question (local-first ingestion):** how ideas get captured when away from the machine is unresolved - see §8.

### 3.1a Adopting existing external work (the reverse funnel exit)

The platform practices **selective adoption, never mirroring**: it tracks only work the user (or their agents) will actually take on. External backlogs are never bulk-synced - critical for the "existing multi-developer project, I own a subset" use case. A 400-card Jira project yields, say, 6 adopted tasks.

Adopted items run through the **same funnel with a different exit**: publish and adopt are the same operation with direction reversed.

```
Point at PROJ-123 / repo#42 → Idea (pre-linked to external ref) → Triage ("am I taking this on?")
  → Discovery → LINK (task created against the EXISTING item; nothing new created externally)
```

Discovery still earns its keep on well-fleshed cards: a card can be *human-ready but not agent-ready*. For adopted items, discovery's output is the platform-side agent context (§4.1) - readiness-contract check, acceptance-criteria extraction, constraints. It's just much faster than greenfield discovery.

The connector interface (§9.2) must support both exits: create (publish) and link (adopt).

**Project onboarding exploration:** when connecting an existing project, an initial discovery-flavored session surveys the repo/board - what is this, current state, greenfield vs. brownfield - and produces the project's context doc (feeds CLAUDE.md / project defaults, and informs which items are worth adopting). In v0 this is simply "human + Claude Code look around the repo together."

### 3.2 Execution (source of truth is external)

```
Task (Jira/GitHub) → Dispatch → Execute → Verify → Checkpoint → Complete
                        ↑                              │
                        └── Refinement ←── needs-human / mis-shaped work
```

1. **Dispatch** - the daemon claims a ready task (lease), prepares an isolated workspace (git worktree), assembles context (task + discovery record + repo + CLAUDE.md), spawns a detached agent session.
2. **Execute** - agent works; the daemon captures stream-json events into the run's event stream.
3. **Verify** - automated gates: build, tests, lint, security scan must pass; then a **separate reviewer agent session** (never the implementer's session) critiques the diff.
4. **Checkpoint** - human approval where required. The human gate for code **is PR review in GitHub** - no custom review UI needed.
5. **Complete** - merge/deliver, transition the external work item, record run artifacts + learnings.

Escape hatch state: **`needs-human`** - agents park a task there with a question instead of guessing. Mis-shaped tasks route to **refinement**.

### 3.3 Task lifecycle states (orchestration metadata, platform-side)

`queued → dispatched → in-progress → verifying → awaiting-review → done | failed | needs-human | needs-refinement`

The external system carries the *human-facing* status (via mapped transitions); the platform carries orchestration state keyed by external ref.

## 4. The Task Readiness Contract

A task cannot be dispatched until it satisfies this contract - "everything an agent needs to succeed without the human present":

1. **Objective** - one sentence, outcome-phrased. ("Add rate limiting to auth endpoints," not "look into rate limiting.")
2. **Context pointers** - where to find what's needed: repo/branch, docs, related task IDs, the discovery record. Pointers, not pasted content - the agent pulls context itself. This is also how **sibling/epic awareness** works for adopted work (§3.1a): sibling cards are never imported as tasks; the agent context points at them ("epic: PROJ-100; siblings: PROJ-121, PROJ-124 - read for boundaries, don't touch their scope") and the agent fetches them live at run time. No import, no staleness, no sync.
3. **Acceptance criteria** - explicit, checkable conditions. **The single highest-leverage field**: it's what verification gates and the reviewer agent test against. If you can't write acceptance criteria, the task isn't ready.
4. **Constraints/guardrails** - what not to touch, allowed tools, budget (max turns/tokens/time).
5. **Task type** - feature / bugfix / refactor / chore / research. Drives persona, prompt template, and verification profile.

Discovery's job is producing tasks that meet this contract. The **readiness gate** is enforced at publish time - nothing reaches the backlog unqualified.

**Tasks produce artifacts, not just diffs**: every run emits a summary, decisions made, and open questions. That's the human's review surface and the memory for future tasks.

### 4.1 The Task entity (platform domain model)

**Task is a first-class platform entity.** The GitHub issue / Jira card is one *linked property* of it - the source of truth for story *content* (title, description, human-facing status), never duplicated platform-side. Everything operational hangs off the platform Task:

| Facet | Contents |
|---|---|
| External ref | Link to the GitHub issue / Jira card (content source of truth) |
| Agent context | The verbose, prescriptive agent-facing material: instructions, context pointers, constraints, verification profile. Deliberately *not* in the issue body - too unwieldy for humans; the issue stays user-story-readable for both humans and agents, the Task carries the agent-only depth. |
| Origin | Link to the discovery record (conversation, alternatives, rejected approaches) |
| Execution | Node binding (project-level default, per-task override), run history, session IDs, agent event stream |
| Deliverables | Linked PR(s) as they're created |
| Economics | Token usage, cost, budget (per §6.4) |
| Conversation | The agent ↔ human message thread (questions, answers, check-ins) |
| Orchestration state | `queued → dispatched → in-progress → verifying → awaiting-review → done \| failed \| needs-human \| needs-refinement` |

Rule of thumb: **content → external system; everything operational → Task entity.**

Being event-sourced, most of this is a projection of the Task's event stream (`RunDispatched`, `RunEventReceived`, `QuestionAsked`, `AnswerProvided`, `PROpened`, `TokensRecorded`, ...) - `h9k task show` and the orchestrator window render straight off it (§12).

**Flagged modeling decision (v0):** an idea does not *mutate into* an epic or task. Discovery **produces** task(s) - plus an epic grouping only when there's more than one - and the idea is archived with origin links both ways. Cleaner event-sourced than entity mutation; confirm when modeling the streams.

## 5. Autonomy Dials (the migration path)

Every lifecycle stage is a *role* with an independent autonomy level:

- **Level A** - human does it
- **Level B** - agent drafts, human decides (agent pre-triages with a recommendation; agent drafts the epic breakdown; human approves)
- **Level C** - agent does it, human audits by exception

**We don't automate the pipeline; we automate stages one at a time, in order of trust earned.** Expected order: implementation first (most verifiable) → discovery breakdown → triage last (spend/priority judgment stays human longest). This per-stage dial *is* the Level 2 → Level 3 path.

## 6. Architecture

### 6.1 Node topology (one machine = one node)

```
┌────────────────────────── ONE NODE (user machine) ──────────────────────────┐
│                                                                              │
│  Orchestrator window                 h9k CLI (PATH, execute-and-exit)         │
│  (interactive Claude Code            [Hall9k.Cli - Spectre.Console.Cli]      │
│   session; conversational UI) ─────► used by human, scripts, AND agents      │
│                                          │                                   │
│                                          ▼ writes commands/queries           │
│  ┌──────────────────────┐      ┌───────────────────────┐                     │
│  │ Postgres (container) │◄────►│ h9kd daemon             │                     │
│  │ Marten + Wolverine   │ bus  │ [Hall9k.Daemon]        │                     │
│  │ event streams        │      │ native host process    │                     │
│  └──────────────────────┘      │ (NOT containerized)    │                     │
│        the DB IS the bus       │ • dispatch loop        │                     │
│        (LISTEN/NOTIFY)         │ • lease mgmt           │                     │
│                                │ • run monitoring       │                     │
│                                │ • verification orch.   │                     │
│                                └───────────┬───────────┘                     │
│                                            │ spawns (detached)               │
│                                            ▼                                 │
│                      headless agents: claude -p --bare (stream-json)         │
│                      outlive any terminal; report + ask via h9k               │
└──────────────────────────────────────────────────────────────────────────────┘

External systems (reached from the node via gh CLI / provider APIs):
  GitHub - repos, PRs, issues (connector)
  Jira   - cards/epics (connector, later)

Future: many nodes, each shaped like this, coordinating P2P (§14).
```

**Why the daemon is NOT in Docker:** it must spawn `claude -p` on the host - needing the host's Claude subscription login (`~/.claude`), git/`gh` credentials, and real repo/worktree paths. Containerizing means mounting home dirs + credential and path translation pain (brutal on Windows) and likely breaks subscription auth. Postgres containerizes cleanly; the daemon runs native: launchd LaunchAgent (Mac, per-user so it sees your creds), Task Scheduler startup entry or service (Windows - decide at build time; a true Windows Service runs as a different identity by default, same credential problem), systemd user unit (Linux). *(Superseded 2026-08-19, Decisions Log #31: service registration is opt-in — `h9k install` registers nothing; the daemon lifecycle is CLI-owned via `h9k daemon start/stop`, and the per-OS agent above is what `h9k daemon autostart enable` registers.)*

**CLI ↔ daemon communication: the database IS the bus.** CLI writes commands/tasks to Postgres; daemon reacts via Postgres LISTEN/NOTIFY (Wolverine supports Postgres-backed messaging natively). No sockets, no local HTTP API.

### 6.2 Node identity, ownership & leases (the P2P down-payment)

**The accountability principle: every node belongs to a human.** Not to an agent, not to a service - a person. Whatever autonomy agents gain, a human is ultimately responsible for every run their nodes perform. The P2P future is multi-*user*: a team project splits work across developers, each developer runs their own node(s) - Brian's nodes, Sarah's nodes - like each brings their own IDE. Cross-user node communication is a later capability the groundwork must not foreclose.

Groundwork rules (paid in v0; all cheap):

- **Owner is a first-class entity**, not an assumption. A node record carries `owner_id`; an owner record exists even when there's exactly one (Brian, created at `h9kd install`). Never "the user" implied by context.
- **Every run records node + owner.** The accountability chain is queryable: this PR ← this run ← this node ← this human.
- **Globally unique IDs everywhere** (owners, nodes, ideas, tasks, runs - UUIDs/similar): records born on different machines by different people must be able to coexist in one merged/synced view without collision. No auto-increment identity anywhere in the domain.
- **No single-owner assumptions baked into streams or queries**: event streams and projections are written as if multiple owners' data could share a store, because someday it might (shared Postgres between teammates is the likely first multi-user topology).
- Task claiming is **lease-based**: claim (by node, therefore by owner) + heartbeat + timeout requeue. Works identically for 1 node or 20, one owner or a team.

That is the *entire* multi-node/multi-user tax paid now. Explicitly deferred: node discovery, gossip/replication, partition handling, and the cross-user trust/auth question (how does Brian's node verify Sarah's node?). When multi-machine arrives, evaluate "several daemons against shared/replicated Postgres" before anything exotic.

### 6.3 Executor abstraction

`IExecutor` seam in the daemon: `Spawn(taskContext) → event stream → result`. v0 implements Claude Code headless only:

- `claude -p --bare` with `--output-format stream-json`, `--allowedTools`, `--permission-mode`, budget flags.
- Spawned **detached** - agents outlive the terminal/session that requested them. Daemon records PID + session ID, monitors via the run record.
- Session IDs captured for resume (the `h9k ask`/`h9k answer` loop depends on this).
- **Do not use Claude Code subagents as workers** - they run inside a parent session, flood its context, and serialize on it. Detached processes with the DB as the coordination bus is the shape.
- **Known limitation**: fire-and-forget per invocation - no mid-run approval callbacks. When that hurts ("I want to intercept *this specific action*"), the upgrade path is a thin **TypeScript sidecar wrapping the Claude Agent SDK** (`canUseTool` callbacks, hooks) that the daemon talks to. Design the seam so this is a swap, not a rewrite.
- Reference: Agent SDK exists in **TypeScript and Python only**; the C# `Anthropic` NuGet package is the raw **Messages API client** (no agent loop) - not a substitute.

### 6.4 Billing posture (design principle: auth mode is config, not architecture)

Current state (verified Aug 2026):

- **Raw Messages API** (incl. the C# `Anthropic` NuGet): always API key, always pay-per-token. Never subscription.
- **Headless CLI (`claude -p`) and Agent SDK**: follow whatever auth Claude Code uses. Logged in on a subscription → draws from the subscription pool (same weekly limits as interactive). Setting `ANTHROPIC_API_KEY` overrides the subscription entirely → pay-as-you-go API billing.
- **The flux**: Anthropic announced (May 2026) a split moving all *programmatic* usage (`claude -p`, Agent SDK, GitHub Actions, third-party agents) to a separate monthly "agent credit" pool billed at API rates; the change was **paused before its June 15 effective date** and is not live, but Anthropic has signaled a revised version may return with advance notice.

Design consequences for Hall9k:

1. **Build headless anyway.** Interactive-terminal spawning to stay on the subscription side of the line is a trap: no `stream-json`, no clean completion signal, screen-scraping fragility - and the "interactive = subscription" line is a proxy Anthropic can (and likely will) redraw around *behavior*. Don't architect around a definition in flux; gaming it also risks violating usage-policy spirit.
2. **Auth/billing mode is per-node (or per-project) config**: `subscription` (default; daemon uses the machine's Claude login) vs. `api-key` (daemon injects `ANTHROPIC_API_KEY` into executor env). A future split becomes a config flip + budget decision, not a rearchitecture.
3. **Track cost per run from the first run**: headless JSON output includes token counts; persist per-run tokens/cost on the run record, roll up per task, per project, per billing mode. This is also what makes the "is the credit pool enough?" decision answerable if the split returns.
4. **Practical concurrency guidance**: 1–3 steady agents on a Max plan → subscription is cheapest; 5+ parallel → subscription rate limits bite fast, API key is for burst. Mixed mode (subscription primary, API key overflow) is the expected steady state.

### 6.5 Verification pipeline

Per task type, a **verification profile**:

1. Deterministic gates: build, tests, lint, typecheck, security scan - configured per project.
2. **Reviewer agent**: a fresh agent session (separate identity/persona from the implementer) critiques the diff against the acceptance criteria. Role separation is what makes the gate trustworthy.
3. Output: pass/fail + review artifact attached to the run.
4. On pass → PR opened/updated → `awaiting-review` (human checkpoint = GitHub PR review).

### 6.6 Agent identity: none. Personas: yes.

**Decision: no bot identities.** Agents act as the node owner's git/`gh` identity, and the work is *authored by the human* - agents did grunt work under the human's planning, discovery, and supervision, and accountability is the owner's (§6.2). No `hall9k-agent[bot]` PRs, no `Co-Authored-By: Claude` trailers (Claude Code adds these by default - configure them off). The audit trail lives in Hall9k, not in commit cosmetics: every PR ← run ← node ← owner.

**Personas are roles, not identities**: a reviewer persona, a discovery persona, an idea-capture persona, an implementer persona - each is a prompt template + tool policy + verification profile applied to an agent session. Role separation matters (the reviewer must not be the implementer's session, §6.5); named separate *accounts* do not.

## 7. Discovery Mechanics

Discovery is conversational and runs as **interactive Claude Code sessions** - which fits local-first natively and runs on subscription:

- **Capture**: `/idea` - the 30-second transaction. Claude asks just enough (which project, if any? attachments?), writes via `h9k idea add`, done. Ends with an optional bridge: "want to discover this now?" - so idea → discovery happens in one motion when the human is at the machine and in the mood, without making capture a commitment to think. **Capture and discovery are different speeds; keep them separate commands.** (Wispr Flow note → paste into `/idea` is the standard capture flow.)
- **Triage**: `/triage` (or "let's triage" in the orchestrator window) - reads the inbox via `h9k`, batch-recommends pursue/park/kill (flags resurfaced ideas), human decides conversationally, state updated via `h9k`. Weekly cadence, like a triage meeting.
- **Discovery**: `/discover <idea>` - interactive interview against the idea, drafts epic/task breakdown into the idea's record, iterates until human approves.
- **Publish / Adopt**: `/publish` - pushes approved breakdown to Jira/GitHub via the connector (or links to existing items), writes back external refs.

The shape - capture → triage → interview → draft → approve → publish/adopt - is stable; whether the record lives in markdown or Postgres in early versions is a build-time call (open decision #7). Slash commands are trivially editable prompts; iteration is cheap.

### 7.1 Where the discovery conversation lives

Discovery is a **phase of the idea's life, not its own aggregate**: discovery *events* (`DiscoveryStarted`, `BreakdownDrafted`, `BreakdownApproved`) go on the **Idea's event stream**. The conversation *transcript* is bulky, so it's stored like an attachment: an artifact on disk (content-addressed, §8.1), referenced from the `DiscoveryCompleted` event alongside a distilled summary (key decisions, alternatives rejected). Tasks carry an **origin link** to the idea ID; agents wanting deep context pull the transcript artifact. Streams stay lean, the origin trail stays complete. Confirm during event-stream modeling (alongside decision #9).

## 8. Ideas & Capture

What's settled:
- **Idea record**: freeform text + optional attachments/links + optional project. No required structure beyond the text. Structure is triage's job, not capture's.
- Voice: Wispr Flow handles speech-to-text; capture a note anywhere (Wispr Flow, Apple Notes, wherever), then paste it into `/idea` or `h9k idea add` at the machine. No voice feature in Hall9k itself.
- **At-the-machine capture**: `/idea` in a Claude session (§7) or `h9k idea add` directly. Both land in the inbox in `triage` state.

### 8.1 Attachments (files on disk, never in Postgres)

- `h9k idea add --attach ~/Downloads/mockup.png` - the CLI **copies** the file from wherever it lives into the node's data directory: `~/.hall9k/attachments/`, **content-addressed** (stored under the file's hash). Duplicates dedupe; references never break on rename or source deletion.
- Postgres stores metadata only: filename, hash, mime type, size, owning idea/task.
- Content-addressing also ages well for P2P: whether future nodes synchronize or shard attachments, "do you have hash abc123?" is the primitive either way.
- Discovery transcripts and run artifacts use the same store (§7.1).

### 8.2 Away-from-machine capture

Deliberately deferred - not a hard problem, just not now. Interim habit: note it anywhere (Wispr Flow, notes app), paste at the machine. Candidates when it's time: a capture inbox in a private git repo / GitHub issues that a node ingests; phone → SMS/email → a poller on the node; the far-future web portal. (Open decision #10.)

## 9. Connectors

Connectors run **on the node** (daemon/CLI reach external systems directly - `gh` CLI and/or provider REST APIs).

### 9.1 Source-of-truth split

- **External system owns**: card/issue *content* - the user-story-style task documentation (title, description, human-facing status, comments). Kept human-readable; useful to both humans and agents at that level.
- **Platform Task entity owns** (§4.1): everything operational - agent-facing context (the verbose prescriptive material that would make an issue unwieldy), orchestration state, runs and event streams, PR links, conversation thread, token/cost, budgets - keyed by external ref (`jira:PROJ-123`, `github:owner/repo#42`). **Never a duplicate copy of the card content that can drift.**

### 9.2 Adapter interface

`IWorkItemProvider`: fetch, create, transition, comment, link - implemented per provider. Must support both funnel exits: **create** (publish - new external item) and **link** (adopt - attach to an existing item, §3.1a).

**Per-project mapping config** (set at project creation):
- Jira: which issue types = epic/task; which workflow transitions map to lifecycle states. (More complex; custom types supported via mapping.)
- GitHub: labels/states mapping - but note GitHub Issues now has native **sub-issues, issue types, and milestones**, so epic→task parent/child is directly representable. Verify current capabilities when speccing the adapter.

### 9.3 v0 scope

GitHub connector (issues + PRs + repos), piggybacking `gh` CLI auth, and a Jira **read** connector on a registered API token (Decisions Log #65). The adapter interface existing from day one is what made Jira an implementation rather than a refactor, which is the claim this section made and the thing backlog 18 tested.

The two connectors are deliberately not symmetrical. Jira reads through `IWorkItemProvider` like GitHub does, and makes exactly one write of its own: a comment on the card when the pull request merges. Creating a card is not modelled at all, because issue types, required fields and routing rules are one organisation's configuration; `h9k task push-to-jira` dispatches an agent session that reads those rules from the project's own repo skills, and `h9k task link-jira` records the result only after the platform has read the card back.

## 10. Identity & Connections (local-first)

No platform login exists - you're on your own machine. Identity is simply the machine's tooling identity:

- **v0**: GitHub access piggybacks the existing `gh` CLI auth. Anthropic access piggybacks the machine's Claude login (or `ANTHROPIC_API_KEY` per §6.4). Jira is an API token, registered with `h9k connection add jira` and recorded as a credential reference rather than a secret: `env:<VARIABLE>`, `keychain:<SERVICE>` on macOS, or `file:<name>` under `~/.hall9k/credentials`, readable by the owner alone (Decisions Log #65).
- **Secrets** live in local config (`~/.hall9k/`), OS keychain where it earns its keep. No cloud vault.
- **Keep the connections principle** even locally: external-system access is modeled as a **list of connections** (`provider, external_account_id, credential ref`), and projects bind to a `connection_id` - never "the machine's GitHub" hardcoded. That preserves multiple-accounts-per-provider later and keeps the far-future portal (which would need real accounts) from forcing a data-model rewrite. It's one level of indirection, nearly free.

## 12. The Attention Surface (no web dashboard)

**Everything awaiting the human, surfaced through the CLI and the orchestrator window:**

- `h9k status` - the one-pane view: running / done / flagged (`needs-human`, `needs-refinement`, awaiting PR review), across projects.
- `h9k task show <id>` - the task detail: external ref, PR(s), run history, event timeline, token/cost vs. budget, agent context, and the conversation thread.

## 13. v0: Local Edition (build this first)

**Reality check (Aug 2026):** even local-first, the full vision is a big build. v0 scopes down to the core value proposition so value lands in weeks, not months.

**Core value proposition:** *the human stops being the message bus.* Today: 10 terminals, every question/completion/verification routed through the human's attention - context switching kills focus. v0 replaces that with **one surface**: agents run to completion or park with a question; the human engages on their own schedule.

### v0 topology

Exactly §6.1 with one node: `h9k` CLI + `h9kd` daemon + Postgres container + orchestrator window + detached headless agents. Node identity + lease-based claiming from day one (§6.2) - the only multi-node tax paid in v0.

**The interaction loop:** you talk to the orchestrator window → it runs `h9k` commands → daemon dispatches detached agents → agents work, report, and `h9k ask` questions → flagged in `h9k status` → you answer via the window (or `h9k answer` directly) → daemon resumes the agent session with the answer injected.

### Scope exclusions

No web UI/portal, no full funnel (see `--from-issue` below), no Jira, no multi-node/P2P, no away-from-machine capture.

### Build slices (each independently usable)

1. **Slice 1 - parallel fire-and-forget** (~80% of the value): `h9k task add` → queue → daemon claims (lease) → worktree → detached agent → verify (build/test/lint) → PR via `gh` → visible in `h9k status`. Window-juggling replaced by a queue. **Ship this before anything shiny.**
2. **Slice 2 - the question loop**: agent calls `h9k ask` mid-run → task parks + flags → `h9k answer` → daemon resumes the session with the answer injected. Agents stop stalling silently or guessing.
3. **Slice 3 - reviewer agent**: separate session critiques the diff against acceptance criteria before the PR opens. The trust layer begins.

Slice 1 nicety (small, high value): `h9k task add --from-issue <url>` - adopt an existing GitHub issue as a task (title/body seed the agent context; external ref linked). The funnel formalism arrives later (§3.1a); this is its v0 seed.

### v0 CLI sketch

`h9k idea add [--attach <path>]` · `h9k task add [--from-issue <url>]` · `h9k task list/show` · `h9k dispatch <task>` · `h9k status` · `h9k ask` / `h9k answer` (agents call `ask` too) · `h9k logs <task>` · `h9k watch [--notify]` · `h9kd install/uninstall/run`

### What carries forward

Task entity + event streams (Marten), `IExecutor`, worktree/dispatch/lease logic, verification profiles, the CLI, cost tracking, node identity. Later versions grow *around* this core (funnel, Jira, multi-node) - the core does not get rewritten.

### Distribution ladder (decided; build only tier 1 now)

1. **v0 (audience: me):** clone + build. `docker compose up -d` (Postgres) → `dotnet tool install -g h9k --add-source ./artifacts` (PATH handled) → `h9kd install`. The dev loop is the install.
2. **Interim (audience: developers) - likely permanent:** GitHub Releases via one Actions workflow on version tag: self-contained per-OS binaries (no .NET required on user machines) + optional nupkg (for SDK users) + `install.sh`/`install.ps1` (curl-based - CLI downloads skip Mac Gatekeeper quarantine and Windows SmartScreen entirely; publish checksums). No Apple Developer Program needed at this tier.
3. **Optional someday:** Homebrew/winget wrappers pointing at the same release artifacts; Apple signing/notarization ($99/yr) only if browser-downloaded distribution to a general audience ever matters.

### v0 discipline rules

- The grand vision will whisper "just add a dashboard." Slice 1 first. Always.
- Steal ideas shamelessly from adjacent tools (Baton desktop app, mraza007/baton, OpenClaw). **Where the novelty lives, honestly:** the v0 core (local agent orchestration) is a crowded space and *should* be boring - that's what makes it buildable. What's unique is the combination and trajectory: decentralized, human-owned, per-developer nodes coordinating shared-project agent work through external sources of truth, with a formal idea funnel and an accountability model on top. Protect that combination; don't chase novelty in the plumbing.
- **Dogfood from the first working slice**: the moment Slice 1 runs, every subsequent Hall9k task goes through Hall9k. Slice 2 gets built by agents dispatched via Slice 1. The tool escapes manual orchestration by orchestrating its own development - this is both the test suite and the proof of value, and it should *accelerate* the build.
- Every v0 decision gets checked against "does this block the later vision?" If no: choose the fast option.

### Exit

v0 scoping/build happens in its own Claude Code session, seeded by this document. (See kickoff prompt accompanying this plan.)

## 16. v0 Decisions Log

Decisions made during the v0 kickoff session (2026-08-16), Brian + Claude. Each was discussed individually; rationale summarized.

1. **Billing & spawn flags.** Subscription is the default billing mode; agents spawn as plain `claude -p` (no `--bare`). Verified against claude 2.1.233: `--bare` never reads OAuth/keychain — it is API-key-only, so it's used *only* when a node/project is configured for `api-key` mode. In subscription mode, agents inherit the user's full config (settings, plugins, skills, MCP servers) — this is desired (§6.6: agents act as the owner, with the owner's tools). The daemon overrides only what matters, e.g. `--settings '{"includeCoAuthoredBy": false}'` for the no-trailer rule. Caveats: interactively-authenticated MCP servers (claude.ai-connected Jira/Figma) may be silently absent headless — test before the Jira connector; tools not pre-authorized are denied headless (see #9).
2. **Agent output capture is file-based.** Each agent's stdout (stream-json) redirects to `~/.hall9k/runs/<run-id>/stream.jsonl`; the daemon *tails the file* rather than holding a pipe. Daemon restarts are a non-event (agents keep writing; the daemon reattaches). The daemon records PID + process start time (PID reuse guard). Completion signal = the stream's final `result` event, never the exit code (unrecoverable by a restarted non-parent). The file doubles as the raw transcript artifact (`h9k logs` reads it).
3. **OS scope: macOS in Slice 1; Windows immediately after, dogfooded.** Cross-platform seams (`IProcessManager`, daemon-installer interface) from the first commit; launchd implemented and tested in Slice 1. Windows (Task Scheduler *logon task*, not a Windows Service — services run as a different identity and lose the user's Claude/git/gh credentials) is among the first tasks Hall9k dispatches to itself, tested on Parallels, validated on the dedicated Windows tower. CI builds `windows-latest` from day one. Linux later.
4. **Worktree lifecycle.** One worktree per *run* (not per task) — retries/redispatches never collide: `wt-<task>-<run>/`, sibling of `dev/`. Branch per task: `task/<id>-<slug>`, created `git worktree add --no-track -b … origin/main` (never tracking origin/main upstream; `main` itself is never checked out outside `dev/`). Cleanup is state-driven: delete on done/merged; **keep on `needs-human`** (session resume requires the same cwd) **and on `failed`** (crime scene) until the task closes. Daemon serializes git ops per-repo (mutex, not retry loops) and runs `git worktree prune` at startup.
5. **Ask/answer = exit-and-resume.** The agent calls `h9k ask` and *exits* (the command's output instructs it unmissably to stop); on `h9k answer`, the daemon runs `claude -p --resume <session-id> "<answer>"` in the same worktree. Session IDs are daemon-assigned up front via `--session-id <uuid>` (no parsing from output). Rejected: blocking `h9k ask --wait` (dies on Bash tool timeout — answers take hours/days) and held-open stdin via `--input-format stream-json` (re-couples agent lifetime to a live daemon pipe). Back-and-forth discussion works two ways: discuss with the orchestrator window first, answer once (default habit); or answer-with-a-question — each exchange is a suspend/resume cycle, recorded as `QuestionAsked`/`AnswerProvided` on the stream. **Pre-Slice-2 spike:** prove `-p --resume` works headless after the original process fully exited.
6. **Transcripts are artifacts; event streams carry milestones only.** Corrects the §4.1 implication of `RunEventReceived`-per-line: a run emits thousands of stream-json lines; they stay in the run's `stream.jsonl` (content-addressed store per §8.1 later). Marten streams record lifecycle milestones (dispatched, started, asked, answered, verification, PR opened, tokens, completed). Whether Run is its own stream vs. events on the Task stream: decided during Task-aggregate modeling.
7. **Leases: generation counter (fencing token) + adopt-before-reclaim.** Each task carries an integer `lease_generation`; every claim atomically increments it; every run records the generation it was dispatched under; any state change from a stale-generation run is discarded (correctness guarantee — no timing puzzles). The lease tracks *daemon responsibility*, not agent progress (PID + stream file track that). Daemon startup order: (1) **adopt** — reattach to live recorded runs and process any completed-while-down results, same generation, nothing killed; (2) sweep expired leases → requeue; (3) claim queued work, killing any superseded prior-generation process first (kill-before-redispatch). Net effect: on one node a healthy agent is never killed by lease mechanics; kills happen only for hung/superseded runs. Never two live runs per task. Heartbeats are the daemon's job; agents know nothing about leases.
8. **DB-as-bus disciplines.** NOTIFY is a doorbell, never a payload (LISTEN/NOTIFY delivers nothing to disconnected listeners; durable truth is rows/events; the daemon also polls as a sweep — Wolverine's Postgres transport does this natively). **Thin CLI, full daemon**: `h9k` uses a lightweight Marten session / raw Npgsql + raw `NOTIFY` and exits (no Wolverine host cold-start on every invocation — `h9k` is called by agents mid-run); the daemon runs the full Critter Stack. No socket/HTTP API between CLI and daemon, deliberately: `h9k` must work while the daemon is down (durable queue semantics for free), every command lands in Postgres anyway (the DB *is* the API), reads never need the daemon, and shared-Postgres multi-node (roadmap #5) is this same pattern with more listeners. Accepted trade-off: no synchronous request/response — nothing in v0 needs it.
9. **Agent permissions: `--dangerously-skip-permissions`, per-project opt-in.** Headless agents can't answer permission prompts; denied tools cause silent workarounds or stalls. Risk contained by isolated worktrees + own-repos scope. Allowlist tuning rejected for v0 as walking-skeleton friction.
10. **Aspire: yes** (resolves open decision #4). An AppHost orchestrates Postgres + daemon for the dev loop, with the dashboard for logs/traces. Docker Compose remains for installed mode (`h9kd install` under launchd needs Postgres independent of the dev loop).
11. **Hung-agent detection.** Three per-run signals, all falling out of settled designs: process liveness (PID + start time), **stream activity** (hung = process alive + `stream.jsonl` silent past a threshold — the daemon tails these files and persists last-activity to the run record, so `h9k status` shows alive/last-activity/tokens for every live run straight from Postgres), and **budgets** (readiness-contract max time/turns/tokens; exceeding = runaway by policy). **Policy: the daemon never kills on its own judgment.** Local stall threshold ~1h of stream silence (configurable) → flag on the attention surface only; the human kills. Budget overruns auto-kill *only when the task explicitly declared limits* (budgets are opt-in contract terms); no declared budget → nothing is auto-killed. Killed/failed runs keep worktree + transcript per #4.
12. **Lease expiry is locality-aware: local = mechanical, remote = human escalation.** Local expiry is unambiguous — the daemon interrogates reality directly (adopt / requeue / kill-before-redispatch, per #7), fully automatic. Remote expiry (multi-node, roadmap #5) is inherently ambiguous (node down vs. partition vs. overloaded) and is **never auto-stolen**: silence escalates with backoff (late → silent → presumed down; default threshold ~24h), and **escalation is owner-aware**: alerts fire only on nodes belonging to the *same owner* as the silent node. A different owner's silent node is shown passively in status (visible, colored by staleness, non-alerting — Sarah's silence is Sarah's business, per §6.2); takeover remains available as a deliberate act. When alerted (or acting deliberately), the human decides whether to **take over** — an explicit command that re-establishes the lease locally (incrementing the generation) and revokes the remote claim. The fencing token is what makes unenforceable remote revocation safe: an unreachable node's agent that later finishes reports at a stale generation and is discarded — worst case is wasted tokens, never duplicate work or corrupted state. Recorded now so the lease model carries it; v0 builds only the local path.
13. **Naming: CLI is `h9k`, daemon is `h9kd`** (was `h9`/`h9d`). Applied throughout this document; the kickoff prompt retains the old names as a historical record.
14. **All domain IDs are UUIDv7** via the **UUIDNext** package: `Uuid.NewDatabaseFriendly(Database.PostgreSql)` — the same library and call used in the owner's production Marten codebase (NTS platform). Time-ordered IDs give chronological sortability and Postgres index locality; satisfies §6.2's globally-unique-IDs rule.
15. **Domain model settled** (task 2, full detail in `TASK-MODEL.md`): Task and Run as separate streams; Owner/Node/Project/Connection as minimal event-sourced aggregates; run ID minted at claim time and carried on `TaskClaimed`; state split (Task = work lifecycle, Run = execution lifecycle); no multi-stream projections; heartbeats/last-activity as mutable telemetry documents; value objects over primitives and enums (closed vocabularies as sealed records with `Unknown` sentinels; enums only for unpersisted in-process outcomes); acronyms spelled out in type/method/property names; `Guid Id` PascalCase identity; System.Text.Json only.
16. **Solution structure settled** (task 3, recorded in §11.1): six src projects + one two-tier test project; no `Hall9k.Contracts` until a real wire boundary exists; ServiceDefaults referenced by the daemon only, keeping the CLI cold-start lean.
17. **The flip is live** (2026-08-16): Slice-1 tasks S1-01 through S1-10 shipped; the flip gate passed with PR #1 (h9k --version) built by a Hall9k-dispatched agent through real build+test gates, review comments resolved via /git:resolve-copilot-reviews, merged by the owner. Dogfooding is policy: subsequent work is queued via `h9k task add`; manual coding needs a stated reason. Also decided: workflow skills become repo-resident (`.claude/skills/` committed, versioned with the code) and a follow-up-run flow will handle PR review feedback on the existing branch — both queued as the first dogfooded tasks alongside the Windows CI fix (container-dependent tests must not run on windows-latest).
18. **PR closeout is a phase, not an event** (2026-08-17): PullRequestOpened begins closeout, it does not end the platform's involvement. The platform (daemon) — not the human — watches each awaiting-review PR for Copilot review comments, failing checks, and the merge itself, dispatching follow-up runs on the existing branch to resolve feedback and appending RunCompleted on merge (the reserved event finds its meaning). Bounded retries; repeated failure parks NeedsHuman. Built in two dogfooded steps: follow-up-run mechanics (backlog 03) then the automatic monitor (backlog 04).
19. **Slice-1 gaps adopted.** Minimal **Project entity** + `h9k project add` (repo path, base branch, verify commands — the daemon must learn these from somewhere; the v0 CLI sketch lacked it). `h9k task add --file task.md` (frontmatter + body) + stdin — the readiness contract doesn't fit CLI flags. Per-node **concurrency cap**, default 3 (§6.4 guidance). Daemon **retry/backoff on Postgres connect** (launchd starts `h9kd` before Docker Desktop at boot).
20. **Follow-up runs reopen the task** (2026-08-17, backlog 03): the mechanics under decision #18 are `TaskReopened` (Done → Queued, carrying the PR branch from the completing run's record) rather than a Done → Claimed "follow-up claim" (would need a parallel dispatch path beside the loop, bypassing the capacity cap, claim race, and fencing token) or a new task (severs the PR from its task's audit trail). A reopened task flows through the unchanged sweep → claim → launch pipeline; the launcher sees `FollowUpBranch` on the task, checks out the **existing** PR branch (`CheckoutExistingAsync` — local branch preferred, fast-forwarded to origin; recreated from origin if local is gone) instead of cutting a new one, and prompts the agent to run the repo-resident resolve-copilot-reviews skill against the PR URL. Verification gates and the push reuse `RunSupervisor`/`VerificationRunner`/`PullRequestOpener`; the opener detects the task's existing PR URL, pushes in place, and appends `PullRequestUpdated` (never a second PR). Guardrails: only Done reopens, and only with a PR URL — Failed/Abandoned stay dead ends. `h9k pr resolve <task>` is the on-demand trigger; the automatic monitor (backlog 04) drives this same reopen path. Full rationale: TASK-MODEL.md §2.1.
21. **Worktrees live until the pull request completes** (2026-08-17): removing the worktree at PR-open contradicted #18 — the worktree IS the follow-up workspace for review resolution and CI fixes. Retained until the PR is merged/closed or another node takes a lease on the task; removal moves to the closeout monitor (backlog 04), with the follow-up checkout-from-branch path kept for the other-node and purged-artifact cases. Origin incident: worktrees deleted at PR-open had to be recreated by hand to resolve Copilot reviews on PRs 4 and 5.
22. **The closeout monitor drives PRs to true completion** (2026-08-17, backlog 04): a daemon background service (`PullRequestMonitor`/`CloseoutEngine`) polls each awaiting-review PR through gh on a gentle interval (DaemonOptions.PullRequestPollInterval, default 3 minutes; reviews and CI move on human timescales and GitHub has no doorbell here). **Who polls: every node watches the runs it executed** (`RunDetails.NodeId`); the task in closeout is Done and lease-free, so run provenance is the only honest owner, and it is also where the worktree lives. Observations land as run-stream events (`PullRequestMerged`, `PullRequestClosed`, `PullRequestChecksFailed`, `ReviewFeedbackReceived`, `CloseoutParked`; TASK-MODEL.md §2.2). Merge appends `RunCompleted` (the reserved event finds its meaning), removes the retained worktree (#21), and deletes the task branch everywhere it lingers: local `git branch -D` (rebase merges mean the tip is never an ancestor of main; the observed merged-PR signal is the justification; origin incident: five merged task branches accumulated locally because nothing owned this step), remote delete when the merge didn't already, and `git fetch --prune`. Failing checks (only once no check is pending) and unresolved Copilot review threads dispatch follow-up runs through the #20 reopen pipeline, with `TaskReopened.Kind` selecting the fix-the-CI or resolve-copilot-reviews prompt. **Bounded retries**: `TaskReopened.Automatic` marks monitor-driven reopens; the aggregate counts them (reset by any manual reopen) and at DaemonOptions.MaxAutomaticCloseoutRuns (default 2, per the #11 never-loop-on-judgment spirit) the monitor parks the RUN (`CloseoutParked`) rather than the task: the task stays Done so `h9k pr resolve` (which now also takes `--checks` and resets the budget) remains the human's retry lever, and merge detection keeps running for parked PRs. `h9k status` composes the phase: ClosingOut for an in-flight follow-up, ChecksFailing/ReviewPending/AwaitingReview from the current run, NeedsHuman when parked, Done only after the observed merge. A PR closed without merge fails the run honestly, removes the worktree, and keeps the branch (it still holds unmerged work; no merged-PR signal, no deletion).
23. **An errored Copilot review is review-pending, not review-clean** (2026-08-17): during a GitHub partial outage, Copilot posted a review whose only content was "Copilot encountered an error and was unable to review this pull request." An errored review produces zero review threads, indistinguishable from a clean pass by thread count alone, so the #22 monitor would have waved through the exact PR that implements it (origin incident: PR #6 nearly ate its own dogfood). The inspector now reads each reviewer's latest review alongside the threads (GraphQL `latestReviews`, per-reviewer latest, so a successful re-review supersedes an errored one structurally); a Copilot-authored latest review whose body contains "unable to review" (a deliberately conservative match on Copilot's own failure notice, never arbitrary review text) lands as `ReviewErrored` on the run stream and holds the run at ReviewPending, which the monitor now watches alongside AwaitingReview. The monitor re-requests the review through the REST review-request endpoint (requesting copilot-pull-request-reviewer[bot]; the website may be down when this matters, which was the origin incident's exact circumstance), records `ReviewRerequested`, and never re-requests the same errored review twice (the review URL is the dedup key across sweeps). Re-requests draw on the same automatic budget as follow-up dispatches: the task's CloseoutAttempts plus the watched run's ReviewRerequestCount, checked against MaxAutomaticCloseoutRuns by both paths. A reviewer that keeps erroring parks the run (`CloseoutParked`) with the errored review named in the reason, surfacing as NeedsHuman; `h9k pr resolve` remains the reset lever. A successful re-review proceeds through the normal thread-resolution flow.

24. **Every diff gets an independent review before its pull request opens** (2026-08-17): between the verification gates and PullRequestOpener, the daemon's `ReviewEngine` dispatches a review agent — a separate headless session with **fresh context**, never the session that wrote the code (a session that saw the implementation reasoning rubber-stamps; same reason human teams don't self-review) — over the run's diff against the base branch. The prompt demands verified findings only (read the surrounding code, confirm the defect, discard the unconfirmed), each with file:line, a defect statement, and a concrete failure scenario, closed by a parsed `VERDICT: merge-ready | needs-fixes` line. Needs-fixes dispatches a fix session in the same worktree with the findings as its prompt; gates re-run; a *fresh* reviewer looks again (review → fix → gates → review). **Bounded** by DaemonOptions.MaxAutomaticReviewFixRuns (default 2, the #22 budget pattern); exhaustion, a fix run disputing a finding as not-a-defect/human-territory, or a reviewer returning no parseable verdict parks the run (`ReviewParked` → NeedsHuman in `h9k status`) with the positions on disk — never a guessed resolution, never an unbounded loop on judgment (#11 spirit). Milestones land on the run stream (`ReviewDispatched`, `ReviewCompleted` with the verdict, `ReviewFixDispatched`, `ReviewFixCompleted`, `ReviewParked`; TASK-MODEL.md §3.1); the full findings text is an artifact in the run's directory (`review-<cycle>-findings.md`), per #6. Review/fix sessions record `TokensRecorded` like any session. A parked run keeps its task Claimed and its lease alive (adoption refreshes the heartbeat) — the worktree is the human's workspace. Review is pre-PR by design: it works during GitHub outages and on non-GitHub origins (origin incident, 2026-08-17, backlog 06: a GitHub outage errored Copilot's review out entirely, leaving the pipeline's only reviewer absent), and PRs arrive pre-reviewed with Copilot demoted to a second opinion. The human's unpark levers are v0-manual: fix in the worktree by hand, or `h9k task abandon`; a `h9k review resolve` retry lever mirroring `h9k pr resolve` is deliberately deferred until the park pattern proves out.

25. **Failed tasks get an explicit human-driven retry: `h9k task retry`** (2026-08-17): `TaskRetried` moves a Failed task back to Queued through the decider (Failed-only; Abandoned stays a dead end), preserving lease-generation fencing (the next claim increments as usual, per #7). Origin incident (2026-08-17): the first two automatic follow-up runs completed their work and passed the gates, then died at the daemon's plain push against their rebased branches (backlog 08); both tasks fell to Failed, which had no exit, and the completed, gated work sat stranded in the worktrees until it was force-pushed by hand. Failure of the machinery around the work must not permanently condemn the task that contains the work. Design: retry *appends*, never rewrites (the stream reads added → … → failed → retried → claimed, and `h9k task show` keeps the failure reason alongside the retry reason); it is distinct from `TaskReopened` (Done-only, PR closeout, different guards) rather than overloading one event with both meanings; and it is human-only (the closeout monitor never retries a Failed task automatically: a failure that repeats without human eyes is the never-loop-on-judgment rule, #11), so the event carries no Automatic flag and touches no budget (like `h9k pr resolve`, the human asking is the grant). The event records the failed run's branch as observed at retry time; the launcher resumes it through the existing follow-up checkout path when it survives (retained worktree first, then local or origin branch) and starts clean from the base branch when the artifacts are gone (never an error, since the retry's whole point is recovery). A required reason (defaulted honestly by the CLI when omitted) lands on the stream for the audit trail.

26. **Follow-up runs fold fixes into the owning commits, and the commit style is a preference** (2026-08-17, backlog 08): a PR branch reads as a natural progression of the whole change (the AGENTS.md authored-history rule), so the follow-up prompts now instruct the mechanics directly: map each fix to the most recent branch commit touching the same file, `git commit --fixup=<owning-commit>` (one fixup per owning commit when a fix spans owners; genuinely new scope gets a new properly-titled commit, never "review fixes"), `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash origin/<base>`, then the REQUIRED tree-identity check (`git diff <old-tip> HEAD` empty) so verification-gate results honestly describe the rebased tree. The mechanics also live in the repo-resident **absorb-review-fixes** skill, reusable by hand. The style is a `CommitStyle` value object on the project (`h9k project set --commit-style narrative|append|default`), resolved project-over-platform with `DaemonOptions.DefaultCommitStyle` as the platform default (Narrative; user-level defaults arrive with IDEA-platform-defaults); Append keeps the historic stack-on-top behavior. The daemon absorbs the rewrite it now asks for: `PullRequestOpener` pushes follow-up runs (`RunDispatched.IsFollowUp`) with `--force-with-lease`, never plain `--force`; a failed lease means the branch moved on origin and fails the run honestly (no blind retry; `h9k pr resolve` is the requeue lever). The worktree manager treats a diverged resumed branch as rewritten-on-origin and resets the follow-up worktree to the remote tip (the pull request's truth; the stale tip stays in the reflog), while a local tip strictly ahead of origin is kept, since that is unpushed work. Branch cleanup already tolerated rewrites (`-D` plus remote delete on the observed merge). Origin incidents (both 2026-08-17): PR #6's review round landed as a separate "harden closeout" commit and was rebuilt into the owning commits by hand; the first two automatic follow-up runs then rebased correctly and the daemon's plain push failed both ("failed to push some refs"), stranding completed, gated work in their worktrees.

27. **Failed is a needs-human waypoint, not a terminal state** (2026-08-18): a failed state means there is an unsolved problem, and an unsolved problem is not an ending. Terminal states say how the story ended; "ended in failure" is only true when a human walks away, which is what Abandoned already means. `TaskState.IsTerminal` is now Done and Abandoned only, and Failed has exactly three human-only exits, which `h9k task show` teaches on any failed task: **retry** (`h9k task retry`, re-run, #25), **resolve** (`h9k task resolve --reason <why> [--pr <url>]`, the new `TaskResolved` event, Failed → Done: the human's attestation that the objective was met despite the run failure, with the PR URL recording where the work landed), and **abandon** (`h9k task abandon`, walk away; previously rejected from Failed because Failed was terminal). The resolve reason is required: an attestation without a why is a guess (the AGENTS.md never-guess rule). Resolve appends, never rewrites: the stream reads added → claimed → failed → resolved, and the failure reason stays visible beside the resolution. Double-Fail stays rejected (`TaskDecider.CanFail`, which the daemon's failure recorders also use as their pre-check), and Fail from Done or Abandoned still conflicts. `h9k status` counts Failed toward "need you" and ranks it just under NeedsHuman, since it now waits on a human decision. Origin incident (2026-08-18): tasks a282deb0 and 13241bd8 sat Failed although their work merged as PRs #7 and #8. The failure was in the machinery (the push step), the objective was met, and the final state was simply wrong.

28. **The pre-PR pipeline verifies what it used to trust** (2026-08-18, backlog 14): four fixes from one origin story — the first fully-automated cycle, tasks 08 and 09, where the review loop, closeout monitor, and retry lever all worked as designed and everything around agent output shape and lease lifetime did not. (a) **A parked run structurally holds its task.** #24's claim that "a parked run keeps its task Claimed and its lease alive (adoption refreshes the heartbeat)" was false in practice — it held only while the heartbeat service was actually ticking, and heartbeat decay (a stopped daemon, a laptop asleep past the 60-second timeout, a wake-up sweep racing the first heartbeat tick) requeued a review-parked task; the platform then rebuilt the same feature from scratch across generations 2-4, roughly tripling the token cost, before gen 5 completed. The correction: the expiry sweep now checks the expired task's current run and, when it is ReviewParked (or CloseoutParked — the guarantee belongs to "parked", not one flavor), refreshes the lease instead of requeueing. A parked lease can no longer expire into a requeue, on any node, no matter how long the daemon slept. (b) **A verdict-less reviewer gets ONE same-session re-prompt, then parks.** The first live review ended with "I'll deliver findings and the verdict when it completes" — a promise, not a verdict — and parked a finished, correct implementation. The review prompt now forbids ending without the VERDICT line (wait for running checks, then conclude), and the engine resumes a verdict-less session once (`claude -p --resume`, the #5 pattern — the session already read the diff; a fresh one would re-spend that work) with `ReviewVerdictReprompted` on the stream; a second verdict-less ending parks (never loop on judgment, #11). (c) **`h9k review resolve` is the unpark lever** #24 deliberately deferred, now proven needed (its absence left a parked run no path forward except abandonment): `--merge-ready` sends the run on to PullRequestOpener, `--needs-fixes <reason>` dispatches a fix session with the reason as its findings; `ReviewParkResolved` records the human verdict on the run stream, and like `h9k pr resolve` it restores the automatic fix budget — the human asking is a fresh grant (#22). The daemon's dispatch cycle resumes resolved runs (adoption's mid-loop counterpart). (d) **Zero commits fails fast.** Task 08's agent completed all its work uncommitted; gates passed vacuously on the unmodified tree and the failure surfaced two stages late as "No commits between main and branch" at PR creation. The verification runner now counts the branch's commits past the base before any gate runs and fails the run honestly ("agent produced no commits") — except Research tasks, whose deliverable is the transcript (the one TaskType whose legitimate output is empty); an unobservable count is never treated as zero (the gates then surface whatever is actually broken). Retry and follow-up prompts now also tell the agent the retained worktree may already carry a previous attempt's work — committed or uncommitted — to review before starting over, closing the loop that made requeue-from-scratch so expensive.

29. **System sleep is not node death** (2026-08-18): a laptop lid-close during two active runs became a generation storm. Each sleep stopped heartbeats; each wake ran the expiry sweep before the heartbeat service's first tick; the sweep saw 50-minute-stale leases and requeued both tasks while the previous agents resumed alongside their replacements. Task 13 reached five simultaneous Running generations, four agents sharing one retained worktree, before a human killed the daemon and every agent by hand; roughly three tasks' worth of tokens went to building the same two features. Four defenses, all in the dispatch path. (a) **The OS outranks the timestamp for local leases.** Before expiring a lease this node holds, the sweep asks `IProcessManager` whether the current run's recorded process is alive (pid + start time, the #2 identity discipline the adoption path already uses); a live local process means a live lease and a refreshed heartbeat, whatever the heartbeat timestamp says. Remote semantics are unchanged: pids only mean anything on the node that owns them, so a genuinely silent remote lease still expires on the timeout. (b) **Wake detection is a wall-clock comparison, no platform APIs.** The sweep records when it last ran; a gap beyond the expected cadence (PollInterval + HeartbeatInterval) means the whole daemon, heartbeat service included, was suspended (sleep, debugger pause, VM freeze all look identical), so this node's heartbeats are refreshed before expiry is evaluated. The wake-time race between sweeper and heartbeat service is closed structurally, inside the sweep itself, rather than by timing luck. (c) **Single-flight per task per node.** A claim is refused while a previous generation's agent process is still alive on this node, closing the duplicate-agent hole from the other side (a requeue that slipped through by hand or before this build). The refusal is per cycle: once the OS reports the process gone, the next claim proceeds. (d) **A merged pull request is never rebuilt.** Before spawning an agent for a task carrying a PR URL, the launcher consults the provider: already merged means the task closes out on the spot (completed with its PR, lease released, worktree and branch cleaned like any closeout) instead of redispatching. Inspection failure falls back to a normal dispatch, since the network is often still down right after a wake. Incident for (d) specifically: after PR #11 merged, the storm-killed generation 5's lease expiry requeued the task and generation 6 spawned a fresh agent to rebuild the feature already on main. This narrows but does not replace #28(a): parked runs' leases stay alive by design; this keeps RUNNING runs' leases honest across suspensions.

30. **A run's input side is three counts, and cost is observed, never derived** (2026-08-18): `TokensRecorded` read only `usage.input_tokens` from the result payload, which for a cached session is a rounding error. The event now carries `CacheReadInputTokens` and `CacheCreationInputTokens` alongside `InputTokens`, appended as defaulted parameters so streams written before they existed replay as zero rather than as a reconstruction (the never-guess rule); `RunAggregate` and `RunDetails` accumulate each count on its own line, and `TotalInputTokens` sums them where a total is what is wanted. The three stay separate rather than lumped because they price differently, so any roll-up that adds them first can never be turned back into money. `CostUsd` remains whatever `total_cost_usd` reported, recorded as observed and never recomputed from the token counts: the platform does not hold a price list, and a computed cost that drifts from the bill is worse than no cost at all. An absent field is zero, never inferred from its siblings. Origin incident (2026-08-18): `mt_doc_rundetails` showed 444,443 output tokens against 822 input tokens across 14 runs, off by about three orders of magnitude, because a resumed session reports nearly all of its input under `cache_read_input_tokens` (one real run: 118 fresh input tokens, 8,239,942 cache-read, 196,080 cache-creation). Any cost report built on those numbers would have been confidently wrong, so the `h9k stats` idea waits until the counts are trustworthy.

31. **The daemon has a CLI-owned lifecycle; autostart is a strictly opt-in extra** (2026-08-19, redesigns S1-12): nobody evaluating a local-first tool wants installation to leave a permanently resident background process behind (colleague feedback at the first demo), and the architecture had already paid for the alternative — adopt → sweep → claim at startup plus the closeout sweep mean a stopped daemon costs latency, never correctness, the same trade #29 encoded for sleep. So: **`h9k install` registers nothing** — it publishes h9k + h9kd release binaries to `~/.hall9k/bin` and retargets an existing `h9k` symlink on the PATH (or creates one), idempotently, never clobbering a real file of that name; the `~/.local/bin` fallback is vetted by the same check as every PATH directory, since it is chosen precisely when nothing on the PATH vetted it; re-running after a merge republishes and offers to restart a running daemon, which answers installed-binary staleness (origin incident: the hand-made symlink went stale the moment main advanced). **`h9k daemon start`** launches h9kd detached through a `/bin/sh` intermediary that backgrounds the process and exits at once — h9kd is reparented to launchd (pid 1) with stdin from /dev/null and stdout/stderr appended to `~/.hall9k/h9kd.log` (read only ever from its tail, and kept inside an 8 MB budget by the daemon itself: a five-minute timer copies the log aside to `h9kd.log.1` and truncates it **in place**, never renames it, because the daemon holds that file's descriptor open for its whole lifetime and a rename would send every later line into the rolled-aside generation invisibly, while an O_APPEND writer lands correctly at the start of a truncated one; `h9k daemon start` runs the same rotation before it starts anything. Origin incident (2026-08-19, pre-PR review of this task): rotation ran only on the start path, so an append-only log belonging to a daemon started once and left up for weeks grew for as long as the node lived. The daemon's console logging filters Npgsql and Marten to Warning in code, not appsettings.json — the installed daemon's working directory is never its binary directory, so a published appsettings.json is not read at all — which keeps the tail on what the daemon did rather than on SQL), the double-fork pattern with no parent-shell tie (origin incident: the hand-started daemon died three times in one day with its shell). On start the daemon runs an immediate closeout sweep alongside adoption and the lease sweep and logs one **catch-up report** line ("Catch-up complete — adopted N run(s) … observed K merge(s)"), which `h9k daemon start` tails and prints, so the on-demand cost is visible the moment it is paid. **Single instance is enforced twice**: the CLI refuses politely with the running pid, and the daemon itself holds an advisory lock file for its lifetime (pid file carries pid + start time, the #2 identity discipline) — the guard's refusal exits 0 deliberately, so a KeepAlive LaunchAgent that loses the race is never thrash-restarted by launchd. **`h9k daemon stop`** is SIGTERM-graceful (in-flight event appends finish inside the host's 30s shutdown budget; detached agents keep running for adoption, per #2/#7) and goes through `launchctl bootout` whenever launchd owns the job, so stopped always means stopped. **`h9k daemon autostart enable`** is the only path to start-at-login: it writes a per-user LaunchAgent (RunAtLoad; KeepAlive with SuccessfulExit=false, so crash-restart never resurrects a clean stop; `AbandonProcessGroup` so tearing the job down never sweeps the detached agents, which share h9kd's process group because nothing gives them one of their own and which launchd would otherwise signal along with the job, contradicting the very promise stop prints; origin incident 2026-08-19, cycle-5 pre-PR review of this task) pointing at the installed binary; `disable` fully unregisters. **The registration carries the enabling shell's environment** (`PATH` plus whichever `HALL9K_*` overrides are actually set, recorded as observed and never invented), because launchd starts a job from its own environment, whose default `PATH` is `/usr/bin:/bin:/usr/sbin:/sbin` and holds neither `claude` nor `gh`; enable also names any tool the recorded `PATH` cannot resolve. `disable` reports a daemon as stopped only when it saw the pid launchd owned for the job actually go away, since `bootout` succeeds just as happily on a loaded but idle one. Origin incident (2026-08-19, pre-PR review of this task): an autostarted daemon would have reported running and healthy while every dispatch died on sh's exit 127, and `disable` would have claimed to stop a daemon that was never alive. A crash-restart under autostart also doubles as the Postgres boot-race retry: a daemon that starts before Docker exits nonzero and launchd retries it, while an on-demand `h9k daemon start` detects the early death and says to start Postgres. `h9k status` states plainly when the daemon is not running ("tasks queue but do not dispatch") so a quiet queue is never a mystery. Windows (Task Scheduler logon task, #3) stays deferred to S1-14 behind the `IDaemonAutostart` seam. This supersedes §6.1's original "`h9kd install` self-registers the right service per OS" — registration is now consent, not a side effect.

32. **The CLI is noun-first: browse and inspect live under their nouns, shortcuts are icing** (2026-08-20, supersedes the 08-18 sketch of a top-level `h9k list`): the top-level things you manage (project, task, and later owner, connection, node) each own their verbs, which is what the tree already hinted at with `h9k project add/set` and `h9k task add/list/show`. So browsing projects is **`h9k project list`**, inspecting one is **`h9k project show <name>`**, and browsing a project's tasks is **`h9k task list --project <name>`** — there is deliberately no bare `h9k list`, because a convenience shortcut invented before the structure it abbreviates is a second, competing organization of the same commands. `h9k status` keeps its narrow job, the attention pane (what needs you, what has gone quiet, what is running, everything else a count in the header); its old flat table of every task was a browse surface that would not have survived real task volume, and browse now belongs to `h9k task list`, which is bounded newest-first with `--all`/`--limit` and a footer naming what it held back. Three rules hold this together. **One truth about state**: every browse and attention surface composes its rows through `TaskStatusComposer` (the task's work state refined by the current run's, per TASK-MODEL.md §2), so a task never reads Running on one screen and AwaitingReview on the next, and the rollup counts are the same composition. **Single-assignment attention buckets** (needs you, stalled, active, in review, queued, done, closed): a project's row on `h9k project list` sums to its task count, so nothing hides between the columns. The pull-request group is named *in review* rather than after the `AwaitingReview` state inside it, because a group name and a state name may never collide: `--state` treats hyphens and case as noise, so the group spelled awaiting-review normalized straight onto the state, and `h9k task list --state AwaitingReview` silently answered with the ChecksFailing and ReviewPending rows as well (origin incident: caught by this branch's pre-PR review, 2026-08-20, with the exact state advertised in `--help` and unreachable). Where a word does spell a state, the state wins, so an exact filter can never quietly widen. **One way to name a project**: `ProjectResolver` takes the name, an unambiguous fragment, or the id, and both failure modes teach — no match names what is registered, ambiguity names the candidates — matching `TaskIdResolver`'s manner, and the ad-hoc exact-name lookups in `task add` and `project set` now go through it. Owner, connection, and node get the same treatment (`h9k owner show`, `h9k connection list`, …) as a follow-on; they are unmanaged today only because bootstrap creates them.

33. **The model each session runs on is a platform decision, resolved and recorded** (2026-08-20, backlog 19): `ClaudeExecutor` never passed `--model`, so every agent inherited whatever the owner's personal Claude Code default happened to be, and the platform kept no record of what that was. Origin incident (2026-08-20): runs silently drifted from Fable 5 to Opus 5 1M when Brian changed his own setting, and the only way to notice was to remember having changed it. Under a subscription this is invisible until usage limits bite, because the spend is limit burn rather than a dollar line item, which is exactly why observability comes first. So: **the model is an `AgentModel` value object** (Shared/ValueObjects, §8 discipline), holding the string `claude -p --model` accepts: the tier aliases `fable`/`opus`/`sonnet`/`haiku` as named statics, any exact model id (`claude-opus-5`, `claude-opus-5[1m]`) riding through as itself. The single word `default` is the exception at every level: Claude Code reads `--model default` as "use this machine's configured default", so passing it through would spawn on the owner's personal setting and then record `default` as the model the run used, which is both the inheritance this decision closes and a provenance no session ran on; it means "no opinion here" instead, which is also how it clears an override. **Resolution is a chain, most specific wins**: task override (`h9k task add --model`, or `model:` in a task file) > per-role default (`DaemonOptions.ModelByRole`) > project default (`h9k project set --model`) > platform default (`DaemonOptions.DefaultModel`). Every level is optional and the chain **bottoms out at an explicit value**, never at inheritance; a node can therefore outrank a project, but only per role, since `ModelByRole` sits above the project default while `DefaultModel` sits below it. Considered and left as specified: putting the whole node default above the project, so that "on this node, run Fable" is one setting. Deferred rather than rejected, because the node-level knobs are not settable on an installed node yet (the known limit below), which makes this a change with no reachable behavior to justify it until IDEA-platform-defaults gives the node a config home; the executor refuses to spawn a fresh session without a usable model rather than falling back to the owner's config, and the value is vetted against a plain-identifier charset because it lands in a `/bin/sh` command line. **Roles are first-class** (`AgentRole`: Build, Review, Fix, and Refinement for the future draft-refinement runs) because they are different shapes of work: a review session reads far more than it writes and may not warrant the same tier as a fix session. **Every dispatch records what it actually ran on**: `RunDispatched`, `ReviewDispatched`, and `ReviewFixDispatched` carry the resolved model, surfaced on `RunDetails`/`RunListItem` and in `h9k task show`; with the per-run token accounting from #30 that makes spend-by-model a query instead of a guess. A **resumed** session (the one verdict re-prompt, #28b) keeps the model it started with, so `ReviewVerdictReprompted` records that model and the engine deliberately does not re-resolve, since recording a model the session never ran on would be a guess. All the model fields are appended with defaults, so streams written before this existed replay as Unknown rather than as a reconstruction (the #30 discipline). **The shipped configuration is deliberately flat**: one exact model id (`claude-opus-5[1m]`) for every role, no tiering. An exact id rather than an alias because an alias is re-pointed as new models ship, which is the same drift in slower motion; the **1M-context variant** rather than the standard-context one because that is what dispatched sessions were observed running on when this was written, so shipping `claude-opus-5` would itself have been a silent, unrecorded narrowing of every build, review, and fix session, and on an installed node (see the known limit below) there would be no node-level knob to put it back. Fable is the human-interactive tier, for the long discovery sessions the human is in, not a silent-agent default: across 71 observed sessions per-session output volume was near-identical (~30k) on both, so the difference the platform pays for is tier weight rather than session length. What this decision buys is the **knob and the record**, not an opinion about which task deserves which tier. Known limit, inherited from every other `DaemonOptions` setting rather than introduced here: an *installed* daemon reads no config file (#31: its working directory is never its binary directory), so the two node-level knobs are settable in a dev run and not yet in installed mode, until IDEA-platform-defaults gives the node a real config home. The project and task levels live in the event store and work everywhere today, and the shipped platform default is the same either way. Deliberately **out of scope**: automatic complexity-based selection, a coordinator judging "this one only needs Sonnet". That is a judgment layer, and #11's never-loop-on-judgment spirit says to wait for data: a few weeks of recorded models against recorded tokens will show whether a smaller tier holds the quality bar (the PGID catch in #31 and the seven-cycle daemon review are the bar). Captured in backlog/IDEA-coordinator-agent.md for when that data exists.

34. **Task development and task dispatch are separate lifecycles.** `h9k task add` creates a **Draft**, not a queued task: `Draft (editable) → Published (the readiness gate; immutable and assignable) → assigned → Queued or Blocked → claimed`, with two explicit reverse edges — `h9k task unassign` (assigned → Published, refused while a lease is held) and `h9k task draft` (Published → Draft, refused from Queued and Blocked onward). Each state means exactly one thing: Draft is being developed, Published is ready to assign, assigned means it should run. **Why:** the old model conflated two different jobs. Discovery produces a rough task and refines it over hours or days, while dispatch is a human deciding *this should run now, and on whose nodes* — and `TaskAdded → Queued` meant the daemon claimed a half-formed thought within seconds of it being written down. Creation now asks only for identity (project + objective); the readiness contract is enforced once, at Publish, as an invariant of that state rather than a toll booth at creation. Assignment (`TaskAssigned`) is the dispatch trigger and always an explicit human act, and the claim guard is one rule with no other path to a claim: **the task is Queued and its assigned owner is the node's owner**. That single rule is also what makes multi-owner projects safe later (IDEA-task-assignment) — arbitrary pickup becomes structurally impossible rather than policy-forbidden. Revision (`TaskRevised`) is permitted **only** in Draft, because each later state carries a promise editing would break: Published promises "a human may assign this at any moment and it satisfies the contract", assigned promises "a node may read this at any moment" (revising a claimable task races the dispatcher). The `unassign → draft → revise → publish → assign` ceremony is deliberate friction, not accidental. **Dependencies:** `BlockedBy` edges are declared at creation or revised in Draft, and a dependency counts as met only at **true closeout** — `RunCompleted`, which the closeout monitor appends when it observes the merge (#18/#22). Nothing weaker: a Done task whose pull request is still open still blocks. Cycle detection lives at Publish alone (a draft may transiently reference a cycle while a graph is authored; a cycle can never become assignable), and the refusal names the cycle hop by hop. A blocker that can no longer reach true closeout leaves its dependents **Blocked with the reason recorded**, reading as NeedsHuman in `h9k status` — the same shape #22's closeout park uses, and for the same reason: silently unblocking would dispatch work whose premise died, and silence would strand it. "Can no longer" is wider than "failed": a task that ends Failed or Abandoned, *and* a task that reads Done on a run that already ended without a merge — `h9k task resolve`'s attestation exit from Failed (#27), a pull request closed unmerged, a killed or superseded run, or a Done task with no run at all. Every one of those is a door out of the closeout pipeline, and a dependent behind any of them waits forever unless it is told. Origin incident (2026-08-20): the first cut enumerated Failed and Abandoned only, so a resolved dependency stranded its dependents silently — Blocked, no reason, not reading as NeedsHuman. Unblocking is driven from the closeout monitor's `RunCompleted` append, so whichever node observed the merge unblocks the dependents and rings the doorbell; the dispatch loop re-evaluates every Blocked task each cycle as the safety net (NOTIFY is a doorbell, polling is what makes it correct — #8). Dispatch order inside the ready set is untouched: FIFO by `AddedAt` among Queued tasks; dependencies and assignment shape the ready set, not its ordering. **Single-owner convenience:** `h9k task publish --assign` (and, in an interactive terminal, a prompt) may assign in the same breath when the platform has exactly one owner — the same explicit `TaskAssigned` event, never a silent one, and never offered when more than one owner exists. **Migration:** `TaskAdded` gained `BlockedBy` and `StartsAsDraft`, both defaulted to the pre-split meaning, so a stream written before this decision replays exactly as it behaved — queued on arrival and assigned to the owner who added it, who is the sole owner of a v0 install (an observed fact, not a guess at provenance). The projections are Inline, though, so a stream that stopped receiving events before the split keeps the document shape it was last written with — and the claim filter reads a document with no `assignedOwnerId` key as nobody's work, which would make every pre-split task permanently unclaimable. So the daemon rebuilds those documents from their events at startup (`TaskLifecycleProjectionBackfill`), keyed on the absent key, idempotent and self-terminating: no marker document, no separate migration tool, and no guess — the events already record whose work it is. Origin incident (2026-08-20): the split first shipped the new filter without the rebuild, and all 24 tasks in the dogfooding database went silently unclaimable, which looks exactly like an idle queue. **Does this block the later vision?** No — it is the mechanism the later vision needs. Multi-owner assignment (IDEA-task-assignment), assigning a whole published graph at once, and refinement runs that develop a draft (IDEA-draft-refinement-runs) all attach to these states. Deliberately out of scope here and fast-following: task attachments (IDEA-task-attachments), which handle the context gathered *around* a task rather than the task's own text.
35. **The idea is a first-class concept, and discovery is its own phase.** An idea is a thought captured before it is anything else: `h9k idea add "<text>"` is one command with one argument, and `--project` is the only option because an idea may precede its project, or become one. Ideas get their own small stream (`IdeaCaptured`, `IdeaRevised`, `IdeaAssignedToProject`, `IdeaPromoted`, `IdeaDiscarded`) in a flat tiny-slice folder, owner-scoped from the first keystroke. **The vocabulary is deliberate and used everywhere:** an idea undergoes **DISCOVERY**, which asks *what is this?*; a draft task undergoes **REFINEMENT**, which asks *how does this become executable?* The two feel similar in activity (reading, digging, drafting) and differ entirely in question, so the platform names them apart in help text, in refusals, and here. **A task is an idea with intent**, which is exactly what promotion records. **Why:** #34 split task development from task dispatch and left the front of the funnel undone; a half-formed thought was being written as a Draft because a draft was the smallest thing that existed, which put a project and an outcome-phrased objective in front of a thirty-second capture. Anything required beyond the text defeats capture, so nothing is. **The discovery workspace is a directory, not an event payload:** every idea owns `~/.hall9k/ideas/<idea-id>/workspace`, created at capture and revealed by `h9k idea show` (which counts what is in it when someone looks, since a human fills it by hand). The path is derived from the id exactly as a run's directory is, so the stream never records a fact it can recompute, and it records milestones only, never file contents (the transcripts-on-disk discipline, #2). Per-file provenance belongs to the attachments feature (IDEA-task-attachments) and can generalize to ideas later; the workspace pointer is the honest v1. **Promotion composes with the existing lifecycle rather than duplicating it:** `h9k idea promote <id> [--project <name>]` produces an ordinary Draft that enters the ordinary draft ceremony (revise, publish, assign). The seed is mechanical and visible: the note's first sentence becomes the objective and the remainder becomes agent context, with the workspace path appended so the research that produced the task is reachable from it. First-sentence extraction is a scan for a terminator followed by whitespace, or a line break, whichever lands first, and the command prints exactly what it took; `--objective` overrides it, in which case nothing is consumed and the whole note rides along as context. The platform never infers what an idea was really about (the never-guess rule). **Provenance runs both ways:** `IdeaPromoted` names the task, and `TaskAdded` gained a defaulted `SourceIdeaId` naming the idea, appended with a default so streams written before ideas existed replay as "written directly" rather than as a reconstruction (the #30/#34 discipline); `h9k task show` prints it. Promotion requires a project because a task belongs to one, supplied at promotion or already assigned. **Promotion to a PROJECT is deliberately deferred, with a teaching refusal rather than a silent gap:** project registration needs a repository path, a base branch, and a connection binding, and an idea has none of them, so `h9k idea promote` with no project says so and points at `h9k project add --name <name> --repo <path>` followed by promoting into it. Inventing a repository path would be precisely the guess the audit rules forbid, and the two-step path costs one command. **Discarding is honest, never destructive:** `h9k idea discard <id> --reason` requires the reason (an idea dropped without a why throws away the signal that a recurring idea is trying to send, PLAN.md §3.1's parking garage) and keeps the note, its history, and its workspace. A promoted idea refuses revision and discard, naming the task that carries the story instead. **Reads:** one projection (`IdeaDetails`) serves both `h9k idea list` and `h9k idea show`, since ideas are few and small; the list shows what is still in discovery by default and counts what the filter hides, and its footer teaches promotion, which is what the list exists to lead to. **Does this block the later vision?** No: this is the front of the funnel §3.1 always described. Triage and resurfacing counts attach to this stream, dispatching agents to work ON an idea during discovery is the refinement-runs idea generalized (IDEA-draft-refinement-runs), and away-from-machine capture stays open question #10 (P2P/multi-node territory, not a CLI question). **Origin:** the backlog's own `IDEA-*.md` files, which had been a naming convention doing the work of a missing concept.

> P2P placement note: #38-#58 are post-v0 decisions from the P2P design sessions (2026-08-18/19), recorded in the v0 log per the #12 precedent - foundations carry them, built at roadmap #5. They were drafted as #25-#45 against a pre-fork PLAN and renumbered +13 on merge (2026-08-20); HALL9K-P2P-DESIGN.md is the consolidated design they cite.

38. **P2P identity is a two-tier key hierarchy; the peering unit is the project** (2026-08-18, design session; full detail in HALL9K-HALL9K-P2P-DESIGN.md §2–§4). **One owner keypair per human** (root of trust, stays cold on the primary machine, signs node certificates and nothing else) and **one node keypair per machine** (generated locally, never leaves, signs every event). The owner key signs each node's public key; a peer verifies two links — event signed by node key N, node key N certified by owner key O — and knows it is Brian's work from Brian's laptop. Per-node revocation is therefore free (lose a laptop, revoke that certificate; the owner identity survives). Keys are **self-sovereign**, generated at `h9k owner init`: no OAuth, works offline, trust root stays owned; a signed GitHub-username attestation is purely additive later. **Rejected: a keypair per project** — it buys unlinkability, the exact opposite of the accountability model (§6.2), and multiplies key management for nothing. **The peering unit is the project, not the node**: a node hosts many projects and authenticates as one owner; an owner may run several nodes; a project may span many owners or one; and **some projects are personal, so peers must never learn they exist** — which forbids wholesale node-to-node peering and puts membership in the project, opt-in per project, with the node as merely a host. **Enrolment** resolves how the owner key signs a remote machine's key without traveling: a short-lived (~1h) token exported from an existing node, carried to the new machine, fed to `h9k init`, carrying node A's addresses, public key, and a shared secret — a one-time ceremony, not a key copy. Its limit is what makes discovery mandatory rather than optional: human-mediated enrolment scales to your own machines and no further, and a token's baked-in addresses go stale on any network change. **Trust and reachability are separate problems** and are solved separately (#39, #40).

39. **Metadata gossips eagerly; payloads materialise lazily on claim; claims belong to the owner** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §10–§11). All nodes stay synchronised on **which projects and tasks exist**; discovery artifacts, transcripts, and attachments are **not replicated by default** — claiming a task pulls its content from a peer that has it. This is why §8.1 chose content addressing: the claimer already knows the hashes it needs, and "do you have hash abc123?" is the right primitive either way. **Claiming while the source node is offline holds the claim and syncs when the source returns** — the claim lives in the event log regardless; the payload is only a cache to warm. Implies an *awaiting materialisation* state so an agent is never dispatched into a half-empty working directory (surfacing is open, §15 #12). **Claims are recorded against the OWNER, not the node**: Sarah needs to know *Brian* holds task ABC, not which machine — the node key signs the event (who typed this), the payload records the claiming owner, and a peer resolves node → owner to reject a duplicate claim from the same owner's second machine. `TaskClaimed(Id, NodeId, OwnerId, LeaseGeneration, RunId, ClaimedAt)` already carries exactly this shape; no change needed. Remote lease expiry is unchanged by any of this (#12).

40. **Discovery: one Hall9k-wide network and an announce/expire seed, never a registry** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §5–§7). **All nodes join one shared address book regardless of project**, inverting the obvious per-project-rendezvous design: finding a project's peers becomes a *query over connections you already have*, not a criterion for finding peers at all. No per-project setup, strangers work fine, and **the seed never learns which projects exist** — it sees only addresses; membership is proven peer-to-peer with keys. Bootstrap needs something out-of-band, so the binary ships **a hardcoded URL, not an IP** (a URL lets the service move hosts or repoint DNS without a release). The endpoint **announces and queries in one call**: a node POSTs who and where it is, the response is the current list of other announcers; every querying node also populates the table; no curation. **The recorded address is the one the service observes the connection arriving from**, never what the node claims — that is the post-NAT address and port that actually works. **The seed never initiates anything**: nodes re-announce on a ~15-minute heartbeat and entries expire after ~1h of silence. *Rejected: probing nodes for liveness* — it hits every NAT problem the peers have and turns a dumb table into a monitoring service holding state; liveness is the node's job to assert, not the service's to verify. The table is deliberately churning and never complete, just currently-warm. **It is a seed, not a dependency**: nodes cache the address book on disk and use peer exchange thereafter, falling back to the seed only when everything they know is stale — **if the hosting bill lapses, existing networks keep running**. Storage is **in-memory, deliberately** (a few hundred hourly-expiring entries is a cache, not a record; loss on restart refills itself within 15 minutes). **Peer exchange** caps active connections at ~8–10 while the on-disk address book grows well beyond that, and deliberately **diversifies which peer each address came from** — Bitcoin's network-group bucketing as an anti-eclipse measure, and note Bitcoin has *no* locality preference and actively resists one. **Finding a project** is a bounded gossip query over established connections — hop-capped, deduplicated by query ID — and silence is a real answer (nobody reachable has it; retry on the heartbeat). **Rejected**: BitTorrent mainline DHT (throttled or blocked on corporate networks by DPI on its handshake signature, breaking peering exactly where it is needed — the useful inverse lesson being that Hall9k's own protocol is unrecognisable and TLS/443 looks like ordinary HTTPS); git-remote rendezvous (imposes repo overhead on every project owner, and publishes home IPs); Bitcoin's crawler model (works only because Bitcoin nodes are expected to be publicly reachable — developer machines are not). Far-future scale is shape-compatible without protocol change: announce **when lonely rather than on a timer**, with a reachable opted-in minority still announcing, tuned by a "check back in N" field in the announce response.

41. **Reachability: LAN first, hole punching second, relay on 443 as fallback** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §8–§9). Try in order of cost and **cache per peer what actually worked**. (1) **Same LAN — mDNS multicast**, no external service, works with no internet uplink at all; full LAN speed makes materialising a large attachment set instant, and the trust check is trivial when both certificates chain to the same owner key. Also what makes the #38 enrolment ceremony pleasant. (2) **Hole punching**: outbound traffic creates a router mapping that briefly admits replies; both nodes learn each other's *observed* external address from the seed, the seed nudges both, and they fire UDP simultaneously — the first packet is dropped (the other side hasn't sent yet, expected), the second arrives at a router that recognises the address it just sent to and lets it through. **QUIC over the punched path** (TLS, streams, reliability for free), keys verified against the project member list, keepalive every 20–30s to hold the mapping; the seed never touches the data. Gets an estimated 70–80% of NAT pairs. (3) **Relay** for the rest. Punching fails on symmetric NAT, blocked outbound UDP (common on corporate/guest networks), and carrier-grade NAT; **the failure is asymmetric** — if the far side's firewall blocks outbound UDP its packet never leaves, so no mapping forms and your correctly-sent packet has nothing to slip through, *your side having done everything right*. You cannot know which case you are in until you try: **attempt the punch, allow 2–3 seconds, fall back quietly** — the user never learns which path was used, they just see the transcript arrive. The relay is a server on a public 443 that both nodes dial **outbound** (universally allowed), which pairs their sockets and pumps bytes both ways **for the entire session** — it is a permanent middleman, explicitly *not* an introducer that steps aside (that is the seed, which is genuinely DNS-shaped). All connections landing on 443 is unremarkable: a port is a doorway, not a channel, and each connection has its own socket. No keepalives needed (real established TCP, no NAT mapping to hold). The relay is dumb by construction — no protocol parsing, no storage — and payloads are encrypted end-to-end between node keys, so it sees ciphertext only. Transports: direct/QUIC when punched, websocket-over-TLS when relayed (HTTP only for the upgrade), same application protocol on top. **Rejected: SignalR for the relay leg** — the hub/RPC model is dead weight for an opaque byte pump, it couples the wire format to a framework, and this is the *exception* path; raw websockets in ASP.NET Core is ~30 lines. (SignalR was stripped during the local-first pivot on the assumption no relay would be needed; a relay proving necessary does not bring it back.) **Rejected: Tor as the node transport** — it would solve reachability outright (onion service per node, dial-out only, stable address behind any NAT, no punching, no churn) but costs 1–2s per round trip, poor payload throughput, and is blocked on many corporate networks by policy; building censorship circumvention into a developer tool is the wrong place to end up. Viable later as a personal-machine fallback. **Hosting**: seed and relay share a codebase (ASP.NET Core minimal APIs, likely Azure Container Apps) but get **separate deployments or at minimum separate scaling rules** — the seed is tiny, bursty, request-response, scales to zero happily, and must pin to one replica (divergent tables otherwise); the relay holds long-lived bandwidth-hungry connections, scales on concurrent connections, and **must not scale to zero** (it would kill live tunnels). If the relay is hammered, discovery must not go down with it.

42. **The owner private key is recoverable by succession, not by backup** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §4.1–§4.6). Follows from noticing how little the owner key does: **it signs node public keys and nothing else** — not events, not project joins, not handshakes. So **every node holds the owner *public* key and any node can join a project on the owner's behalf**; the primary is special for exactly one operation, enrolling a machine. Therefore **losing the owner private key is inconvenient, not fatal**: every node keeps claiming, syncing and signing indefinitely, and the only broken capability is enrolling a *new* machine. **Decision: at enrolment, each node generates its own owner keypair and the primary signs a succession statement ("owner key A also controls owner key B")**, stored on the enrolling node and carried in project state — enrol five machines, get five vouched-for heirs, at the cost of one extra signature in a ceremony that happens a handful of times per lifetime. Recovery is "promote a node you still have": no password manager, no paper. **Promotion is deliberate, never automatic** — since nothing is broken there is no failover to detect, hence **no health checks, elections, quorum, or split-brain machinery**. It discovers itself at the right moment: `h9k node invite` on a secondary finds no reachable node holding the owner key, says so plainly, and prompts (*this node can be promoted — proceed?*); on yes it presents its succession statement, announces, mints the token, and the remaining nodes re-enrol against it as ordinary onboarding. The prompt is required — promotion changes the identity root network-wide and must not be a side effect of wanting a new laptop. **Ordering is oldest reachable node**: it needs no extra state and enrolment dates are already signed by the primary, so the order is *verifiable rather than declared*; skip down when the oldest is offline, and the promoted node announces so others stand down. **Floor if there is no chain and no surviving node**: a project member re-invites you with an ordinary project token — one Slack message — at the honest cost that prior work is attributed to an owner key nobody vouches for anymore (history intact, authorship orphaned), which is precisely the argument for minting succession statements by default. **Rejected: copying the owner private key to every node** — every copy is another leak surface, a leaked owner key certifies nodes as you forever (a leaked token dies in an hour), and it collapses per-node revocation since a laptop holding the owner key *is* you. **Rejected: threshold signatures (2-of-3)** — the right instinct and it does solve the failure directly, but it is real cryptographic engineering with thin .NET library support, and it requires two machines online simultaneously to enrol, trading a rare inconvenience for a routine one; disproportionate for a key that signs perhaps five things in its life. **Rejected as the sole answer: manual key backup** — remains possible and is proportionate for a solo project with nobody to vouch for you, but as *the* design it pushes ceremony onto every user; Hall9k manages code, not money.

43. **Two token types; certificates travel with stored events only; pre-P2P history needs a one-off migration** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §4.2, §4.7–§4.8, §10 amendment). **Node enrolment tokens and project invite tokens are distinct types on the wire.** Enrolment requires the owner private key and causes it to sign a node public key, granting scope over every project the owner belongs to; a project invite requires no owner key, can be minted by any member's node, and merely adds an owner public key to one project's member list. Keeping them separate prevents a project token silently becoming "act as me everywhere." Both are single-use, ~1h TTL, proven by HMAC over the joiner's public key keyed by the token secret. **An inviter need not know the invitee's owner public key beforehand, or that it is Brian at all** — it arrives inside the join request wrapped in the token proof; the token bootstraps exactly one fact, that this owner public key belongs to the person meant to be invited. **Certificates travel with anything that will be repeated by someone else**: transient messages (queries, heartbeats, project questions) carry a signature only, since identity was settled in the handshake and the message dies at the receiver; **stored events carry signature *and* certificate in their persisted form**, because a third peer that never handshook with the originating node must verify independently rather than take the relaying peer's word. **Not built now** — dead weight in every aggregate today; what matters is not foreclosing a signed envelope *around* an event rather than assuming an event is only ever what the local node wrote. **Pre-P2P events are unsigned and this does bite**: history propagates, so a back catalogue synced to a peer gets relayed onward to nodes that will reasonably ask who signed it. A one-off migration at switch-on — retroactive signing (attesting now to what you wrote then) or a hash-chain checkpoint signing the tip once (Bitcoin's block chaining in miniature) — is owed then, not now. **Same-owner sync relaxes #39's lazy-payload rule**: eager metadata / lazy payloads was reasoned about with cross-owner peers in mind, but between two machines of the same owner on a fast link, pulling attachments is essentially free and the laptop is worth having as a genuine mirror rather than a thin index — **same owner on a fast link pulls everything; anything else waits for a claim**, and a newly enrolled node **syncs all of that owner's projects by default** (the certificate is owner-scoped, so which projects sync is a preference, not a trust question).

44. **Competing promotions reconcile after the fact; duplicated work arbitrates through GitHub** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §4.9). Closes §15 row 16. **The common case is not a race**: a sleeping primary wakes, hears a promotion announcement it can verify *because it signed the succession statement itself*, and steps down to ordinary node. **Promotion events form a chain**, each naming the key it supersedes, so a node offline across several promotions replays them in order — step-down logic handles a chain, not a single hop. **The hard case is a partition, and a quorum rule does not prevent it**: when a location loses its uplink its *local* network stays healthy, a quorum of the owner's nodes is available, is consulted, and agrees, because from inside a partition both halves look correct. **Rejected: detecting the condition** ("don't promote while offline") — that requires knowing your view is incomplete, which is a liveness oracle and does not exist; an uplink is only one of many reasons two locations stop seeing each other, none reliably distinguishable from a dead primary. **Decision: reconcile by lowest hash of the promotion event.** Both sides compute both hashes from immutable data, agree with no negotiation and **no trusted clock** — wall-clock time being precisely what a partition makes unreliable. This is CAN-bus arbitration (the same trick offered for the claim-race tiebreak, §15 row 13): arbitrary but deterministic priority that losers detect for themselves. Hash rather than raw node ID because it is unpredictable and so ungameable; costs nothing. **Aftermath**: the loser's certified nodes re-enrol under the winner (new certificates, nothing lost), and **a certificate is valid for what it signed while it was valid** — events already signed under the losing key stay verifiable forever, since rejecting them discards legitimate work and voiding the key retroactively would misstate what happened; therefore **the losing promotion event is retained as evidence, not deleted**. **This is not a chain split**: blockchain reorgs erase one history because the two *compete* (same coins, contradictory spends), whereas two machines certifying two laptops doing unrelated work are not in conflict at all — both histories merge, nothing is orphaned. **The one genuine conflict is the same task claimed twice**, which is a claim-race problem at a different layer and needs solving regardless. **GitHub arbitrates**: a branch or PR is a fact both sides can check and creating one is atomic, so whoever's push landed wins — the external-source-of-truth decision paying off rather than new machinery. Two residual shapes: both pushed (two PRs on one task; a human picks — wasteful, not incorrect) and **a task that never reaches a PR** (spike, investigation, discovery), where nothing arbitrates. For that, **the system flags and does not resolve** — on heal, surface the duplicate claim as needing attention; do not pick, merge, or discard, because two conclusions to the same question are two opinions and only a human can say whether they agree, complement, or one is better (plausibly via a Claude Code session reading both and reporting divergence, the same shape as the pre-PR review loop). **Net: the claim race is a cost problem, not a correctness one.** The inverse case — zero promotable nodes — is already covered by the re-invite floor (#42).

45. **Sync shape confirmed, and repositories materialise lazily** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §10 amendment). **Event log eagerly, everywhere** — projects, tasks, claims, runs, discovery metadata; Postgres rows, megabytes not gigabytes, so syncing every project of an owner by default is cheap. **File payloads lazily** (#39 unchanged). **Git repositories clone lazily**, triggered by the same claim. **Gap this exposes**: `h9k` assumes the repository is already present because you are standing in it, but cross-node claiming means a machine can hold the complete event log for a project it has never cloned. So a **materialisation step sits ahead of work-tree creation** — do I have this repo? no → clone from the project's GitHub connection → create the work tree as normal. Same lazy-materialisation shape as attachments, with git doing the fetching. `init` is never lazy and never needs to be: when a project is created the repository already exists locally, so **only cloning is ever lazy**.

46. **Losing runs are attached, not merged, and an agent triages them** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §4.10). Closes §15 row 19. **First, a framing correction**: there is no "primary" in the user's world — nobody walks up to a machine caring what kind of node it is, they walk up and start working. "Primary" names exactly one capability (holding the owner private key) exercised the handful of times a machine is enrolled. So **the key reconciliation of #44 is silent plumbing**: a losing node finds out at the one moment it matters, when `h9k node invite` fails and offers the other machine or promotion. **The reconciliation that ever speaks is the one about work**, and it must surface per-node, where the human is standing. **Losing runs are attached, not merged**: a task has one identity and two runs against it, both stored as they arrived, each keeping its own identity — no replaying, no interleaving, nothing rewritten or discarded. This works because **ordering across nodes was never a single true sequence**; each run is internally ordered, the runs are concurrent, physical log order is arrival order and an implementation detail, and distinct stream IDs mean there is no collision to resolve. The partial order is admitted rather than flattened. **Consequence: the storage layer needs no partition-specific machinery at all** — the only place the ambiguity was ever real is the *lease*, which is exactly what the #44 hash tiebreak settles. **The tiebreak decides who had authority; the events record what happened either way.** Nothing combines at the data level; what combines is the *conclusion*, and that is a **third artifact** — an appended interpretation, never an edit to history. **The winner proceeds normally** (its branch is the branch, its PR is the PR) and **the losing run is flagged as unreviewed, non-blocking** — optional curiosity if the winner already merged, potentially better work if the task is still open, since shipping the winner purely because its push landed first is arbitrary. **Nothing is deleted**: the work, transcript and diff stay; a losing run is a second attempt someone might want to read, not a duplicate to clean up. **An agent triages**, and this is Hall9k reconciling itself: a losing claim **materialises a review task** carrying both attempts as payload, an agent picks it up through the ordinary queue and reports where they diverge. Most of the time they converged — two agents on the same task and codebase reach near-identical results, differing in nuance not outcome — so the agent says so, the winner stands, and no human reads two transcripts to learn nothing; **absorbing that common case is most of the value**. **Escalate only genuine divergence**, which is rare enough to be cheap. **The agent recommends; it does not decide** — discarding your own work wants a human nod and asking costs nothing, which keeps this at the edge of supervised autonomy rather than past it. Same shape as the pre-PR independent review loop (#20–#24): an agent reading work it did not do and reporting rather than acting.

47. **QUIC everywhere, no HTTP anywhere in the P2P layer** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §1). **All peer traffic is QUIC over UDP via `System.Net.Quic`** — in-box .NET on top of MsQuic, no third-party package. We *use* QUIC and do not implement it: packet layout, encryption, handshake, retransmission, congestion control and stream multiplexing belong to the library; the only thing Hall9k writes is the framing inside the streams (#49). Two layers that had been conflated and now are not: **QUIC/TLS provides a private authenticated pipe; the Hall9k protocol decides what the two nodes say over it.** **Why not TCP+TLS**: TCP's single global order means one lost packet stalls everything behind it, whereas QUIC's independent streams let a large back-catalogue sync run alongside a live push; TCP+TLS 1.2 costs three round trips before a useful byte moves, QUIC merges the transport and crypto handshakes into **one**, which also means **certificate exchange happens as part of connecting rather than as a protocol message we design**; a QUIC connection is identified by connection ID rather than the IP/port four-tuple, so **connection migration** carries a sync across a network change with **no resume logic to write**; and QUIC's logic ships in userspace with the next deployment rather than waiting a decade for kernels (UDP itself is still kernel — "userspace" here means privilege level, not a user account). **And UDP is what makes hole punching possible at all**: a router notes outbound traffic and thereafter admits replies, and *that note is the hole* — UDP's statelessness, normally a weakness, means the router does not care whether the packet ever arrived. TCP insists on a SYN handshake in strict order, so simultaneous dials drop both SYNs. TCP's only alternatives are relay (both parties dial *out*; the relay never dials either), manual port forwarding, or UPnP — and a UPnP-opened port is open to *anyone*, which is why routers ship it disabled, with carrier-grade NAT defeating it regardless: **worth trying as an optimisation, never worth depending on**. **Therefore no ASP.NET Core**: the seed listens on a UDP socket, there is no URL, route table, middleware or controller, and the only reason to want ASP.NET Core would be a browser, of which there is none. **The handshake is four steps and one round trip**, and Hall9k writes code for exactly one of them: the Initial packet carries an invented connection ID, the version, an **ephemeral** public value and cipher suite list, padded to ~1200 bytes to prevent amplification, with the payload encrypted under keys derived from the connection ID (format consistency, not secrecy) and **no certificate or identity in it at all**; the reply adds her connection ID, her ephemeral value, the chosen suite, her node certificate and a signature over the handshake so far; **step three is our hook** — the library verifies cryptographically and then asks *do you accept this?*, and our answer is *does this chain to an owner key I recognise as a member of a project I care about?*, with rejection closing the connection silently; step four confirms. **This is a TLS channel and mutual identity verification in a single round trip.** Standard TLS lets the client stay anonymous (that is web browsing); Hall9k configures QUIC to **require a client certificate**, a setting rather than a message. 0-RTT reconnection exists and is attractive later. **Two keypairs, two jobs, and nothing is encrypted with either private key**: the **ephemeral** keypair (X25519, microseconds, generated per connection and discarded) does **key agreement**, and the **node** keypair does **signing**. Key agreement means each side sends only a public value, then combines *its own private half with the other's public half*, and the mathematics yields **the same number on both sides without anything secret crossing the wire**; discarding the ephemeral keypair gives **forward secrecy**, so recorded traffic stays unreadable even if a node key leaks years later. Signing is the opposite in intent — hash, transform with the private key, and the output is **public evidence anyone can verify** — and **verification does not recompute the signature** (it cannot, that would need the private key): signature, hash and public key go into a verify function that answers yes or no. Underneath: the keys are two halves of one relationship, built on an operation easy forwards and effectively impossible backwards, so the public key is *derived from* the private one and anything the private key does leaves a checkable fingerprint. **A certificate is a signed statement, not an actor** — node public key, plus the owner key's signature over it, plus metadata; the certificate signs nothing, the node *private* key makes the handshake signature. And the receiver needs **the owner public key it already holds from out-of-band join**, not one sent over the wire, which would be circular. That prior possession is the whole root of trust.

48. **The seed and relay are ordinary nodes, hosted on Azure Container Instances** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §2). **Every node can be both seed and relay**, so deploying "a seed" is deploying the ordinary daemon with a public address and capabilities enabled — one binary, one code path, and the infrastructure runs the same code every user runs. The hosted node is a **flavour with no owner and no project data**: it participates in discovery without participating in work. **Seeding is nearly free; relaying costs your bandwidth indefinitely**, so they are not the same commitment — and most home nodes cannot relay anyway, sitting behind exactly the routers that created the problem, which is precisely why a hosted node exists. **Relay capability is auto-detected, not a checkbox**: a node asks the seed *can you reach me at this address?* and advertises only on yes, so NAT'd home nodes self-select out without the user knowing there was a question. **Throttled** to a configurable share of uplink so someone else's partition healing cannot saturate your connection. **Distributed passively — rejected: actively rerouting relay load**, because dynamic load-shifting needs coordination and a view of global state while **peer exchange already solves it**: a slow relay simply loses out as peers pick other paths. Home relaying stays possible via manual port forwarding plus dynamic DNS, at more friction than most will accept. **Hosting is Azure Container Instances.** **Rejected: Container Apps and Functions — inbound UDP is a hard no** (ACA ingress passes HTTP, HTTPS and TCP only; outbound UDP works, inbound does not), which is disqualifying for a QUIC listener. ACI has no ingress layer: point it at an image, declare ports including UDP, get a public IP, pay per second. Given up: autoscaling, managed certificates, custom domains, revisions — none of which a UDP broker needs. **DNS**: static IP, an A record, DNS managed yourself; if the instance moves, update one record. **Security**: ACI gives an NSG and little else, but **the attack surface is already tiny** — one UDP port, a custom binary protocol, and a handshake rejecting unknown peers before real work; a WAF protects HTTP and would do nothing here, so **the real security is in the protocol**. **DDoS is the one legitimate concern** since UDP suits amplification; mitigated by NSG rate limiting, QUIC's mandatory round trip and padded Initial, and Azure's free platform-level volumetric protection — not naked, not as wrapped as ACA, an accepted tradeoff. **No Kubernetes** (ACI is explicitly the no-Kubernetes option). Billing has more line items than ACA but is tiny in absolute terms and likely cheaper in practice. **Scale-to-zero is irrelevant and would be wrong**: a seed that is not reachable is useless, so always-on is correct. **To verify before committing**: no ACI deprecation notice was found (results surfaced only unrelated Reserved VM Instance retirements and ACA preview-feature retirements), but confirm independently.

49. **The wire protocol: six messages, three shapes** (2026-08-18; HALL9K-HALL9K-P2P-DESIGN.md §4–§5). Closes §15 row 14 and HALL9K-HALL9K-P2P-DESIGN.md §13 Q3. **The handshake is not among the six** — QUIC already did it. **Framing**: every message carries a type byte and a length prefix, requests additionally a correlation ID, and **unknown types are ignored rather than erroring** so a newer node cannot break an older peer. **Join request** carries project identifier, joiner's owner public key and node certificate, wrapped in proof of the invite token, and is **synchronous** because the invite already constitutes approval. *(An earlier draft had it pending a human decision — wrong: without an invite you would not know the project identifier or which node to ask.)* **An invite token carries** the project identifier, **Sarah's owner public key** (the critical field — without it you cannot verify her node certificate during the handshake and would be trusting whoever answered), addresses, an expiry, and her owner key's signature over the whole thing. Note it works at **two layers**: the owner public key is loaded **before connecting** so the QUIC verification hook can say yes, and the token is then presented **inside** the join message — **handshake mechanics are QUIC's, the trust decision is ours, and the invite is what supplies it**. **Project query** returns project identifiers plus a **version marker** per project (highest sequence per stream, or a hash), enough to answer *am I current?* without transferring anything. **Event range request** names the point as **the last sequence number held per stream, never a timestamp, because clocks lie**; an empty position set degenerates gracefully to *from the beginning*, so bootstrap and catch-up are the same message in two modes. Two properties fall out: **position is derived entirely from what you hold**, so you need not remember who you synced with or when — correct after a crash and when syncing from a different peer — and it is **naturally idempotent**. **Event push** is fire-and-forget with no acknowledgement, which is safe because **the range request already covers gaps**: *push is the fast path, sync is the correct path*, and reliability is unnecessary in the push because correctness lives elsewhere. **Peer exchange** trades node identifier, last known address and last-seen time as **hints, not facts** — stale addresses just fail and are discarded — making the mesh self-healing and propagating relay capability with no coordinator. **Gossip is project-shaped**: a push travels to the sender's project peers, who can read and verify it, and onward to theirs, so **you need no connection to Sarah, only to someone who eventually has one** — and it explicitly does *not* travel through nodes outside the project, who hold no project keys and would be forwarding opaque unverifiable blobs, a spam vector for no benefit. **Cross-project relaying is for discovery only, never payloads.** **The whole event travels** (a claim is a few hundred bytes; making recipients dial the origin would defeat gossip). **Owner-to-owner enrolment syncs wholesale; a cross-owner join concerns one project** — same messages, different scope. **Connection maintenance**: one project connection is the floor and is genuinely sufficient for correctness, but fragile, so **target two or three warm connections** and dial the rest on demand, letting peer exchange fill gaps; a QUIC connection is cheap but not free (keepalives, state, sleeping laptops), though migration means a warm one survives a network change. **The two-owner case is special**: no redundancy, so both sides reconnect on startup with backoff, and **the seed matters far more** since it may be the only possible introduction — and if she is simply offline you just work, events queuing until she appears, which is the entire point of local-first. **The six are a floor, not a ceiling**: revocation announcements, succession distribution and awaiting-materialisation surfacing all need messages and are deliberately left to be discovered while building.

50. **A TCP/443 fallback transport for UDP-blocked networks.** Some corporate and guest networks drop outbound UDP entirely, killing direct, punched, and relayed QUIC alike. Rather than treating those networks as unsupported, peers on such a network dial outbound to a relay over TLS on 443 and the relay pumps bytes between them. *Rejected: accepting those networks as unsupported (corporate networks matter); Tor (blocked by policy on many of the same networks).* Inbound UDP blocking is already handled by punching; **outbound** blocking is the wall this addresses. See HALL9K-HALL9K-P2P-DESIGN.md §9.1–§9.2.

51. **The fallback path is single-stream and sequential.** Multiplexing existed so a large sync could not head-of-line block a live push. On the degraded path that is acceptable: correctness matters, latency does not much, and the push/sync split already recovers anything delayed. Framing and message set are unchanged — this is a second transport, not a second wire format. See §9.3, §9.9.

52. **Ordinary nodes may volunteer as full relays; TCP fallback capability requires a DNS hostname.** TLS on 443 needs an SNI-valid certificate, and IP-address certificates are effectively unavailable; plain TCP would sidestep this but stops looking like HTTPS and may be killed by inspecting firewalls. So a volunteered relay advertises either a hostname (eligible for fallback relaying) or an IP only (QUIC relaying only). The QUIC relay path needs no certificate at all. See §9.5.

53. **The seed relay is the fallback directory and filters peer exchange by TCP capability.** Volunteered relays are learned via gossip, which runs over QUIC — so a UDP-blocked node cannot learn the relays that would help it. Candidates therefore come from the seed (always TCP-capable) plus relays cached from earlier permissive networks. The never-connected-successfully gap is closed by the seed preferentially handing out TCP-capable peers **when the requesting node arrived over TCP**. A filter on the existing peer exchange message, not new machinery. See §9.6.

54. **The relayed TCP pipe carries its own authentication and encryption.** TLS on 443 authenticates the relay's hostname only, and the relay terminates both legs, so it holds plaintext. A two-step inner exchange fixes this: (1) each side sends ephemeral public key, node certificate, and a fresh nonce; (2) each side signs a hash of its own ephemeral key, the peer's nonce, and the peer's ephemeral key with its node private key. This defeats relay key substitution (it cannot sign over the substituted key) and replay (the nonce is fresh). Verification is the same check as the QUIC hook: does the certificate chain to a recognised owner key. Rejection is silent. See §9.8.

55. **Hash arbitration is the single tiebreak mechanism, used everywhere.**

Both contested
orderings — the claim race (§15 row 13) and promotion reconciliation (#44) — resolve by taking the
hash of the competing events and picking the lowest. One mechanism, one code path, no clocks to
reason about.

*Rejected: Lamport logical clocks and hybrid logical clocks* — both capture causality more
faithfully, but add per-node counters, exchange rules, and a second concept to reason about, for a
benefit the recovery path already absorbs.

*Rejected: "most recent event stream wins"* — this presupposes exactly what does not exist, a shared
notion of time. A causal variant (**whichever stream already contains the other's event is
provably later**) is genuinely stronger evidence than a hash, and is noted here as a possible future
refinement, but it only helps when one side actually observed the other and so cannot stand alone.
Deliberately set aside in favour of simplicity.

**Accepted cost, stated plainly:** hash arbitration is *arbitrary*. A stale claim can beat a fresh
one, and the better piece of work can lose. This was already accepted for partition handling; the
recovery path is identical either way — the loser's work is **triaged, never destroyed**.

56. **The winner reviews the loser's work.**

Triage is not merely salvage. When a claim race or
promotion reconciliation is resolved:

   - The **losing branch survives triage** — it is preserved, not deleted.
   - Something **records that a review is owed**: the winner should examine the loser's diff and
  reasoning and fold in anything worth keeping.
   - The review itself is an **agent task**, not platform machinery. Both the losing diff and its
  reasoning exist; hand an agent both and ask it to incorporate the improvements.

The design obligation is only to *make this possible*: preserve the losing branch, and record the
outstanding review. Since the tiebreak is arbitrary, the losing approach is as likely to be the
better one — this is what recovers that value.

57. **Hall9k requires a Postgres connection string, and takes no position on where Postgres runs.**

The container in `docker-compose.yml` is a *convenience*, not a requirement. Docker, Podman, Apple's
container framework, a native `apt install postgresql`, Homebrew, or an existing server the user
already runs are all equally valid — Hall9k needs a reachable Postgres and credentials, nothing more.

Rationale: the install cliff was assumed to be Docker, and on inspection it is not. Anyone who has
Claude Code installed and authenticated, plus `git` and the `gh` CLI, is comfortably over the Docker
bar. And on Linux a container is arguably the *odd* choice, since Postgres is a package; macOS has
Homebrew for the same reason.

**Remote Postgres is supported but is not the default, and the docs must say why.** A database in
someone else's cloud quietly forfeits the local-first promise — offline capability goes away. Allowed
because it costs nothing to allow and some people genuinely have this set up already; never suggested.

*Note for the P2P future:* two people pointing at the **same** remote Postgres are sharing a store,
not peering. That is the shared-Postgres topology already contemplated in §15 row 11 / roadmap #5, not
a defect.

**Rejected: embedding Postgres in the product.** Investigated 2026-08-19. The .NET options
(`MysticMind.PostgresEmbed`, `EmbeddedPostgres`) are small community projects aimed primarily at
integration testing, thin on maintenance, and some require a Visual C++ redistributable on Windows.
There is an open request asking Npgsql to provide an official embedded package, which is itself
evidence that none exists. Not something to stake a product's install path on.

58. **Install stays boring; a doctor check does the teaching.**

Installation puts binaries on the
PATH and nothing else — no database prompt, no provisioning, no guessing. This extends the principle
already settled in `backlog/12-daemon-install.md` (install registers no service, starts nothing).

*Rejected: prompting for a connection string during install* — it asks a question most users cannot
answer yet, at the least informed moment. *Rejected: guessing a local default silently* — it converts
a clear setup step into a confusing failure later, at a moment the user cannot connect back to the
install.

Instead, **the first command that needs a database runs a check**, and that check answers four
questions in order:

   1. **Is a connection string configured at all?** If not, that is the entire answer; nothing else
   matters yet.
   2. **Is it reachable?** Distinguish *nothing listening on that port* from *reached it, credentials
   rejected* — completely different fixes, and conflating them is the usual sin.
   3. **Is the schema present and current?** Marten can create its own tables, so this is mostly an offer:
   *shall I set that up?*
   4. **Only if (1) found nothing — what is available?** Is a container runtime running; is there a native
   Postgres on the standard port; **is there a stopped `hall9k-postgres` container from a previous
   session.** That last case is the nicest possible outcome: *your database exists, it is just not
   running* is a one-line fix.

**The same check works forever, not only at install.** Database moved, container stopped, credentials
rotated, laptop reimaged — same diagnostic, same teaching message. It is not an onboarding wizard; it
is a permanent piece of the CLI.

**Placement consequence:** the check must work while the daemon is down, so **it lives in the CLI, not
the daemon.** This sits slightly awkwardly against the thin-CLI rule (§16 #8 — no Wolverine host
cold-start on every invocation), but a raw Npgsql connection attempt is cheap enough that the rule
survives intact.

36. **The dependency graph routes context, and it routes exactly one hop** (2026-08-20, backlog IDEA-context-routing): the comparison that produced this was Beads, where agents post threaded messages to each other on an issue so that the one who finished the schema can warn the one picking up the projection. Notice what that substitutes for: Beads has no supervisor, so agents must coordinate directly, and peer-to-peer messaging is what you build when there is no central authority to route through. Hall9k has that authority, and after #34 it also has the graph, so the equivalent here is not messaging but **the daemon deciding what a task starts with**. That is the stronger position, because a note depends on agent A correctly predicting what agent B will need before B exists, while the daemon decides after the fact with knowledge A could not have had: which tasks actually depended on it, what merged, and what did not. **The edge does double duty by construction.** A `BlockedBy` edge was declared for scheduling, but "this could not start until that finished" is also a statement about relatedness: the blocker almost certainly touched the same area or produced the thing the dependent builds on (the schema before the projection, the interface before the implementation). So the graph a human already declared answers the context question, with no second structure to maintain and nothing extra to keep in sync. This matters more after #34 than it would have before, because #34 made a dependency mean something stronger: a blocker is met only at true closeout, so by the time an edge resolves there is a merged pull request, a completed review, and a settled outcome behind it. There is something real to hand down. **Capture and landing are two moments, honestly ordered.** The handoff is authored by the run's own agent as the last thing in its final message (a `HANDOFF:` block the build prompt asks for, covering what it did, what a dependent needs to know, and what it deliberately left undone), and the daemon reads it from the terminal result event the session already produces, extending the result parsing rather than adding a summarizer session: cheaper, and the agent that just did the work is the one that knows what it chose not to do. But the run has no merge yet, so nothing may travel: the text goes to `~/.hall9k/runs/<run-id>/handoff.md` and waits there. `RunHandoffRecorded` is appended by `CloseoutEngine` at **true closeout**, in the same transaction as `PullRequestMerged` and `RunCompleted` and immediately before `TaskDependencyResolver` unblocks the dependents who will read it. That ordering is the whole guarantee: an unmerged run has no handoff event, so a summary describing code that never landed can never reach work built on it. Its own event rather than a field on `RunCompleted`, because a run can complete without a usable handoff and `RunCompleted` should not have to lie about that. **The absence is a recorded answer, never an empty string**: `HandoffOutcome` distinguishes `Captured`, `NotAuthored` (the result was read and carried no block), `NotCaptured` (there was no session-end capture at all: a park a human resolved by hand, an agent that never reported), and `Unknown` (a stream written before this existed, replaying as ignorance rather than as a reconstruction, the #30 discipline, and equally an artifact that exists but cannot be read, since an unread file is not an observed one). The three states of the artifact on disk (non-blank, empty, absent) are exactly those three observations, which is what lets the append be honest without guessing (the never-guess rule). **What lands is the task's handoff, not the completing run's.** A handoff belongs to a run, but what a dependent wants is what the blocker *task* ended up doing, and #22 makes review follow-ups automatic, so essentially every merged pull request is an original run retired with `RunSuperseded` plus a follow-up that resolved the review threads and reached `Completed`. Reading only the completing run hands a dependent the thread resolution and leaves the description of the feature itself unread in a superseded run's directory; that is an origin incident rather than a hypothetical, since the first cut of this did exactly that and every task on main that had reached true closeout showed the shape (two runs, one superseded). `CloseoutEngine` therefore composes the landed summary from the `handoff.md` of every run that carried the pull request, in dispatch order, so the run that built the thing leads and the follow-ups read as what they are. Failed and killed runs are excluded, and that exclusion *is* the retry case: a run that died left work which never merged, so its summary must not travel, while a superseded run is the opposite situation, the run whose work is in this merge. Where no run authored one, the recorded absence is the least certain of the ones observed, because a file that could not be read might have held the very text the dependent wanted. **Assembly is depth one, and the depth is the design, not an optimization.** A chain A → B → C passes B's handoff to C and none of A's. If C genuinely needs a fact from A, that is a **missing A → C edge**, something a human can fix and itself a learning worth recording, rather than a context gap the platform should paper over by walking further back; the prompt tells the agent to say so in its own handoff, which is what makes the graph self-correcting. Accumulating ancestry would also mean that by the end of a long chain most of what the agent reads is about work it will never touch, which is both expensive and worse than having less. `TaskDependencyQuery` keeps its transitive closure, because cycle detection at publish must see a cycle anywhere in the chain; context assembly reads the first hop and stops. **The retry case is correct by construction rather than by filtering**: the handoff a blocker contributes is read from the run whose own state is `RunState.Completed`, which only the closeout monitor's merge observation produces and which is where the composed summary lands, so a blocker that died and was later retried to a merge hands down the successful run's summary and never the failed one's (pinned by a test, since #34 left this open). A blocker that no run has carried to true closeout reads as `NotClosedOut`, a query-only member of the same vocabulary: still in flight is a different absence from closed out with nothing to say, and only the task's own edges can observe it. A blocker with no handoff falls back to its objective and acceptance criteria; a blocker with nothing to say still says what it was for. **Fan-in condenses above a configurable threshold** (`DaemonOptions.BlockerSynthesisThreshold`, default 3): eight tasks converging on an integration task is good decomposition rather than a smell (the parallelism is the point, and after #34 the absence of an edge is the daemon's explicit licence to run them at once), but eight handoffs is a heavy way to open a session, so above the threshold a platform-dispatched synthesis session condenses them into one document first, following the review-session patterns (resolved and recorded model per #33, tokens recorded on the dependent's run, artifacts in that run's own directory). Configuration rather than a constant, because the right number is only visible once real fan-in patterns appear. A synthesis that dies or returns nothing usable (including a response that drops the document's own heading, which would land in the dependent's prompt as unlabelled prose continuing the objective) records `Synthesized: false` and the launch falls back to the raw handoffs: condensing is an optimization over a context that already exists, so it may never be the reason a dispatch loses one. This is also the one session the daemon **blocks a dispatch on** (every other spawn is fire-and-forget, monitored in the background), and `RunLauncher.LaunchAsync` is awaited inside the dispatch loop, so a condenser that hangs would hold up every other claim on the node. Hence `BlockerSynthesisTimeout` (default 5 minutes): the wait ends, the timed-out session is terminated rather than left burning tokens for nobody, and the run starts on the handoffs it already had. **`h9k task show` prints the context a task would receive if claimed now**, through the same `BlockerContextDocument` renderer the prompt uses, so the human is reading the agent's actual starting context rather than a second telling that could drift from it. Deliberately **out of scope**: the reviewer's findings travelling downstream alongside the agent's handoff. Findings are about the blocker's code, which the dependent is probably about to build on, so it is plausible, which is exactly why it waits for evidence rather than being built speculatively; it stays an open extension in `backlog/IDEA-context-routing.md`. **Does this block the later vision?** No. Sequenced deliberately BEFORE the 16/18/20 dependency-edge batch so those edges are this feature's first live exercise, and the depth-one rule is what makes that exercise informative: every time an agent reports needing something two hops back, the graph learns an edge it was missing.

59. **Pre-PR review runs two lenses per cycle, and the second one is adversarial** (2026-08-21, backlog 34): the internal reviewer built in #23 checks the work against its objective, its acceptance criteria, and repo doctrine. Origin incident (2026-08-21, PR #21): four Copilot passes over the same branch each surfaced different findings, and the difference was not that fixes introduced new defects. Checked empirically, the final pass flagged code in `TaskAddCommand.cs` that was byte-for-byte identical in the previously reviewed commit, and a prompt-injection risk in `WorkItemContext.cs` that had been present in all four reviewed commits. Copilot was re-sampling the same code, and the accumulated samples caught real defects that our own conformance review had missed across several cycles. The lesson is not that a third-party reviewer is better; it is that **one review pass is one attention budget**, and what a pass is not looking for it does not find. So a cycle now runs **two independent passes with fresh context**: the existing **conformance** lens, and an **adversarial** lens that is told to assume the code is wrong somewhere and find where. The adversarial prompt is a genuinely different attention budget, not a second roll of the same dice: it is never told the objective or the acceptance criteria, because a reviewer holding the intent reads for alignment with it, and the defects this lens exists to catch (injection and trust boundaries, missing sanitization, concurrency and races, API misuse, resource and process lifetime, failure-path leftovers) are wrong whatever the intent was. Those classes are named in the prompt as a warm-up and explicitly not as a checklist, since a checklist becomes the next blind spot.

**What merges and what does not.** The passes run independently and their findings merge before the verdict: MergeReady requires **every** lens clean, either lens finding real problems produces **one** NeedsFixes verdict over the merged finding list, and **one** fix session addresses all of it. Each pass records its own `ReviewDispatched` (with its model, per #33) and its own `ReviewPassCompleted` carrying the lens and that lens's verdict, so "which lens earns its keep" is a query over the stream rather than an impression; `ReviewCompleted` stays the cycle's merged milestone. The budgets stay **per cycle, never per lens**: one automatic fix run per cycle against `MaxAutomaticReviewFixRuns`, and one verdict re-prompt per cycle however many passes ended without a VERDICT line or with a needs-fixes verdict naming nothing (#86). Two lenses do not double the parking math.

**Cost, and the seam.** Two fresh-context passes roughly double review tokens per cycle. That is stated rather than hidden: it is the price of not outsourcing defect hunting to a third-party reviewer's roll of the dice, and the per-pass token records make the bill visible. `ReviewLens.CycleLenses` is the seam - a third lens, or a repeated adversarial sample, arrives by appending to that list, and the engine, the aggregate, the artifact layout, and the merge rule already handle an arbitrary count. Two is the shipped shape because two is what the incident justified. Relationship to backlog 25 (all reviewers): that task broadens whose findings get **handled** on the PR after it opens, this one broadens what internal review **generates** before it opens. They compose, and neither replaces the other - Copilot stays valuable precisely because its sampling is outside our control.

**Two passes, one worktree.** The lenses are dispatched back to back and read the same directory at the same time, which is the first point in a run where two agent sessions overlap: before this, the main session, the gates, the single reviewer, and the fix session were strictly sequential. Anything a session touches therefore has to be its own. Each spawn now writes its **own settings file** rather than the run's; the shared one was rewritten by every spawn, so the second dispatch would truncate it inside the first child's config-loading window and cost that child the co-authored-by suppression the file exists for (PLAN.md §6.6). Review sessions run with **`GIT_OPTIONAL_LOCKS=0`**, because the opportunistic index refresh that `git status` and `git diff` perform takes `.git/index.lock`, and the loser of that race reads `fatal: Unable to create '.git/index.lock'` as evidence about the diff; the locks a writer genuinely needs are untouched, and a read-only reviewer runs none of those. And both prompts **forbid building and testing**, naming the gates that already ran and passed on this exact commit so the reviewer knows the question was answered rather than skipped: two builds sharing one `obj/` and `bin/` fail each other with file-in-use errors that read exactly like defects in the code under review. That is why all three are stated rather than left to luck: a platform collision reported as a verified finding spends the cycle's one fix run on nothing, or lands in the fix session's dispute path and parks the run for a human. Giving each pass its own read-only worktree would isolate more thoroughly and stays available if the read-only rules ever prove insufficient; it is not needed while neither pass writes.
60. **Adoption reads once, refuses closed work, and never invents a contract** (2026-08-21, SLICE-1 S1-11): `h9k task add --from-issue <number-or-url>` makes `ExternalReference` real, and every choice in it follows from one distinction the platform already draws (§9.1): the external system owns the item's *content*, Hall9k owns the *readiness contract*. **The title is a seed and the body is context; acceptance criteria are neither.** An issue body describes what somebody wants; criteria state what would make it done, and deriving the second from the first is exactly the plausible reconstruction the never-guess rule forbids (AGENTS.md), and worse here than elsewhere, because a fabricated contract is one an agent would then be measured against. What counts as acting rather than reading is named one character at a time: the control characters, where the escape sequences live, and the format characters that reorder or hide what surrounds them (the bidirectional embeddings, overrides and isolates, the deprecated format characters, the annotation characters, and, outside the BMP, the tag block that spells out ASCII in glyphs that render as nothing). 61. **A recovered blocker refreshes its dependents** (2026-08-21, backlog 27): dead is a question asked fresh every sweep, never a flag set once. Origin incident (2026-08-21): the platform's first overnight crash-recovery ran through the first real dependency graph. The machine went down with the chain's head running; on daemon start the orphan was failed honestly and both dependents were held-for-human with the dead-blocker reason, all correct. Then `h9k task retry` put the blocker back to work and the holds did not clear, so both dependents kept reading NeedsHuman for what would have been the whole rebuild: hours of a board saying "act now" about a situation already handled. The unblock-at-closeout path ignores the stale record, so nothing dispatched wrongly and nothing was stranded; this was display honesty. That is not a small thing, because a status surface which overstates urgency trains its reader to ignore it, and an attention pane nobody trusts is worse than no attention pane.

**The mirror of the hold, appended by the same owner.** `TaskDependencyResolver` is the single owner of dependency state transitions, so the pass that records a hold is the pass that observes the hold has stopped being true, and the two can never disagree. It appends `TaskDependencyRecovered` on each dependent, naming the blocker and what was observed about it; the recorded death is dropped and the task returns to plain `Blocked` with the ordinary waiting-on display. **Driven by observed state, never by the command that caused it**: the resolver asks whether the blocker is dead *now*, so a blocker back in the pipeline is alive whether a human retried it, a lease sweep requeued it, or anything later does the same. Nothing in the resolver knows `h9k task retry` exists. That is also why `h9k task retry` appends nothing to the dependents itself, which would have been the tempting shortcut: it would assume the retry succeeds, and it would put dependency bookkeeping in a second place. Latency is one dispatch cycle, which is the same budget the hold itself was recorded on: only the sweep notices a death, and only the sweep notices a recovery, for the same reason (neither appends a closeout event for the merge-driven path to react to).

**History stays honest, and the pattern is hold, recover, hold.** Both records stay on the stream, because the hold happened and so did the recovery; nothing is rewritten. A blocker retried into a second failure is held again by the next sweep, which is why the recovery is an event rather than a cleared flag. The aggregate and both read models now keep what was recorded **per dead blocker** rather than only the newest reason, which is what lets two questions be answered without guessing (the never-guess rule): when one of several dead blockers stops counting, whether by recovering or by closing out, the reason the human keeps reading is the newest death the task still records; and a blocker that is still dead but died a *different* death gets its hold restated, taking the newest slot among the dead because it was observed just now. **What survives is derived wherever the event is applied, never carried on the event.** A pass computes from the world it read, so a death another node appends between that read and the commit is invisible to it, and a surviving reason snapshotted there would silence a hold that had just been earned — permanently, because every later sweep compares against the recorded deaths, finds that one already recorded, and has nothing new to say. Deriving costs nothing, since the records are already there, and cannot go stale. Keeping the records in the read models as well as the aggregate is what stops the same stream replaying to different advice in `h9k task show` than the decider sees. **A new projection field ships with its rebuild.** The task projections are Inline, so a document written before this change lists its dead blockers with no per-blocker map beside them, and the surviving-reason fallback would read that as nobody having said anything: the first blocker to recover or close out would blank the reason for the blockers still dead, permanently, since the aggregate is rebuilt from events and finds the surviving death already recorded, so no later sweep has anything new to say. The field is therefore a staleness marker in `TaskLifecycleProjectionBackfill` alongside #34's `assignedOwnerId`, and every document missing it is replayed at daemon start. That backfill also stopped using Marten's `Advanced.RebuildSingleStreamAsync`, which stores the rebuilt document one version ahead of its stream (repeated calls walk it up by one each time); an Inline projection skips an event no newer than the document it is applying to, so the next event the repaired stream ever received was silently dropped, and here that next event is the recovery the repair was for. The rebuild now deletes and re-stores at the version the events actually reach, in one transaction, so a crash cannot leave a task with no document at all, which is a state a backfill that queries documents could never find again. Origin incident (2026-08-21, caught in pre-PR review): the first cut of this decision added the field to both projections with no marker and no rebuild, which is the same shape as #34's own 2026-08-20 incident. The restatement case is `h9k task resolve`: a resolved blocker is still dead by #34's rule (its run stays Failed, so the merge observation true closeout waits on will never arrive, the 2026-08-20 incident), so its dependents are still held, correctly. What was wrong was the recorded advice, which still read "retry or resolve it" about a task that is now Done and would have both commands refused. Restating it is the same crying-wolf fix as clearing it, applied to the case where the hold itself is still true.

**Advice that names a lever the platform will honour.** A Done blocker is dead exactly when the run that would have carried its merge observation has left the closeout monitor's watch set, and the monitor only ever inspects runs still in that set (`AwaitingReview`, `ReviewPending`, `CloseoutParked`). So telling the human to merge that pull request is telling them to do work nobody is watching for: the merge lands, nothing observes it, and the hold stays. What the restated reason names instead is `h9k pr resolve` on the blocker, which dispatches a follow-up run onto the existing pull-request branch and puts it back under watch, so that run's merge *is* observed and the dependents clear on their own. It is named only where the reopen would actually be accepted — the blocker needs a recorded run to follow up on and a pull request to follow up about — and where it would not, the only honest lever left is on the dependent's own side, revising its dependencies. This is the same rule the Abandoned branch already followed: never advise a lever the decider will refuse.

**Deliberately not done:** treating `h9k task resolve --pr <merged url>` as closeout, which would clear the hold outright. Nothing weaker than an observed merge counts as a dependency being met (#34), and a human's attestation about where work landed is exactly the weaker signal that rule exists to refuse.
62. **Every reviewer's threads are feedback the platform sees and dispatches on** (2026-08-21, backlog 25): the closeout monitor built in #22 counted unresolved review threads only when Copilot had opened them, and the resolve skill filtered to the same author. Origin incident (2026-08-20): Brian left a review comment on PR #20 and the machinery was structurally blind to it, on the same evening the question came up. Teams mean teammates reviewing, so the inspector now counts **every** unresolved thread whoever opened it, and a teammate's thread triggers the same automatic follow-up on the same budget with the same park behaviour. Copilot keeps its one genuinely bot-specific path: an errored-review placeholder is still matched by Copilot's own login and failure notice, because a human review cannot error and matching "unable to review" in a person's prose would read an opinion as an outage.

**The self-review discriminator, and what it rests on.** Under §6.6 there are no bot identities: agents commit and comment as the human. That made human and agent comments indistinguishable by author, which is exactly what hid the PR #20 comment. The rule that survives it is about **thread starters, not authors**: agents never open a review thread, they only reply inside existing ones, so a thread's FIRST comment is always a reviewer's, including when its author is the pull request's own owner, which is a human leaving themselves a note and is treated as reviewer feedback like any other. Later comments in a thread are judged by content, since a reply under the author's login may be the human's or a previous run's. This is a heuristic riding on an invariant, and it is recorded as such in AGENTS.md beside the no-bot-identity rule: if agents ever gain their own thread-opening voice it breaks, and the honest long-term answer is node-signed authorship from the P2P identity layer (#38-#58). Bot versus human is read from the provider's own actor type (GraphQL types an app account as `Bot`) rather than guessed from the login string, with the known Copilot logins as an extra yes rather than the rule.

**Human threads get more care than bot threads, and the prompt says so.** A question gets an **answer**, not a code change invented to look responsive; a suggestion gets the fix or the reasoning, once; a human's thread is never resolved without a substantive reply, because a resolved thread with no answer in it reads as handled and is worse than an open one. Judgment stays bounded exactly as everywhere else (#11's never-loop spirit): one honest attempt per thread per follow-up, and a **design disagreement the agent cannot honestly judge parks the run** rather than being settled by whichever side it found more persuasive. The park reuses `ReviewParked` whole (it already surfaces as NeedsHuman, keeps the lease refreshed through adoption, and is resolved with `h9k review resolve`), and it is triggered by the same `RESOLUTION: disputed` marker the pre-PR fix session already answers in (#23), read from follow-up runs only, with the agent's closing summary saved beside the run as the second position a human reads. Nothing is pushed when a run parks. **Responses land where the feedback lives**: an inline comment gets an in-thread reply, and a review BODY, which GitHub makes unthreadable, gets a top-level PR comment naming the review it answers and summarising what was done, never silence and never an unanchored comment the reviewer has to connect themselves (origin: the PR #20 human review was answered only through the work itself, with no visible reply on the PR). The skill is renamed `resolve-review-threads` and the Copilot-specific name is retired.

**What the platform cannot see, said out loud.** GitHub hides an unsubmitted (`PENDING`) review's comments from the API, so feedback reaches the platform only on submit and a reviewer part-way through a draft reads as silence. That is correct behaviour, not a gap to work around, but leaving it unexplained invites the wrong conclusion, so the inspector, the skill, the follow-up prompt, and AGENTS.md all say it.

**Re-requesting review after fixes is opt-in, priced, and capped** (Brian, 2026-08-21). When enabled, a fix follow-up that pushes earns the reviewers another pass, so whoever raised the findings countersigns that they were addressed. Off by default, because each pass costs review quota and a reviewer re-reading a diff it has already read is precisely how the doom loop of refinement and re-refactoring starts. Configurable at the **owner** level (a standing "I want my work countersigned") and the **project** level, with precedence taken from the model-policy shape (#33): the more specific level wins, so **project over owner over the node default**, since a repository is where review culture actually lives. Bounded by its own counter beside the closeout budget (`MaxReviewRerequestsAfterFixes`, default 2) rather than inside it, because a re-request asks a reviewer a question while the closeout budget bounds the agent runs that answer them, and one running out should not silently spend the other. The counter is summed across the task's runs, since every follow-up is a fresh run and a per-run cap would be no cap at all; each run asks at most once, which is the natural dedup (a run pushes its fixes once). At the cap the pull request settles on the internal review, the in-thread replies, and CI: the guards that already reviewed every fix before it pushed, which is exactly what it would have settled on with the option off. This is the first owner-level setting the platform has, so it also brings `h9k owner show` / `h9k owner set`.
63. **The two lenses become two tracks, each converging on its own terms** (2026-08-21, backlog 35): #59 gave a cycle two passes but kept one loop around them, so a cycle ended when both lenses agreed and the whole thing was bounded by a single fix budget of 2. Both halves of that were wrong in practice. The conformance-only loop at budget 2 **parked work that would have converged at cycle 3 or 4**, and the first manual adversarial loops on PR #21 (three rounds, 24 findings, two of them regressions introduced by earlier fix rounds) showed the opposite failure: the adversarial lens keeps finding things for many more rounds than 2, and it converges: severities trended down every round. One bound cannot be right for both, because the two lenses are asking questions that terminate differently. So the lenses become **tracks**: dispatched together after the gates pass, each with fresh context and **its own cycle count**, each ending when its own rule says so. A track that comes back clean goes dormant and the other continues alone.
**Two rules, because two questions.** **Compliance** (the #59 conformance pass, unchanged in what it reads) grades nothing: a criterion is met or it is not, and there is no severity ordering to gate on. It ends the moment it is clean, and if it is still returning findings at `MaxComplianceReviewCycles` (3) the run parks, because at that point nothing automated is left to try. **Adversarial** runs under a **severity gate**. Every finding carries a grade with anchors stated in the prompt rather than left to the reviewer's intuition. `high` is a correctness, security, or data-integrity defect reachable in realistic use; `medium` is a real defect with bounded or unlikely impact, or a doctrine violation that misleads without corrupting; `low` is polish. Cycles 1 through 3, **any** finding of any grade is fixed and forces a fresh re-review: the early cycles get full rigor while the code is still converging, and the gate is deliberately not the tool for that phase. From `AdversarialSeverityGateFromCycle` (4) onward only a `high` forces the next cycle; mediums and lows are still fixed, they simply stop re-triggering the loop, which is the nit-churn tail the gate exists for. The cap is `MaxAdversarialReviewCycles` (10), and highs still appearing there park the run, **not as a spent budget** but as "the machine kept finding real problems in this diff and a human should look at why", which is what the park reason says. That reason is read off the cycle's recorded grades rather than assumed from the fact that the track continued, because a high is not the only thing that keeps it alive: an ungraded finding forces another cycle by the rule above, so a reviewer whose grades never parsed can reach the cap with no stated high at all, and telling the human the machine kept finding high-severity problems there would steer them to restart correct work over a defect nobody ever graded. Restarting with a fresh agent is a resolution the human may choose, never an automatic one. The single `MaxAutomaticReviewFixRuns` knob dissolves into these two, plus the gate cycle, so the split is legible in `DaemonOptions` rather than hidden in one number.

**Scope decides where a fix lives, never whether it matters.** Every adversarial finding also carries a scope tag with a **mechanical anchor**: in-scope if the defective line lives in code this branch added or changed, out-of-scope if the defect is pre-existing on the base branch, checkable against `git diff <base>...HEAD` rather than a judgment about whose problem it is. An out-of-scope **high** is fixed in this pull request, in a commit of its own, so cleanup-as-you-touch does not blur into the branch's real work in the authored history. Out-of-scope findings the reviewer graded **medium or low are not fixed here at all**: the daemon turns each into a **draft bug task** (`ReviewDraftBugTask`) carrying the originating task and run, the branch, the lens, the cycle, the reviewer's declared grade and scope, and the finding verbatim behind a fence, all recorded by machinery per the observation-gates doctrine, and explicitly stating that no pull request existed yet rather than leaving a reader to assume one went unrecorded. The draft is inert until a human publishes it (#34). **Routing takes both tags stated.** A finding whose grade the reviewer omitted, or wrote in a word the parser does not know (`critical`), is ungraded rather than low, and an ungraded finding is fixed here and forces its cycle exactly as a high would. Reading it as a non-high would do both irreversible things at once: export a defect nobody graded out of the pull request, and spend none of the cycle it would otherwise have forced. Unknown is not low anywhere the gate is consulted, and routing is one of those places. Every routed finding is recorded on the stream whether or not the draft was created, because a routing that failed and a routing that never happened must not read the same, and **a failed draft creation never fails the review loop**; it is a courtesy paid to a defect this branch is not fixing. A failed one is counted apart from the routings that worked, since no draft exists for it and "routed" is what tells a reader the defect is written down where they can find it. **A defect is routed once per run.** The fix session is told to leave a routed line alone and every later reviewer reads with fresh context, so the same line comes back for as long as the other track keeps the loop alive; routing it again would turn one exported defect into one inert draft per cycle and report it to the human as several. Two reports are the same defect when they name the same **place**, not the same string (`ReviewFindingLocations`): each cycle's reviewer is a fresh session writing paths in its own hand, so `src/Legacy.cs:40`, `./src/Legacy.cs:40`, and `Legacy.cs:40` are one defect written three ways. A *different* stated line in the same file is deliberately a different place, even though a routed line can shift when a fix session edits above it: a duplicate inert draft is visible and a human discards it in a moment, while collapsing by file alone would silently swallow a second, genuinely different defect in a file this run had already routed one from. Same file and same stated line is an observation; same file and some other line is a guess, and so is a file with no line on it at all: an unplaced finding, whether it named no file or only a file, is treated as new rather than folded into a defect it may have nothing to do with.

**The terminal verdict stays MergeReady; the record says how it was reached.** `ReviewSettled` carries a `ReviewSettlement`: **Clean** when a reviewer read the final tip and found nothing, **Settled** when the severity gate ended the loop, findings were routed away, or a human resolved a park. Settled endings ship fixes **without another review pass**, by design (that is the whole point of the gate), but never without the **gates**: the terminal fix session's commits reach the pull request like any other, so `ReviewFixCompleted` re-runs build and test before the loop settles, and it is the reviewers' reading of those commits that is skipped, never the machine's. The **residual record** is what keeps the history honest about the part that is skipped: every finding a track ended on, plus every finding routed out of the pull request in any cycle, each with its grade, its scope, and whether it was fixed-unreviewed or routed. Routing counts from the cycle it happened in rather than from the track's last one, because a cycle that routes one finding and is forced to run again by another still exported the first; counting only terminal cycles would let a run settle **Clean** over a defect it knowingly shipped to a draft. `h9k task show` prints "merge-ready (clean)" or "merge-ready (settled, N residuals fixed, M routed)", naming any routing that failed separately rather than counting it as routed, because merge-ready is one word for two different claims and a reader deciding how much to trust a pull request should not have to dig through the run stream to tell them apart. A run whose review was in flight before settlements existed records none and says so, rather than being assumed clean. There is also an **empty terminal case**: from the gate cycle onward, a cycle whose findings are all routed away leaves nothing to fix, so the track ends immediately with no fix session, because nothing changed and a fresh reviewer would read the identical tip and return the identical findings. Before the gate the same cycle keeps the track alive, which is where the acceptance criteria put the line: the other track can still be forcing fix sessions that rewrite the branch, a dormant track is deliberately never reawakened, and a track retired at cycle 1 over one out-of-scope medium would never read the fix commits, which is exactly where PR #21's two regressions came from. It cannot spin on an unchanged tip either, because a cycle with nothing anywhere left to fix settles the run whatever the track decided. A track the run ends that way still gets its own `ReviewTrackConcluded`, written as Settled at the cycle the run stopped on: the per-track record exists to say how and when each track ended, and a lens with no entry at all reads as one that is somehow still running.

**Agents never grade their own way past the gate.** A fix run disputing a finding **or its severity** parks for the human, exactly like the existing dispute lever. The severity decides how the loop converges, so an agent quietly re-grading a High as a Low would be deciding its own exit condition.

**Dormant tracks stay dormant, deliberately.** Adversarial fix sessions after compliance has gone clean do not reawaken the compliance track, so a late fix ships without a conformance reviewer ever reading it. Accepted trade-off (Brian, 2026-08-21): compliance converges in one or two cycles in practice, the fix sessions in question are small, and the build/test gates, the external reviewer, and the human merge gate all stand behind the loop. This is documented rather than fixed; if late fixes start breaking criteria, the cheap correction is to re-open the compliance track for one final pass before settling. **Explicitly out of scope:** the post-PR closeout reopen budget (Copilot threads, failing checks, attempt 1/2) is untouched and stays at 2, with `h9k pr resolve` as its reset lever. **Does this block the later vision?** No. The per-track policy is one pure decider (`ReviewTrackPolicy`), so a third track, a different gate, or a per-project cap arrives there rather than in the engine.

64. **The dispatcher counts live agent runs, and stops claiming at the number the machine can hold** (2026-08-22, backlog 37): the claim loop took everything eligible, so the ceiling was enforced by the operating system rather than by the platform. Origin incident (2026-08-21, twice in one day): a morning kernel panic with compressor exhaustion and 37 swapfiles under an MCP-heavy agent fleet, then an afternoon OOM that killed three of four concurrently dispatched Opus-1M sessions (tasks 17, 35 and 27 died mid-run; 25 survived) the first time the queue went four wide. `DaemonOptions.MaxConcurrentAgentSessions` (default 3) is now measured against the node's **live-run count**, converted to the sessions those runs reserve, and everything past it simply stays `Queued`, which already honestly means waiting, and is claimed as slots free up **oldest assignment first**. Assignment is the ordering key rather than `AddedAt` because assignment is the act that put the task in the queue: a task drafted in January and assigned this morning is behind one drafted and assigned last week, and ordering by drafting alone gets that backwards. The difference was invisible before the ceiling, since everything eligible was claimed in one sweep and the order decided nothing; now it decides who waits. `AddedAt` still breaks ties, which is what a backlog assigned in one command looks like, and an unassign clears the timestamp, so re-assigning joins the back of the queue, which is what unassigning and assigning again means. `AssignedAt` is a new field on both task projections and therefore carries a staleness marker in `TaskLifecycleProjectionBackfill` like every projection field before it. The ceiling is denominated in sessions rather than runs because a session is what the machine runs out of memory for, which **retires** the older run-denominated `MaxConcurrentRuns` key rather than renaming it: a number written in runs cannot be carried across into a session budget without silently meaning something smaller, so a node that still has the old key configured is told at startup that it is no longer read and which setting replaced it, rather than having its number quietly reinterpreted or quietly dropped.

**The ceiling is denominated in agent sessions, not in runs.** Sessions are what the machine runs out of memory for, and a run tree is not one process: a review cycle spawns every active lens together and waits on them together (#59), so a run under review is `ReviewLens.CycleLenses.Count` resident Opus sessions. A run-denominated ceiling of three therefore permitted **six** concurrent sessions — two more than the four that caused the origin OOM, which is to say the guard shipped without the protection it was written to provide (found in pre-PR review of this change, 2026-08-22; the two-sessions-per-run amplification predates the ceiling, the false guarantee did not). `NodeLoad` is the conversion. It counts run trees, because a run is the only thing the dispatcher can decline to start, and charges each live run the **peak** sessions its tree can hold, from `NodeLoad.PeakAgentSessionsPerRun`, which is derived from the lens list rather than written down — so appending a third lens tightens the ceiling instead of quietly doubling what the machine is asked to hold. The peak is reserved from the moment a run is claimed rather than counted once it is reached: a run building today reaches its review cycle on this same machine, and a ceiling that only counted what was resident this second would claim three build sessions and then watch them become six, which is precisely the failure above. Reserving is what makes "cannot start more agents than the machine can hold" a guarantee rather than an average, and it is why the shipped default of three sessions means **one run at a time** on a two-lens review cycle. That is the honest reading of the incident (three sessions is what this machine was observed to carry; four killed it), and the lever is per-machine: the tower sets eight and gets four runs. A session budget smaller than one run's peak still dispatches one run, because a node that silently does no work is a worse answer than a node that runs one task over a budget no schedule could have honoured anyway.

**Open, and Brian's call to close: what the shipped default delivers.** Backlog 37's acceptance criteria asked for `MaxConcurrentRuns` with a default of 3, meaning three concurrent runs. What shipped is three *sessions*, which on a two-lens review cycle is one run at a time, so a fresh install carries a third of the runs the criterion named. Both cannot hold at once while a review cycle is two resident sessions: three runs is six sessions, two more than the four that caused the origin OOM, and three sessions is one run. The session denomination is the honest unit and is not the open part; the number is. Leave the default at three sessions (one run, the count this machine was observed to carry) or raise it to six (three runs, the criterion as written, on a machine with the memory for it). That is a per-machine product judgement rather than an implementation detail, so the pre-PR review that found it routed it to Brian and this entry records it as open rather than settled (2026-08-22). Until then the default is three sessions, and changing it is one configuration line on the node that wants a different answer.

**A live run is a session tree, counted once.** Build sessions, review cycles, fix runs and synthesis passes all belong to the run that owns them, so they cost that run's slot and never a second one: counting them separately would let two builds plus their reviews exceed the number the ceiling was chosen to protect. The unit is nonetheless the **run**, not the task: one task can hold two slots, because a daemon restart can leave it with two session trees. Startup adoption resumes a run's review cycle, the sweep that follows requeues the task without failing that run (its build process is long gone), and the next claim launches a fresh build for the same task. Counting per task read those as one and let the node go a whole session tree over its ceiling (found in pre-PR review of this change, 2026-08-22); the ceiling counts what the machine has to hold, and the machine holds both. **Corrected by #66 (2026-08-22, backlog 39):** the two-slots-per-task account above was a bug this paragraph documented rather than a shape the platform intended — catch-up now refreshes the adopted run's lease before the sweep evaluates expiry, so adoption wins outright and a task is never both adopted and requeued in the same startup. A concurrency overshoot from a resumed park or a re-entered stranded run is still possible and still accepted for the reasons stated here; the double-booked *task* the old account described is not. A run gives its slot back when its tree ends, which is completed, failed, parked, or handed to a follow-up with nothing running, and **not** at true closeout: a task waiting on a merge observation holds no memory, and a follow-up takes a slot the ordinary way, by being claimed as its own run. The unit is deliberately **not the lease**, which is what the first cut counted. A parked run keeps its lease on purpose (#24, so the expiry sweep cannot requeue the task out from under a human's worktree), and counting leases would let one abandoned review hold a slot on a two-run laptop until somebody came back to it. Two consequences follow honestly. A claim whose run document has not landed yet **does** hold its slot, because the dispatch handoff is a session about to exist and a sweep inside that window would otherwise claim straight over the ceiling. And resolving a park hands a worktree back to a session while the node may already be full, which is an accepted overshoot: refusing a human's explicit resume to protect a number is the worse trade, and capacity reads as zero rather than negative, so nothing further is claimed until the node is back under. Startup adoption re-entering a stranded run is the same shape with the same answer. Accepted is not the same as invisible: the sweep that measures a node over its ceiling says so once per episode rather than once per five seconds, and `h9k status` reads the over case as what it is instead of as "4 of 3 running", which on a pane whose job there is to say the board is throttled rather than broken would read as the opposite (found in pre-PR review of this change, 2026-08-22). The lease-expiry sweep also records the run it took the lease from as failed, in the same transaction, when that run is this node's own and was `Dispatched` or `Running`: those are the states an agent process is resident for, the sweep only ever requeues past a locally dead one, and a run left reading `Running` behind a dead agent would have gone on occupying a slot until the next daemon start's orphan adoption noticed. Another node's run is left alone, because the sweep reads every stale lease in the shared database and cannot ask that machine's operating system anything: a stopped daemon whose detached agent is still working is the ordinary case (#29, down is not death), and a `RunFailed` recorded for it would hide that run from its own node's startup adoption, so the live session is never re-monitored and its work is thrown away (found in pre-PR review of this change, 2026-08-22). The task is still requeued either way, because the task is the shared thing and the run is not. Nothing startup adoption resumes is failed by the sweep, and adoption resumes three things. `Verifying` and `UnderReview` are two of them: the build session has already exited by then, so its recorded pid says nothing about whether the run is over. The third is a run still reading `Dispatched` or `Running` whose process is gone but whose result is already on disk, which is the agent that finished while the daemon was down; adoption re-monitors on alive-or-result-on-disk, so the sweep asks the same question through the same shared check rather than a second one that could drift from it. Adoption runs immediately before the startup sweep, so failing any of the three would record a failure for a pipeline executing at that moment, which the next event that pipeline appends would silently undo (all three found in pre-PR review of this change, 2026-08-22).

**Waiting for a slot is not a state.** The task is `Queued`; the reason line is display composition in the backlog-28 shape. The daemon publishes what each sweep is carrying as it leaves (`NodeDispatchLoad`: the live count, the run and session ceilings it was measured against, the sessions those runs reserve, and when), measured after that sweep's claims rather than before them, because the sweep that fills the node is precisely the one whose deferrals need explaining and a pre-claim count would have it report spare capacity while it turns work away. `h9k status` reads that record rather than re-deriving the rule, so the board and the dispatcher cannot disagree about how full the machine is. That record is telemetry and is written after the claims have committed, so a failure to write it is logged and the claims are handed to the launcher regardless: a lease with no run behind it is stranded past the reach of both the expiry sweep (the heartbeat service keeps refreshing it) and startup adoption (no run document exists to adopt), which is a far worse outcome than one stale number on the pane (found in pre-PR review of this change, 2026-08-22). A measurement too old to describe now produces no line at all rather than a repeated number, per the never-guess rule. The queue earns a section on the attention pane only when the ceiling is the reason nothing is dispatching, because that is the one case where a board with nothing moving is working exactly as designed, and a human who cannot see that goes looking for a fault. The section lists its rows in the order the dispatcher will serve them, since it tells the human that each one starts as a run finishes, and every `Queued` task is in it, including a closeout follow-up the monitor reopened: the dispatcher defers that follow-up like any other queued task, so a pane that showed it as running work would disagree with the daemon's own log. The log follows the same discipline: the ceiling is stated once at startup, and each deferred claim is logged once with the task id and the live count, never once per five-second sweep.

**Configuration, not code**, like the review caps: the tower with the memory for six sessions and the laptop that panicked at four are the same platform with different answers, and the setting is now in the unit those sentences are already written in. **Does this block the later vision?** No, and it moves toward it: the count is per node and published as node telemetry, which is the shape a P2P scheduler needs to place work on the node with room (§16 #38-#58). This composes with backlog 29 (the slim agent profile) rather than substituting for it: 29 shrinks what each agent costs, this bounds how many exist.

65. **Jira is a read connection plus an agent-mediated pen** (2026-08-21, backlog 18): `h9k connection add jira` registers a Jira Cloud site, account and API token; `h9k task add --from-jira PROJ-123` adopts a card through the same seam #60 built; `h9k task push-to-jira` dispatches an agent run that writes a card; `h9k task link-jira` records the result after reading it back; and closeout comments the pull request on the card. Every one of those follows from a single asymmetry Brian named: **reading Jira is configuration-agnostic and writing it is not.** A GET returns the same document whatever a project's issue types are called, so the platform reads cards itself. Creating one is configuration all the way down: whether a "dev task" is a Task or a Story, which fields are mandatory, which board a support request routes to. Those are one organisation's rules, and a platform that modelled them would be modelling somebody's Jira admin screen and then arguing with it every time it changed. So the registered credential is for reads (the import snapshot, the verification of an agent-reported key) plus exactly one config-agnostic write, and all card authoring goes through an agent session instead. That is not a compromise; it is the setup Brian's team already runs by hand, where the org's Jira rules live in a skill file and a person reads it before filing anything. `DiscoverRepoSkills` already hands every dispatched agent that file, so the platform's job is to dispatch a session into the project's repository, tell it what the work is, and stay out of the way. **Agent-facing platform commands are observation gates.** The corollary of handing the pen to an agent is that the platform must not take the agent's word for what it wrote. So the run finishes by invoking `h9k task link-jira <task> <KEY>`, and that command reads the key back through the registered connection before recording anything: the reference, the title and the status on `WorkItemLinked` are what Jira answered, and the agent's claim is an argument that was checked rather than a fact that was accepted. A mistyped, hallucinated, or wrong-site key does not resolve, nothing is written, and the refusal names the key and the site and both reasons a card can fail to resolve, so the agent can correct itself and try again. This is the house CLI standard (failures print why, quoting the rule) doing double duty as an integrity mechanism, and it generalises past Jira: anything an agent wants Hall9k to believe should pass through a command that verifies first. The daemon's own record follows the same rule from the other side, since `WorkItemPublicationCompleted` reads "was this task linked" off the task rather than off the session's summary: a run that reported a beautiful success and never got a key past the gate completed without a link, and the ledger says exactly that. **A comment at merge, never a transition.** When the closeout monitor observes the merge of a task carrying a Jira reference it posts one comment with the pull request. A comment is the one Jira write that needs to know nothing about how a project is configured, which is precisely why it is the one the platform makes itself. Which status a merge should move a card to is one team's workflow rather than a fact about software (Done on one board is Ready for QA on the next), so transitions wait until real usage says which ones matter. The comment says outright that nothing else will happen to the card, because a card that silently gains a comment and never moves reads like an integration that half worked. The write is best-effort and never retried: the merge is already recorded and the dependents already unblocked by the time it runs, and a retry loop around a write nobody is watching is how one card ends up with four identical comments. GitHub gets nothing equivalent, deliberately, because #60's pull-request mention already makes GitHub cross-reference the merge on the issue's own timeline. **The status mapping lives in the adapter, and reads the category rather than the name.** #60 made the adoption gate positively open, which put the job of translating a source's own vocabulary on the source's adapter. Jira's answer is `statusCategory`: every status in every workflow, however it is named, belongs to `new`, `indeterminate`, or `done`, so "Ready for Ozzie" maps honestly without the platform knowing what Ozzie is. The status's own name rides along on `WorkItemStatus.SourceLabel` so the agent context stamps what the board said ("In Progress (open)") rather than replacing an observation with a conclusion, and a card whose category is missing keeps its name verbatim and maps to nothing, which the gate then refuses. **The credential is a reference and the token is checked before it is trusted.** A connection records `env:<VAR>`, `keychain:<SERVICE>`, or `file:<name>` under `~/.hall9k/credentials`; the token never reaches an event payload, and the new `file` kind exists because the other three all point at a credential something else already holds while a token pasted at a prompt is held by nobody yet. `h9k connection add jira` calls `/rest/api/2/myself` before recording anything, so a mistyped site or an account password pasted where an API token belongs is refused while the human is still looking at the command that caused it; registering again replaces the existing connection, because a refusal there would be a dead end with no remove command to send anyone to. API version 2 rather than 3 on purpose: both are current, v3 carries rich text as Atlassian Document Format and v2 as a string, and what is being moved in both directions is text. **One Jira connection per install, said out loud.** Several accounts per provider stay possible in the model, but nothing yet says which of two Jira accounts a given project uses, so a second one is refused by name rather than resolved by taking the oldest. That refusal reaches only the commands that need Jira: the importer is built with GitHub always present and an unusable Jira carried as a deferred refusal, because GitHub needs no connection record and cannot be ambiguous, and a Jira misconfiguration that made `h9k task show` or a `--from-issue` adoption exit non-zero would be a configuration problem in one source breaking a command about another. **What is deferred, and why each one is a policy question rather than a missing feature:** bidirectional status sync (Hall9k is the source of truth for task state and Jira is a mirror surface, the board-as-truth lesson from the Collaboard comparison and the same stance #60 took on GitHub); automatic card creation at publish (which lifecycle event means "created" changes with backlog 05); webhook-driven updates; and Jira Server / Data Center, whose auth is a different scheme and would be half-supported by a header that merely looks the same. **Does this block the later vision?** No. `IWorkItemProvider` gained a second implementation and no new shape, the create half of §9.2's interface is still deliberately unimplemented rather than designed away, and the observation-gate pattern is the reusable part: `h9k learn`, GitHub issue creation, and any other agent-reported fact land as commands that verify before they record.

66. **The board answers four questions with three surfaces** (2026-08-22, backlog 41, absorbing backlog 28): one field was carrying the lifecycle, the live activity, the attention, and the cause, and the owner who helped build it found it confusing, which is the whole finding. Four incidents, all inside a week. Task 17 read **Done** while its pull request was open and follow-up runs were still going, contradicting the platform's own strictest rule, since a blocker counts as met only at true closeout. **ClosingOut** meant two opposite things - watching-and-dispatching-follow-ups, and watching-with-nothing-left-but-the-human's-merge - and Brian had to ask which one PR 24 was in. Task 35 read ClosingOut while a fix session was actively editing its worktree, and the orchestrator nearly rewrote history under a live agent because the board said the lane was quiet. And a red row still arrived with no reason on it, which delegates the investigation to the human it was meant to spare (backlog 28's whole case). The fix is to stop asking one word to answer four questions: **State**, **Phase**, and **Attention**, with a fourth line of derived facts under a Published row.

**Display-first: the persisted model does not change at all** (Brian, 2026-08-22). `TaskState` and `RunState` keep every state and every transition; what changes is what a human is shown. The lifecycle vocabulary becomes **Draft, Published, Working, Delivered, Done, Failed, Archived**. `Queued` and `Blocked` keep their streams and render under **Published**, with the difference moved onto that row's derived-facts line ("not assigned", "assigned and ready; the dispatcher has not claimed it yet", "waiting on 2 dependencies to close out"). That line is an ordered list of facts rather than a sentence precisely so the ranking model's facts (unranked / ranked / expedited, available / held) can join it without a second redesign; the column exists, the facts arrive later, and no unranked-count reporting is built here. When ranking retires Queued and Blocked, one composer changes. **A queued row says it is ready and stops there.** Why the dispatcher has not claimed it yet is a question only a measurement answers, so the slot line is #64's `DispatchPressure` and nothing else: where this node's last sweep reported itself full, the row carries that sweep's numbers, and where no measurement is current it says nothing about slots at all. The first cut asserted a wait on a slot from the state alone, which named contention nobody had observed on the commonest still queue there is, the one behind a stopped daemon (pre-PR review, 2026-08-22). The same measurement is what a pushed follow-up's phase line reads, so the two surfaces cannot disagree about why nothing is moving. **Delivered** is the word for pushed-but-not-closed-out, and **Done** now renders only at true closeout - the merge observed, or the task closed with no pull request to watch at all - which is exactly the bar the dependency rule uses. That second arm is answered before the run is read, because a task closed by hand keeps the run document it was closed on top of: `TaskResolved` does not clear `CurrentRunId`, and reading that leftover run would render a task that never pushed anything as Delivered. A pull request closed without merging is deliberately *not* Done: closeout ended, but not the way Done claims, and the attention line says so. `Abandoned` displays as **Archived** whichever word the stream records, so backlog 33's persisted rename lands without touching the display.

**Phase is derived only, and observes rather than asserts.** The run vocabulary is the phase line's material and never appears in the Status column. Composition is the run's records **plus one observation of the recorded process**, because the liveness half can only ever be observed, never replayed. `RunDetails` therefore records **every** session a run currently has in flight: each one's role (Build, Review, Fix, Synthesis), its lens when it is a review pass, its pid, and its process start time, which together are the identity the log #2 reuse guard needs. A list rather than one slot, because a review cycle dispatches one pass per active track and both read at once (log #59). That is what lets a cycle waiting on its slower track ("review cycle 2, adversarial pending") read differently from a cycle nobody is working, and it is what keeps a healthy cycle from reading as a dead one: the passes exit in whichever order their diffs allow, so a pass that has already finished sits beside one still reading, and a run is reported as having lost its process only when **every** process it records is gone. **A phase never claims a session is doing something without observing the process.** A run on another node, or a resumed session whose event records only a pid, reads as "session liveness not observed here"; a live run state with no recorded session says "no session recorded" rather than reassuring anyone. These are read-model fields over events that already existed, not new events, and they need no backfill: a document written before them carries none of them and therefore reads as no-session-observed, which is the honest answer, while any run still alive rewrites its document on its next event. The two meanings of the old ClosingOut separate here - "follow-up on PR #24: building, session alive" against "watching PR #24 — Copilot review landed" (or awaiting Copilot, or plain "watching PR #24" when nothing has been observed yet, log #89) - so "is it my turn?" never needs a log dive.

**Attention absorbs backlog 28 whole, with one composer owning the mapping.** Needs-you or not is a first-class column; the one-line cause and its lever are the line beneath. `AttentionComposer` is the single owner, so `h9k status` and `h9k task show` cannot disagree about whether a row is asking for something. Every cause is quoted from a record - `ReviewParked.Reason`, `CloseoutParked.Reason`, the dependency-failure record, the recorded failure reason, the observed check and thread counts - and every lever names a command the platform will actually honour, which is why a question asked by an agent points at `h9k task show` and says plainly that no command answers it yet, and a run that ended with no merge observed points at `h9k pr resolve`, whose follow-up run rejoins the closeout monitor's watch set so the merge is finally observed, which is the identical remedy a dependent blocked on that task is already given. The one exception is a pull request the monitor observed closed: a follow-up onto a closed pull request's branch rejoins no watch, so that row points at the pull request itself, and the recorded failure reason is what tells the two apart rather than the run state they share. That row also shows what the run recorded rather than naming a closure: `RunState.Failed` is what *every* run failure records, and a pull request closed without merging (which does record its own reason) is only one way to reach it, so a gate failure the human then resolved onto a pull request is never described as a closure nobody observed. A quiet pull request says what is recorded rather than reporting an all-clear: the monitor does not act on checks or review threads while a check is still reporting, though it still records what it saw of Copilot's review state that same sweep, so silence beyond that recorded observation covers both a pull request with nothing on it and one whose gates have not answered yet, and the row says so and sends the reader to the pull request's own checks. **The needs-you group is where a row that has stopped is counted**, whatever its lifecycle state. Only the awaiting-the-merge row stays counted under Delivered (moving every open pull request out would empty that group on most boards); a parked closeout, a review park and an agent's question on a follow-up all count under needs-you, or the header would report that nothing needed you while work was definitively blocked on a human. **Waiting-but-handled is its own level and renders dim**: a blocker already retried and rebuilding, a pull request the closeout monitor still owns. A board that says "act now" about a handled situation trains its reader to ignore it (log #61's origin incident, restated). **Failed rows compose their cause**: gates are named because `VerificationFailed` names them, a kill is named because `RunKilled` records its reason, and a cause with no distinct record yet - token exhaustion, until backlog 40 lands - is shown as whatever text the machinery wrote rather than sorted into a category nobody observed. A park with no recorded reason says exactly that. `TaskListItem` gains the recorded failure reason for this, because the launch-failure path can fail a task before a run stream exists, and that field is a staleness marker in `TaskLifecycleProjectionBackfill` like every other one (log #34, #61).

**What this costs and what it does not.** The task surfaces stop being Spectre tables: a table has no column span, and the phase and attention lines need the whole console rather than the objective column's share of it, so one shared layout measures and pads the columns and runs the detail lines full width underneath. A settled row is still one line. `h9k status` prints every detail line a row has; `h9k task list` and `h9k project show` print the first one only, which is what keeps them from losing the distinctions the run vocabulary used to carry there - three published tasks that all read Published in the column say "not assigned", "assigned and ready" and "waiting on 2 dependencies to close out" underneath it, and the attention column travels to those surfaces with them. `h9k task show` leads with State, Phase and Attention before the objective and the context mountain, and backlog 36's token lines compose in beside the phase line when they land. The rollup columns follow the same words (Active becomes Working, In review becomes Delivered) and `--state` accepts three vocabularies - attention group, lifecycle state, run state - keeping the old spellings as aliases so an agent's saved command line outlives the rename. **No word belongs to two of them, and where one did, the column wins** (Brian, 2026-08-22): the word a reader types selects the rows whose Status column shows that word, because that is the word they just read off the screen. The vocabulary that loses a word gets a spelling of its own rather than an unreachable entry in `--help`. `RunState.Failed` is selected as `run-failed`, since `Failed` alone is the lifecycle state and means a different thing (a task that failed, rather than a run of it that did); the four attention groups the new lifecycle vocabulary shadowed are `attention-working`, `attention-delivered`, `attention-draft` and `attention-done`, and the fifth, the ready-to-assign group, keeps its own name `ready` and no longer answers to `published`. That restores log #32's rule, which the first cut of this redesign inverted by trying the groups first: an exact filter can never quietly widen, and it can never quietly narrow either - `--state delivered` was returning the Delivered *group* and leaving out the pushed row parked on a question, which the Status column calls Delivered just the same (origin incident: caught by this branch's pre-PR review, 2026-08-22). **Explicitly not done:** any state-machine surgery, backlog 33's persisted rename, backlog 36's token lines, backlog 40's budget outcome, and a "waiting for budget" phase, which nothing records today and which would therefore have to be invented.

67. **A command line that never reached a command teaches with the command's own help** (2026-08-22, SLICE-1 S1-13): the CLI runs with `PropagateExceptions` so domain failures can be mapped to exit codes by hand, and the unnoticed cost of that posture was that Spectre's *own* parse and binding failures had nobody to catch them. Origin incident (2026-08-20): a bare `h9k task publish` answered with `Unhandled exception. Spectre.Console.Cli.CommandRuntimeException` and eight frames of Spectre internals. That is a wall for a human and a dead end for an agent, and it broke the house CLI standard (failures print *why*, quoting the rule) at the one moment the caller most needs teaching, since a caller who mis-shaped the command line has demonstrably not read the help yet. So `Program` catches `CommandAppException` and `UsageError` prints the failure followed by **the offending command's own help**, rendered from the same command tree the binary runs, with the exit code EX_USAGE (64). Quoting the help rather than a hand-written hint is the whole point: there is exactly one description of what a command looks like, so the correction cannot drift from the command, and the caller gets the arguments, the options and a worked example in the same breath as the refusal. The command path is taken from the leading tokens of the failed line and shortened until something renders, so a stray argument still lands on the command that was reached and a misspelling falls back to the root. Three consequences followed. The command tree moved out of `Program.cs` into `CliCommandTree`, because it now has two callers and, more importantly, because a `--help` tree that is a first-class interface should be something tests can walk: `CommandTreeHelpTests` walks the shipped tree and asserts every command and branch carries a description, at least one example, and only examples that invoke the command they document. That test immediately found `h9k logs` shipping with no example at all. The elapsed time is small and beside the point: the standard became law on 2026-08-17 and `h9k logs` was written the day before it, so the command never passed under the new rule and five days of unrelated work went by without anything re-reading the tree against it. That is the argument for enforcing a standard rather than remembering it, because a gap nothing checks is not one that decays on a schedule; it is one nothing was ever going to look at again. Second, examples are now written with their multi-word values quoted, because Spectre renders an example verbatim and `--objective Add the browse surface` is not a command anyone can paste; an example that is printed back at an agent as a correction has to be runnable as printed. Third, the root `EXAMPLES` block is stated rather than inherited: left alone Spectre fills it with whatever registration order put first, and the first thing anyone reads should be the orchestrator's loop. **Does this block the later vision?** No. It is display and diagnosis over the existing model, and it generalises: any surface that refuses an agent should hand back the thing the agent needs to self-correct, which is the same principle #65's observation gates apply to writes.

69. **Adoption wins outright, and a run's generation fences every task-level write it drives** (2026-08-22, backlog 39): catch-up's own order (#7 — adopt, then sweep, then claim) turned out not to be enough by itself. Origin incident (2026-08-21 evening, twice observed): after a sleep-through-restart, catch-up both adopted the detached runs of tasks 18 and 35 AND requeued the same tasks' expired leases, because adoption resumed three of its four cases (`Verifying`, `UnderReview`, and `Dispatched`/`Running` with a result already on disk) without ever touching the lease, so the sweep one line later still saw a stale heartbeat and requeued the task out from under the very run adoption had just reattached. Both generations then ran full two-lens review cycles in parallel in the same worktree — roughly eight concurrent Opus sessions of duplicate work — and the stale generation's lane spent its fix budget, parked, and its park/fail path wrote the task Failed while the live generation's fix session was still mid-flight; the dependent's crying-wolf hold (#61) re-armed off the lie. **Adoption now refreshes the lease for every case it adopts**, not only the review-parked one: `RunSupervisor.AdoptOrphansAsync` calls the same `RefreshAdoptedLeaseAsync` (generalised from the review-park-only helper) before `ResumePipeline` or `StartMonitoring` returns control, so the heartbeat the sweep reads one line later is already current and the task is never requeued out from under a run adoption just reattached. That closes the double-booking gap, but PLAN.md's own decision #7 promised a second guarantee this fix found unimplemented: **"any state change from a stale-generation run is discarded."** `LeaseGeneration` was already a fencing token on both `TaskAggregate` and `RunAggregate` — stamped once at dispatch, bumped by every claim, monotonic across a requeue — but nothing compared a run's generation to its task's before a run-driven write landed. `RunSuperseded`'s own doc comment said "this run's further output is discarded" and nothing read the field. **Corrected by #67 (2026-08-23):** comparing `LeaseGeneration` directly, as first shipped, had a gap of its own — the generation is bumped only by a claim and deliberately survives a requeue, retry, or reopen, so between one of those and the next claim the task sits at its old generation with no current run at all, and a late write from the run that generation used to belong to would pass a generation-only check in exactly that gap. #67 replaced the comparison with the task's `CurrentRunId`, which has no such gap, and closed the narrower read-then-write race described below with `expectedVersion`. So every task-level state transition a run drives — review parked, run failed, pushed, closed out (the five call sites: `RunSupervisor.AppendFencedTaskFailureAsync` and `ParkedOnThreadDisputeAsync`, `ReviewEngine.FailAsync` and `ParkAsync`, `VerificationRunner.FailBeforeGatesAsync` and `RecordFailureAsync`, `PullRequestOpener.OpenAsync` and `RecordFailureAsync`, `RunLauncher.TryCloseOutMergedPullRequestAsync` and `RecordLaunchFailureAsync`) — now checks `GenerationFence.AllowsAsync` immediately before the task-stream append: current generation, write proceeds; stale, the write is skipped, the task's lease is left untouched (a stale lane's failure must not release the live lane's lease), and one line is logged naming both generations — "run at generation 2 attempted TaskFailed; task is at generation 3 - rejected" — so an operator watching the log can see the stale lane die instead of the board silently lying. The run's OWN stream still records its own honest fact regardless of generation (a `RunFailed` for a session that really did die is true whichever generation it ran at); only the *task*-level write is fenced, because the task is the shared thing two generations can disagree about and the run is not. `ReviewEngine.DriveAsync` additionally checks the fence at the top of every loop iteration, before the phase switch decides what to dispatch next: a stale generation stops there, at the first check, rather than burning further review or fix cycles into a worktree the live generation now owns — closing the other half of the origin incident, where the stale lane's own sessions kept running to completion before anything noticed. The two mechanisms are complementary rather than redundant: the loop-level check stops wasted dispatch (`ReviewDispatched`/`ReviewFixDispatched` are run-stream events with no task-level write to fence), while the per-write fence is what actually makes decision #7's "discarded" promise true, since a generation can go stale in the minutes between a loop iteration's check and the write a long-running session's result triggers. **Does this block the later vision?** No: the fencing token was already load-bearing for #38-#58's P2P design (a node/edge whose write arrives after a fresher claim is exactly the same shape as a stale generation on one machine), and closing the gap here is what makes that design's safety argument actually hold rather than assume.

70. **The generation fence compares identity, not a number, and its write is version-reserved** (2026-08-23, backlog 39 follow-up, an independent review of #69's PR): the fence #69 shipped had two gaps of its own, both found by review before merge rather than in production, and both fixed the same way #69's own doctrine demanded — a stale lane discarded, never absorbed. **The comparison gap:** `GenerationFence.AllowsAsync` compared `task.LeaseGeneration == runGeneration`, and the generation is bumped only by a claim, deliberately surviving a requeue, retry, or reopen (#69's own account of why). Between one of those and the next claim, the task sits at its old generation with `CurrentRunId` null — Queued, waiting to be reclaimed, not Claimed by anyone. A run whose generation happened to still match passed the old check in that gap, and `TaskDecider.CanFail` accepts `Queued`, so a late write from the very generation that had just been requeued could still flip the task to `Failed` before a fresh claim ever landed. The fence now compares `task.CurrentRunId == runId` instead: identity has no such gap, because no run's id ever equals `null`. **The write gap:** `AllowsAsync` was always a read-only check with no reservation through the caller's subsequent write — a fresh claim could commit between the check and the caller's `SaveChangesAsync`, and an unversioned append would land on top of it regardless of what the check said. `GenerationFence.LoadFencedAsync` now reads the task aggregate pinned to the stream version observed at that moment, and every task-level append that follows fences on `expectedVersion: version + 1`, catching `EventStreamUnexpectedMaxEventIdException` as the same "lost the generation race" outcome the identity check already logs. The run's own stream is deliberately left out of that reservation: an earlier version of this fix ran the task-level write in its own transaction so a lost race would never roll back the run's honest failure record, but that opened a worse hole — a window where a reader could observe the run `Failed` while its task still read `Claimed`, caught by an existing regression test. Losing the run-stream fact too, on the rare lost race, is the smaller cost; every fenced write is back to one atomic commit. **Three more gaps, same doctrine, applied where #69 had not yet reached:** `RunLauncher.LaunchAsync` checked the fence only on the already-merged-PR path, so a stale launch with no PR yet, or an unmerged one, fell through to a fresh checkout and spawn — a second live agent for one task. The fence now gates the whole method, before any checkout. `RunSupervisor.AdoptOrphansAsync` recovered every non-terminal candidate for a node without checking which run a task's `CurrentRunId` actually named, so a reclaim that landed while the daemon was down could leave two non-terminal runs for one task and adopt both; it now retires (terminates the process if still alive, appends `RunSuperseded`) any run that is not its task's current one instead of resuming it. `ReviewEngine.DriveAsync` checked the fence once per while-loop iteration, but one iteration dispatches every active lens plus the reprompt and fix helpers — several spawns a reclaim could land in between; the fence is now checked immediately before each `executor.SpawnAsync`, and a rejection — loop-level or per-spawn — retires the run with `RunSuperseded` rather than merely unwinding the call stack, so it drops out of `NodeLoad` and every later non-terminal query instead of sitting live for a sweep to relaunch. **Does this block the later vision?** No, for the same reason #69 gave: this hardens the same token #38-#58's P2P design already leans on.

71. **`AllowsAsync` must read no earlier than `LoadFencedAsync`, or the identity check is answering about a task that has already moved on** (2026-08-23, backlog 39 follow-up, found by adversarial pre-PR review of #70's own PR): of the ten methods #69/#70's five call sites named, six actually append a task-level event guarded by `expectedVersion` — `ReviewEngine.FailAsync`, `VerificationRunner.FailBeforeGatesAsync` and `RecordFailureAsync`, `PullRequestOpener.OpenAsync` and `RecordFailureAsync`, `RunLauncher.RecordLaunchFailureAsync` — and all six called `GenerationFence.AllowsAsync` first and `GenerationFence.LoadFencedAsync` second, then used the aggregate `LoadFencedAsync` returned without asking it about identity again. (The other four never reach a task-level append at all: `ParkAsync` and `ParkedOnThreadDisputeAsync` only ever write to the run's own stream, so there is nothing for a stale ownership check to protect.) A reclaim landing between the two reads is invisible to that ordering: `AllowsAsync` saw the old, still-matching `CurrentRunId` before the reclaim committed, and `LoadFencedAsync`'s later read — now reflecting the reclaim — became the `expectedVersion` baseline for the write, so the optimistic-concurrency guard has nothing left to catch. `TaskDecider.CanFail`/`CanComplete`-style checks only look at state, not ownership, so the stale write lands on the live generation's task, the exact double-booking #69 exists to prevent, reproduced through a narrower window than either #69 or #70 closed. Two sites in the same diff already had this right and are why the gap was narrow rather than universal: `RunSupervisor.AppendFencedTaskFailureAsync` loads the aggregate first and checks `AllowsAsync` last, immediately before the write; `RunLauncher.TryCloseOutMergedPullRequestAsync` checks `AllowsAsync` first but re-checks `current.Task.CurrentRunId != runId` explicitly after `LoadFencedAsync`, catching the same gap a different way. The six sites now match the first shape: `LoadFencedAsync` runs first, and `AllowsAsync` is the last check evaluated before its result is used, so a reclaim in the gap is caught by `AllowsAsync`'s own fresh read; a reclaim after that is still caught by `expectedVersion`, as before. **Does this block the later vision?** No, for the same reason #69 and #70 gave: read-then-write ordering discipline around a fencing token is exactly what a P2P node applying a remote write out of order will also need.

72. **The closeout sweep also inspects Delivered rows nothing is watching, and dates what it observes rather than what it finds** (2026-08-23): the three-surface board (#66) rendered six Delivered rows honestly as "the run ended without a merge being observed, and nothing is watching this pull request any more" — every one a pre-closeout-monitor task whose pull request had in fact merged by hand, days earlier, verified on GitHub. 73. **The connection-string precedence is env var, then the platform config file, then a per-project override — checked in that order, deliberately least-committing first** (2026-08-23, backlog 24, resolving §15 row 29): #57 said Hall9k needs a connection string and takes no position on where Postgres runs; this is where that string actually lives. 74. **A doctor check diagnoses the database, and it is the same check forever** (2026-08-23, backlog 24, extending #58's teaching-not-guessing principle from install to every later moment — database moved, container stopped, credentials rotated, laptop reimaged): four questions, answered in order, stopping at the first one that fails. (1) Is a connection string configured at all — reads #73's precedence chain and, only here, says nothing else has been checked yet. (2) Is it reachable — a raw Npgsql connection attempt distinguishes `RefusedConnection` (nothing listening) from `AuthenticationFailed` (reached it, credentials rejected) from `DatabaseMissing` (reached it, authenticated, wrong database name), because Npgsql's own `PostgresException.SqlState` already carries that distinction and conflating them was the one sin #58 named by name. (3) Is the schema there — checked against `to_regclass('public.mt_streams')`, and answered as an offer rather than a warning, because Marten's `AutoCreate.CreateOnly` (every store in this platform already opens with it) creates it on first real use regardless; the offer just does that on the spot instead of the next command eating the latency. (4) Only reached when (1) failed: what is available — a running container runtime, a native Postgres already on 5432 (a bare TCP connect, honest that it cannot tell Postgres apart from anything else on the port), and, the nicest possible finding, a **stopped** `hall9k-postgres` container from a previous session, because "your database exists, it is just not running" is a one-line fix and worth surfacing ahead of "go get Postgres." Question 4's container probe speaks Docker's CLI specifically (`docker info`, `docker ps`), while #57 keeps Podman, Apple's container framework, and a native install equally valid Postgres hosts the same as always — the probe covers the one runtime with a scriptable CLI convention worth automating; the others fall out through "point HALL9K_CONNECTION_STRING at whatever you already run." Every branch is a raw Npgsql connection attempt or a `docker` shell-out — no Wolverine host, no Marten codegen beyond the one schema-creation offer — so it survives the thin-CLI rule (#8) even run before every database-touching command. It lives in `Hall9k.Cli`, never the daemon, for exactly that reason: it has to work while the daemon is down. `h9k doctor` runs it on demand; `Program`'s top-level catch runs it — offering no fixes, since a command mid-failure is not the moment to start Docker underneath it — the instant any command's `NpgsqlException` or missing-configuration refusal reaches it, so the first raw failure a caller sees is already the diagnosis rather than a driver stack trace.

**The offer is offer-never-force, the same shape as the auto-assign prompt at publish**, and it is where `h9k daemon start` stops printing a lie: origin incident (2026-08-21), a post-restart `daemon start` printed `h9kd started (pid N)` and then, moments later, "exited during startup" with an Npgsql stack trace, because Postgres was not back up yet — a claim that had to be retracted before the human finished reading it. `DaemonLifecycle.StartAsync` now runs the same doctor check **before** the log rotation, the detach, and the "started" line, so an unreachable database refuses to spawn `h9kd` at all rather than spawning it and reporting the death after. When the probe finds nothing listening, a container runtime running, and the host:port looks like the local default (`localhost:5432`, the one case Docker starting anything could plausibly fix), it asks — "Found a stopped hall9k-postgres container… start it now via Docker?" or "Postgres isn't running. Start it now via Docker?" — waits for readiness by polling the same raw connection attempt, and only then continues into daemon startup. A non-interactive invocation (`AnsiConsole.Profile.Capabilities.Interactive` false, a script or a dispatched agent) gets today's behavior: a named fix and a refusal, never a prompt nobody is there to answer. `h9k doctor` offers the identical action for the identical reason — the same check, run on demand instead of triggered by a failure.

**The offer starts platform-owned infrastructure, and install stays boring anyway.** `h9k install` writes Hall9k's own Postgres definition — a `docker-compose.yml` mirroring the repository's own, embedded in the binary — to `~/.hall9k/postgres/docker-compose.yml` on every publish-and-refresh (a local edit there is lost the next republish, deliberately: it is not a supported customization surface). Nothing is started and nothing is prompted for at install time; only the file lands, so `h9k daemon start`'s offer and `h9k doctor`'s offer never need a repo checkout to act on — the thing #58 flagged as missing (an installed user has no dev worktree to run `docker compose` from). The doctor's own start-offer writes the same file as a belt-and-suspenders fallback for a CLI used straight off a dev build, without ever running `h9k install`.

**Resolves §15 row 28: the two Postgres provisioning paths stay deliberately separate.** The Aspire AppHost (`dotnet run --project src/Hall9k.AppHost`) manages its own Postgres container for the dev loop through Aspire's own APIs and injects a connection string directly into the daemon's configuration (`builder.Configuration.GetConnectionString("hall9k")`), which `Hall9kDatabase.Resolve`'s `configured` parameter treats as outranking even the environment variable — Aspire's wiring is a fourth, dev-loop-only channel, never one of the three precedence homes documented above. `h9k daemon start`, `h9k doctor`, and `h9k install`'s shipped compose file are installed mode's own path and never touch Aspire's container or vice versa; the two paths already bind the same port on purpose (so the default connection string works unmodified against either), which is why `docs/operations.md` says to run one at a time rather than the platform trying to reconcile them.

**Deliberately left for a refinement pass, named rather than silently skipped:** the symmetry question raised alongside this task — does `h9k daemon stop` offer to stop a container the start-offer started? A compose container outlives the daemon, and "what the offer starts, the mirror command should be able to end" is a real design obligation this task does not close, because it needs the daemon to record *that* an offer started the container (versus finding it already running) before `stop` can decide whether stopping it is its call to make. **Does this block the later vision?** No. The precedence chain, the container-name convention, and the shipped compose file are exactly the seams a stop-side mirror or a P2P-era per-node Postgres would build against.

75. **A gate failure that carries a connection-class signature retries once, in place, before the run believes the agent's work is broken** (2026-08-23, backlog 53, origin incident: task 40's follow-up failed gate 'test' twice in one afternoon, both times the Testcontainers Postgres dying or losing its connection under the suite while the agent's actual work was fine): `VerificationRunner`'s gate loop previously treated every non-zero exit identically, so a container hiccup and a genuinely broken build cost the same thing — a failed run, a failed task, and a human's diagnosis. `GateInfrastructureFailureClassifier` applies the never-guess rule exactly as backlog 40 applied it to budget exhaustion: a fixed, narrow set of literal markers (Npgsql connection refused/reset/timeout exception types, "Exception while reading from stream", "Failed to connect to", the SSLRequest handshake mismatch, Testcontainers/Docker API failures) — nothing fuzzier, so a test's own assertion output never qualifies by coincidence. A gate whose failure classifies as infrastructure is retried once, in place: a new `GateRetried` event records the gate and the cause on the run stream before the retry runs, so the record says the flake happened whichever way the retry goes, and the run is never failed nor is any budget spent on a flake the retry absorbs. 76. **Every project owns a home directory, created by a recipe rather than an agent** (2026-08-23, backlog 47, absorbing backlog 43; slice 1 of the project-centred structure, idea 64e4ebd2): a project's files were scattered by convention rather than laid out by contract - the repository wherever it was cloned, ideas under a global `~/.hall9k/ideas`, runs under a global `~/.hall9k/runs`, and nothing at all tying them to the project they belong to. There is deliberately **no top-level `runs/`**: a run belongs to exactly one task, so it lands under that task's directory and the task directory is the task's whole story (ruled during task refinement of backlog 49, which supersedes the six-entry list backlog 47's own criteria were written from). **Creating it is platform code end to end** - the installation sitting's words, restated at this discovery: "this is a recipe, not an agent". Directories, bare clone, refspec correction, worktree, skill seeding and render are all deterministic, so `h9k project add` does them at registration and `h9k project init` is the adopt-and-repair path for a project without a home. Agents are reserved for the two judgment moments the discovery named: one-time migration of a nonconforming project, and configuration-laden tracker authoring. Neither is setup. **`repo/` absorbs backlog 43's recipe wholesale**, including the step that is the whole point of it: `git clone --bare` writes `+refs/heads/*:refs/heads/*`, mapping every remote branch onto a *local* branch, so a worktree cut from it has no upstream and `origin/main` does not exist to branch `--no-track` from. The refspec is corrected to `+refs/heads/*:refs/remotes/origin/*`, the local branches the bare clone invented are deleted, `core.longpaths` is set on Windows, and a failed clone names `gh auth login` / `gh auth setup-git` rather than leaving an operator to guess. Every step is idempotent: an existing clone is reported and left alone, a missing `dev/` beside one is repaired rather than treated as a reason to start over. **Init always materialises fresh from the recorded remote**, and an existing clone elsewhere on the machine is inconsequential - git is distributed, including across one disk - so the recipe never adopts one in place; once the clone is real the project is re-pointed at it, loudly, because a `repo/` nothing dispatches against is decoration. Moving live work out of an old location stays the cutover chore's agent-assisted job (backlog 52), which `--keep-repo-path` exists to defer to. **The generated `AGENTS.md` is a render, never a hand-maintained file** - the same one-way-render ruling the task and idea files get (backlog 48). It names the layout, points at the repository's own `AGENTS.md` as the deep layer rather than restating it, and lists the tool dependencies *derived from the project's bindings*: `h9k` and `git` always, `gh` when the remote is GitHub, the Atlassian CLI when a Jira board is bound. A project's `skills/` entries are **symlinks into that directory** and `.claude/skills/` is a second layer of symlinks into `skills/`, so republishing the install updates every project's platform skills in one move, a project-specific skill is a real directory that re-seeding never touches, and there is never a second copy of a skill's content to drift. Side-by-side duplicate content directories were rejected outright at the discovery: two copies that can drift means one of them is lying. **The dispatcher composes the home into the briefing.** When a task's project has a home, `AgentPromptBuilder` names it, its generated `AGENTS.md`, its `skills/` (each with its frontmatter description) and its `tasks/`, `ideas/` and `repo/` alongside the repo skills `DiscoverRepoSkills` already hands over; a repo skill of the same name wins, because the repo tier is the more specific one. That is the discovery's dispatch-composition ruling: a dispatched agent never hunts for context. It is also what makes the generic `skills/` genuinely model-agnostic - "read this file first" is the one instruction every runtime understands, so nothing depends on any vendor's directory-walking behaviour, and native discovery in the home stays a nicety for interactive sessions rather than a load-bearing assumption. **Does this block the later vision?** No, and it is the bridge to it: the home is the boundary a from-anywhere session navigates into, the place the task and idea renders (backlog 48) and the relocated runs (backlog 49) will land, and the unit a project-move or a shared-room migration operates on. The P2P layer's lazy, claim-triggered materialisation (#45, §15 row 20) is unaffected - it now has an explicit sibling to be the eager half of, and one place that already knows what a materialised project looks like.

80. **The closeout budget counts stalled repetition, not raw laps, and a human's own engagement buys a lap the counter would otherwise refuse** (2026-08-23, backlog 45): the flat `MaxAutomaticCloseoutRuns` (#22) conflated distinct causes under one counter — task 18's budget of 2 went one lap to review threads and one to an unrelated CI flake, so a fresh, deliberate Copilot re-request Brian made by hand on PR 26 had no budget left despite nothing having looped. Two counters now do what one used to. `TaskAggregate.LastAutomaticObstructionKey` and `ConsecutiveObstructionLaps` are the progress cap (`DaemonOptions.MaxCloseoutLapsPerObstruction`, default 2): a check obstruction keys on its check name, a review obstruction keys on the exact set of unresolved thread ids present at dispatch (mechanical identity, never judged — two different check names, or two different thread-id sets, are two different obstructions), and a lap whose obstruction key matches the task's last one increments the count while a changed key restarts it at 1. `CloseoutAttempts` keeps its old job as the absolute lifetime ceiling (renamed in spirit rather than in code, default raised 2 → 6): the true runaway backstop for a busy pull request that legitimately grinds through many DIFFERENT obstructions, checked first and unconditionally — nothing bypasses it except `h9k pr resolve`. The walk's own framing was "the home directory only ever holds what the install wrote", true on the dedicated test machine the walk describes but not true in general: `docs/operations.md`'s own disk layout shows `projects/<name>/` (a project's bare clone and worktrees, `repo/dev` included), `credentials/`, and the global `ideas/`/`runs/` fallback directories all living directly under `~/.hall9k`, as siblings of `bin/` and `config.json` — so a literal recursive delete of the home would take a project's uncommitted worktree changes and a registered Jira token with it, which is precisely the "taking the work with it" this command exists not to do. `UninstallCommand.InstallOwnedEntries` names exactly what install writes instead — `bin/`, `bin.staging/`, `bin.old` and any `bin.old.<random>` fallback, `postgres/`, the daemon's `h9kd.log`/`.log.1`/`.pid`/`.lock`, its `h9kd.stop`/`.stop.claimed` graceful-stop request pair (#85), and Windows's `h9kd-autostart-launch.vbs` launcher — built from literal relative names rather than by calling `DaemonRuntime`/`Hall9kDatabase`/`PostgresRuntime` directly, since those resolve against the live `PlatformPaths.Home` a test must not touch. `config.json` is deliberately not one of these: install never writes it, an operator or `h9k doctor`'s start-offer does, and it can be the only record of a hand-configured connection string, so deleting it would leave a reinstall silently pointed at nothing rather than reconnecting to the database the operator set up (found by this feature's own pre-PR review, cycle 2). When the daemon could not be confirmed stopped, none of this list is touched at all — not just the pid and lock files — because bin/ and the PATH link have to survive for `h9k uninstall` to be re-runnable, and Postgres has to survive untouched because a daemon still running may still be writing to it (the same review cycle: stopping or purging the container out from under an unconfirmed-stopped daemon risked the very in-flight appends the daemon's own stop budget exists to protect). The canonical skill set is deliberately not one of these literal entries: unlike everything else install writes, an operator can and does write skills of their own straight into that same `skills/` directory, so removing it takes the identical name-and-content-hash discipline `SkillSeeder.PublishCanonical` already applies to its own retiring pass (`SkillSeeder.RemovePublished`), never a blind delete of the directory; `RemoveInstallOwnedEntries` deletes file by file within each entry rather than in one recursive call, so a single locked file (typically the running `h9k.exe` itself, mid-uninstall on Windows) costs exactly that file, named rather than silently dropped, and `TryRemoveIfEmpty` deletes `~/.hall9k` itself only once it is genuinely empty — which is what "a removed home is a removed home" means for the machine the walk actually describes, without extending the same claim to a machine that has also registered a project. Everything else in the command is the split #78 already drew between the binary and the data: stops a running daemon through `DaemonLifecycle.StopAsync` on every platform — autostart-aware on macOS/Linux, and on Windows the `DaemonRuntime.StopRequestFile`/`WindowsStopRequestWatcher` graceful-stop pair #85 landed in this same branch, never a direct `Process.Kill` (an earlier draft of this command did force-kill on Windows, before #85's graceful path existed to route through; that was corrected before this branch shipped) — unregisters autostart (`IDaemonAutostart.DisableAsync`), and removes the PATH link (the reverse search of `InstallCommand.LinkOntoPath` on Unix — every candidate directory, delete only a symlink resolving to exactly the installed binary; the reverse of `EnsureOnWindowsPath` through the same `HKCU\Environment` registry seam on Windows). The `hall9k-postgres` container is stopped (`docker stop`) and left alone otherwise: its data volume (`PostgresRuntime.VolumeName`, newly split out from `ComposeFileContents` so the purge path can name it without depending on the compose file uninstall is about to delete, and pinned there with an explicit compose `name:` so the volume Docker actually creates is that literal string rather than whatever project-name prefix Compose would otherwise have guessed from the invoking working directory) is never touched, so a later `h9k install` finds the same database `h9k doctor`'s existing detect-and-start flow already knows how to reconnect to — no new provisioning path, the one #73 built already covers the post-uninstall state. `--purge-data` is the only path that runs `docker rm -f` and `docker volume rm`, and it asks before touching anything (before the daemon is even stopped), refusing outright in a non-interactive session unless `--yes` is also given. It names the volume by asking the container itself (`docker inspect`) what it actually has mounted rather than assuming the pinned literal: a container created before this branch's compose `name:` pin (or brought up from a checkout whose own `docker-compose.yml` was never pinned) mounts a Compose-project-prefixed name instead, e.g. `postgres_hall9k-pgdata`, and guessing the bare literal would either miss that real volume or, worse, hit an unrelated volume that happens to carry the guessed name (found by this feature's own pre-PR review, cycle 2, against the Aspire dev loop's pre-migration volume of the identical literal name) — the same teach-and-ask-never-guess-or-force posture #58 and #78 already hold for install, applied to the one command capable of destroying rather than merely moving work. A purge that Docker cannot actually carry out (unreachable, or a volume it refuses to drop) is reported as incomplete and ends the command with a nonzero exit — never a quiet claim of destruction that did not happen. The final summary and the command's own `--help` both name the two tiers explicitly (machine-local install artifacts, always removed; Docker-resident data, survives unless `--purge-data` said otherwise), and `docs/INSTALL.md` gained the uninstall section this decision describes. **Does this block the later vision?** No: the split this formalizes (install-artifact-is-disposable, registered-work-is-durable) is the same one a P2P node's own local cache versus its shared state will need to draw.

85. **Windows runs the daemon lifecycle as a standalone node — S1-14's `IProcessManager` half, a Task Scheduler logon task, never a service** (2026-08-25, SLICE-1.md S1-14, depends on #59/#82): the gap decision #78 recorded honestly (delivery landed via backlog 42; `h9k daemon start`/`stop`/`autostart enable` still refused on Windows) is closed by this task, deliberately without the S1-14 end-to-end walk itself — that stays Brian's own acceptance step on real hardware once a release exists (§16 is a record of what shipped, not a substitute for the machine that proves it). `IProcessManager` gained a `Spawn` member — every OS-specific detail (`IsAlive`, `Terminate`'s kill-tree) turned out to have none, since `Process.GetProcessById`/`StartTime`/`Kill(entireProcessTree: true)` already behave identically cross-platform, so only `Spawn` differs and only it is virtual (`ProcessManagerBase`). `UnixProcessManager` keeps the `/bin/sh -c "exec ..."` trick (the returned pid IS the real command for its whole life, image-replaced in place); `WindowsProcessManager` has no `exec` equivalent, so it spawns through `cmd.exe /c "..."` instead and returns cmd's own pid — cmd blocks on `/c` until the real command exits, so liveness tracks the real command's lifetime exactly, and kill-tree takes both together. It is also written so a reviewer's own verbatim echo of it cannot manufacture a "named" finding (cycle-4 conformance finding): the sentence naming a file-shaped location and the sentence using defect vocabulary are kept in separate paragraphs, since `ReviewVerdictValidation.NamesAFinding` reads the two sharing a sentence as a stated defect (Decisions Log #86's origin gap), and `NamesAFinding` gained a `priorRulingReasons` parameter so a reviewer's echo of a human's own merge-ready `--reason` text is stripped the same way an echoed objective or acceptance criterion already is. The strip is deliberately restricted to merge-ready rulings: a merge-ready reason is a dismissal the prompt tells the reviewer not to re-raise, so removing its echo is correct, but a needs-fixes reason describes a human-confirmed defect the same prompt asks the reviewer to re-verify and re-raise if unfixed, and stripping its defect vocabulary erased exactly that re-raise, letting a still-unfixed confirmed defect be rewritten into a hollow verdict that parked a run instead of dispatching its fix. `h9k review resolve`'s `--merge-ready` gained an optional `--reason <TEXT>` (previously only `--needs-fixes <reason>` could carry one) — a human dismissing a finding as a false positive can now say why, e.g. the evidence that dismissed it, and have that reach the next fresh-context pass instead of vanishing the moment the park cleared; `--reason` is refused alongside `--needs-fixes`, which already carries its reason as its own argument. **Does this block the later vision?** No: this rides on the existing per-run review-loop event stream and an existing task→runs query shape, with no dependency on which node dispatches the review or where the run lives.

89. **The Delivered state is observable and driven: a pull request opening logs a structural wake hook, and a post-PR watcher reads Copilot's review state so the Delivered phase and attention lines can tell "awaiting Copilot" from "awaiting you"** (2026-08-26, origin: PR #50 sat Delivered for 23 minutes with a landed Copilot review nobody had read before the merge — the only PR-open log line was prose with nothing structural to key on, and the board gave no sign whether the silence between PR-open and merge meant Copilot was still working or the human was). `DaemonLogEvents` (`Hall9k.Daemon`) gives `PullRequestOpener` two EventIds instead of one shared, reworded log line: `PullRequestOpened` (2001) fires only when a PR URL exists to log, and the non-GitHub-origin arm — a branch pushed with no PR to watch — fires the distinct `BranchPushedWithNoPullRequest` (2002), so a monitor keyed on 2001 expecting a PR URL never wakes for a push that carries none. `CloseoutEngine`'s existing sweep gained no new remote call: `latestReviews`, `reviewRequests`, and `reviewThreads` were already in `GitHubPullRequestInspector`'s GraphQL payload, so reading Copilot's review state off them and appending the run-stream-only, informational `ExternalReviewObserved` event (never a `RunState` transition, deduped so a quiet PR does not grow one event per sweep) cost nothing extra. The read is five-valued — `Landed` (a real, non-errored Copilot review sits on the current head commit, confirmed only when both the review's own commit and the pull request's head commit were actually reported by the provider; either one unreported is not guessed at in either direction, independent pre-PR review, cycle 7), `RequestedPending` (Copilot is currently asked and has not answered), `Stale` (a real, non-errored Copilot review sits on a commit confirmed to no longer be the head, and nothing is currently asking it to look again — a countersign re-request recreates the pending request while the stale review still sits in `latestReviews`, which is what reads as `RequestedPending` instead of `Stale` in that window; independent pre-PR review, cycle 6, corrected the original three-valued design here, which had the superseded review falling through to `None` and telling a reader Copilot never looked at all), `None` (none of the above), or `Unknown` (no confirmed review activity) — and `TaskPhaseComposer.AwaitingReviewPhase`/`AttentionComposer.AwaitingReviewAttention` both switch on all five, so `h9k status` prints the same read on the phase line and the cause line beneath it rather than the old single "waiting on your merge" that used to cover every AwaitingReview row regardless of what was actually known. Two restraint corrections landed inside this same decision, both caught by independent pre-PR review: `Unknown` — a run recorded before this observation existed, a sweep that has not landed yet, *or* (independent pre-PR review, cycle 9) a sweep that read a real Copilot review whose own commit or whose pull request's head commit went unreported, so the review could not be compared at all — carries strictly less information than `None` (a sweep that looked and found nothing), so it reads exactly as conservatively as `None` does rather than keeping the pre-existing line's "waiting on your merge" claim — asserting the human is the last gate while CI may still be reporting is precisely the all-clear `None`'s own comment already refuses to make, and `Unknown` has even less grounds for it; critically, `Unknown` never claims *nothing was recorded* either, since a sweep that saw an unclassifiable review recorded exactly that. And `GitHubPullRequestInspector`'s `CopilotReviewThreadCount` is scoped to the threads the *currently-landed* review itself opened (matched by GraphQL review id, not just Copilot authorship), not every thread Copilot has ever opened across the PR's whole history — without the scoping, a countersigned re-review that landed clean on a fresh commit still reported the thread count from an earlier, already-resolved review nobody asked about any more. `AttentionComposer.AwaitingReviewAttention` renders `RequestedPending` as waiting-but-handled (Copilot has not answered, so it is not the human's turn) and `Landed` as needs-you naming Copilot's review directly, so the cause line never again contradicts the phase line printed one row above it. **Does this block the later vision?** No: the observation is a read-only sweep over an existing remote call, gated behind the same run-stream fencing every other closeout append already uses, with no dependency on which node runs the sweep.

90. **A fix session dispatched over the same findings an earlier fix round already tried resolves the review role's model instead of the fix role's, and de-escalation is automatic once the repeated findings clear** (2026-08-26, origin: task 60 generation 2's Sonnet fix session responded to the UnixProcessManager.Spawn start-time race by restructuring the flaky test rather than fixing Spawn — the gate caught it because three sibling parity tests hit the same race, costing a full extra generation; ruled with Brian rather than moving every build to Opus, which stays parked pending post-chain measurement per the review-optimization chain, #86-#88): `ReviewFixEscalation.Reason` (`Hall9k.Daemon.Review`) is the trigger, conservative by design — a location match via the existing `ReviewFindingLocations.SamePlace` comparator, or the human's own `h9k review resolve --needs-fixes` reason literally naming a previous round's location, either one enough; when in doubt it returns null, since a false negative costs one more cheap round and a false positive silently inflates quota burn. `RunAggregate` gained `LastFixRoundFindingLocations`, `LastFixRoundCycle`, and `LastFixRoundHumanFindings`, recording the most recent automated-findings fix round's own findings rather than the whole run's history — not necessarily the immediately preceding round, since a human-findings round advances the cycle without replacing this list and so can leave it lagging by more than one round — which is what makes de-escalation automatic: a round whose findings clear that set simply stops matching the next comparison, with no separate reset. **The escalation only takes effect when the review and fix roles actually resolve to different models**: `ReviewEngine.DispatchFixSessionAsync` requires `reviewModel != fixModel` alongside `ReviewFixEscalation.Reason` returning non-null before setting `Escalated`, so a default install that has never set `--model-review`/`--model-fix` (#82), or a task carrying a `--model` override that covers both roles the same way, resolves the two identically — a repeated-findings round there dispatches on the ordinary fix model exactly as it would have anyway, `ReviewFixDispatched` records `Escalated: false`, and nothing on `h9k task show` or the daemon log distinguishes that round from an unrepeated one. A mechanical redispatch of the very same round (a budget-exhaustion retry re-enters `FixNeeded` with the cycle and `PendingHumanFindings` both unchanged) reuses the round's already-decided outcome instead of asking the question again over content that has not changed; the pairing with `PendingHumanFindings`, not the cycle number alone, is what tells that apart from a human granting a genuinely fresh round at the same cycle (resolving a dispute with new guidance), which does get a fresh evaluation. `ReviewFixDispatched` gained `Escalated`/`EscalationReason`, threaded onto `RunDetails` (`h9k task show` prints a "Fix escalation" line while the newest run's most recent fix dispatch is escalated) and into `ReviewEngine.DispatchFixSessionAsync`'s own dispatch log line. **Does this block the later vision?** No: this narrows `ReviewEngine.DispatchFixSessionAsync`'s existing role-resolution call from an unconditional `AgentRole.Fix` to a conditional one, with no dependency on which node dispatches the fix session or where the run lives.

91. **A daemon-dispatched session never strands its work behind background execution: the dispatch prompt forbids it, and the pre-gate stage now catches a session that ends with committed work but a still-dirty worktree, not only one that commits nothing at all** (2026-08-27, backlog 57, extends #28(d), origin incidents both 2026-08-26: PR #53's follow-up cycle-3 fix round left eight files modified but uncommitted, caught only by the next review pass instead of by verification; task df277369 backgrounded its own test suite twice and ended the session before it finished, waiting on a notification that a killed-at-final-message process can never receive). Two fixes, one for each half of the same failure shape. First, `AgentPromptBuilder.AppendSessionEndsAtFinalMessageRule` is appended to every working dispatch prompt (`Build`, `BuildFollowUp`, `BuildFixChecks`, `BuildRebase`, `BuildReviewFix`): it states plainly that the session's process is killed at its final message, that backgrounded commands, scheduled wakeups, and monitors never get to fire after that point, and that verification has to run in the foreground and be committed before the final message — closing the gap that let a session hand off to tooling the platform's own dispatch model cannot honor. `BuildReview` needed no addition (`AppendVerdictContract` already carries the equivalent wait-then-conclude rule). `BuildCardPublication` forbids modifying files at all, which covers the commit half of the rule, but not the background-execution half: that prompt's own final step is running `h9k task link-jira` to report the card back, and a session that backgrounds that command or ends before it returns strands a published card the platform never learns about — exactly task df277369's failure shape, just without a worktree. It gets its own narrower addition instead of the full worktree-flavored rule: the session-ends-at-final-message fact, stated once, pointed at that specific reporting command rather than at gates and commits that do not apply there (independent pre-PR review, cycle 2 conformance finding). Second, `VerificationRunner`'s pre-gate stage (#28(d)) is now two checks rather than one: the existing no-commit check (Research-exempt) stands alongside a new uncommitted-files check, reading `git status --porcelain -z --untracked-files=all` in the run's worktree (NUL-separated so a path holding a space or a non-ASCII character comes back verbatim instead of quoted or octal-escaped, and untracked files expanded per-file rather than collapsed to one entry per new directory, so a brand-new vertical slice never `git add`ed is named file by file rather than as one directory — independent pre-PR review, cycle 2 conformance finding) and, when the tree carries modified-or-staged files, failing the run before any gate runs, naming every file left behind, capped at 20 with a "such-and-such more" tail so a wide-rewrite task's file list cannot blow out `h9k status`'s one-line attention cause the way an uncapped gate-output tail is already guarded against (`TailOf`). Untracked files are excluded from that failing list — a gate's own regenerable build/test output is not stranded agent work, and failing a retryable run on it would leave the task permanently stuck since the next session's gates recreate the same file — but they are not silent either (independent pre-PR review, cycle 2 conformance finding: silence here would leave the prompt's own promise to name "anything left modified but uncommitted" partially false for the most common shape of stranded work, a new source file never `git add`ed): they are logged as a distinct warning that never fails the run. This check is deliberately NOT Research-exempt: a research task that left modified files behind still stranded work regardless of what its deliverable is. Both pre-gate checks share the same "never guess" discipline: git unobservable (not a repo, `git` unreachable, the worktree gone) skips the check and logs why, rather than either failing on an unknown or silently treating it as clean. **Does this block the later vision?** No: both changes are local to the dispatch prompt and the existing pre-gate stage, with no dependency on which node dispatches the run or where the worktree lives.
